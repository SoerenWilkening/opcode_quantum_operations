## 1. Julia source excerpt

### 1.1 `soft_fsqrt` — `fsqrt.jl:1-118`, verbatim

```julia
"""
    soft_fsqrt(a::UInt64) -> UInt64

IEEE 754 double-precision square root on raw bit patterns.
Uses only integer operations. Bit-exact with hardware `sqrt`.
Fully branchless.

Algorithm: digit-by-digit restoring sqrt (Ercegovac-Lang, "Digital Arithmetic"
Ch. 6; fdlibm `e_sqrt.c`). Structurally mirrors `soft_fdiv`'s restoring loop.

Kahan's theorem (no-midpoint property of sqrt on floats): the true real-valued
sqrt of a binary64 input is never exactly halfway between two binary64s. A
sticky bit from `remainder != 0` combined with the standard round-to-nearest-
even in `_sf_round_and_pack` therefore produces correctly-rounded output —
no Markstein correction or Tuckerman post-test needed.

Scaling rationale: to produce a 56-bit quotient (53 mantissa + 3 GRS-slot)
with leading 1 at bit 55 (the format `_sf_round_and_pack` expects), we need
a 112-bit radicand (`m_adj << 58`). We stream the radicand from the top of a
conceptual 128-bit register, processing two bits per iteration. Stored as a
`(a_hi, a_lo)` UInt64 pair. 64 iterations cover the full 128 bits; the top
16 bits of the register are zero (leading bit lands at position 110 or 111
depending on exponent parity), so the first ~8 iterations produce leading
zeros in the quotient and the meaningful bit lands at position 55 as
required.

No subnormal result path: `sqrt` of a positive finite maps to
`[2^-537, 2^512]` which is well within the normal Float64 range. Exponent
overflow also impossible.
"""
@inline function soft_fsqrt(a::UInt64)::UInt64
    BIAS = Int64(1023)

    sa = a >> 63
    ea = (a >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK

    # ── Special-case predicates ──
    a_nan  = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    a_inf  = (ea == UInt64(0x7FF)) & (fa == UInt64(0))
    a_zero = (ea == UInt64(0))    & (fa == UInt64(0))
    a_neg  = sa != UInt64(0)

    # ── Mantissa with implicit bit (subnormal: no implicit) ──
    ma = ifelse(ea != UInt64(0), fa | IMPLICIT, fa)
    ea_eff = ifelse(ea != UInt64(0), Int64(ea), Int64(1))

    # Pre-normalize subnormal operands so leading 1 is at bit 52.
    (ma, ea_eff) = _sf_normalize_to_bit52(ma, ea_eff)

    # ── Exponent parity + halving ──
    # We want the unbiased exponent to be even so that result_exp = e_unb / 2.
    # If odd, absorb a factor of 2 into the mantissa: ma_adj = 2*ma, which shifts
    # leading 1 from bit 52 to bit 53. Use arithmetic right shift to handle
    # negative e_unb correctly (floor toward -inf preserves the identity
    # sqrt(m * 2^e) = sqrt(m or 2m) * 2^((e or e-1)/2)).
    e_unb = ea_eff - BIAS
    e_is_odd = (e_unb & Int64(1)) != Int64(0)
    ma_adj = ifelse(e_is_odd, ma << 1, ma)
    result_exp = (e_unb >> 1) + BIAS        # biased result exponent

    # ── Set up 128-bit radicand A = ma_adj << 58 ──
    # Leading 1 of A lands at bit 110 (e_unb even) or 111 (e_unb odd).
    # Split A as (a_hi, a_lo), each UInt64: a_hi holds bits [64..127] of A,
    # a_lo holds bits [0..63]. ma_adj has ≤ 54 bits (bits 0..53), so after
    # shift by 58: bits 0..5 of ma_adj land in a_lo[58..63], bits 6..53 of
    # ma_adj land in a_hi[0..47].
    a_hi = ma_adj >> 6
    a_lo = (ma_adj & UInt64(0x3F)) << 58

    # ── Restoring digit-recurrence sqrt, 64 iterations (2 bits/iter) ──
    # Invariant: after iteration i, r = A_consumed - q², and 0 ≤ r ≤ 2q.
    # A_consumed is the top 2(i+1) bits of A shifted into r so far.
    # The first ~8 iterations extract the all-zero top of A (above bit 111),
    # producing leading-zero bits in q. The meaningful bits of q begin at
    # bit 55 and run down to bit 0, giving the 56-bit working format that
    # `_sf_round_and_pack` expects.
    q = UInt64(0)
    r = UInt64(0)
    for i in 0:63
        top2 = (a_hi >> 62) & UInt64(3)
        a_hi = (a_hi << 2) | (a_lo >> 62)
        a_lo = a_lo << 2

        r = (r << 2) | top2
        t = (q << 2) | UInt64(1)
        fits = r >= t
        r = ifelse(fits, r - t, r)
        q = (q << 1) | ifelse(fits, UInt64(1), UInt64(0))
    end

    # ── Sticky bit from nonzero remainder ──
    # Kahan's theorem: sqrt is never an exact halfway case. OR-ing a 1 into
    # bit 0 of q when r≠0 preserves the tie-break information needed for
    # round-nearest-even inside `_sf_round_and_pack`.
    wr = q | ifelse(r != UInt64(0), UInt64(1), UInt64(0))

    # ── Round + pack ──
    # sqrt of a valid positive finite can neither overflow to Inf nor
    # underflow to subnormal; the overflow flags from `_sf_round_and_pack`
    # are unused here.
    (normal_result, _overflow_result, _exp_overflow, _exp_overflow_after_round) =
        _sf_round_and_pack(wr, result_exp, UInt64(0))

    # ── Special-case select chain ──
    # Order (last override wins): normal → +Inf → ±0 → -finite/-Inf → NaN.
    # `a_nan` must fire strictly last so the NaN passthrough (preserving
    # sign + payload, force-quieting sNaN per Bennett-r84x / U08) wins over
    # the negative-argument invalid-op, since `a_neg_nonzero` also includes
    # negative NaNs (sign=1, fraction!=0).
    a_neg_nonzero = a_neg & (!a_zero)
    result = normal_result
    result = ifelse(a_inf & (!a_neg), INF_BITS, result)                        # +Inf → +Inf
    result = ifelse(a_zero, a, result)                                          # ±0 → ±0 (incl. sqrt(-0) = -0)
    result = ifelse(a_neg_nonzero & (!a_nan), INDEF, result)                    # -finite / -Inf → x86 INDEF
    result = ifelse(a_nan, a | QUIET_BIT, result)                               # NaN → preserve + quiet
    return result
end
```

### 1.2 The loop it mirrors — `fdiv.jl:89-98`, verbatim


**Read the two side by side before §5.1's `cq_divrem_step` question.** They agree on
`fits = r >= <subtrahend>`, on `r = ifelse(fits, r - <subtrahend>, r)` and on
`q = (q << 1) | fits`. They disagree on **what the subtrahend is** — `mb`, a
loop-invariant, against `(q << 2) | 1`, a function of the partial root — and on **how
many bits enter `r` per iteration** — one, implicit in `r = r << 1` off an initial
`r = ma`, against two, streamed from a `(hi, lo)` pair that is itself shifted. Those
two disagreements are the whole of §5.1, and they are what *"structurally mirrors"*
(`fsqrt.jl:9`) does and does not promise.

### 1.3 `_sf_normalize_to_bit52` — `softfloat_common.jl:37-105`, verbatim

```julia
"""
    _sf_normalize_to_bit52(m, e) -> (m, e)

Normalize a mantissa so its leading 1 is at bit 52 (the IEEE 754 normalized
form). Decrement the effective exponent `e` by the shift count. Used by
`soft_fdiv` to pre-normalize subnormal operands before the restoring-division
loop, which assumes `ma, mb ∈ [2^52, 2^53)` so that the ratio fits in 56 bits
of precision. For an already-normalized input (bit 52 set), this is a no-op.

Precondition: `m` has no bits set above bit 52. All callers guarantee this
(subnormal inputs have `m < 2^52`; normal inputs have `m < 2^53` with bit 52
set, so already-normalized).

# Bennett-tpg0 / U135 — m == 0 contract
[... the contract paragraph, softfloat_common.jl:50-66 ...]

Six-stage branchless binary-search CLZ; structure mirrors `_sf_normalize_clz`
but the target bit is 52 instead of 55.
"""
@inline function _sf_normalize_to_bit52(m::UInt64, e::Int64)
    # Bennett-tpg0: defensive guard for m == 0. Substitute IMPLICIT
    # (1<<52, leading 1 already at the target bit) so the CLZ is a
    # no-op; restore zero outputs at the end.
    m_zero = m == UInt64(0)
    e_orig = e
    m = ifelse(m_zero, IMPLICIT, m)

    need32 = (m & (UInt64(0xFFFFFFFF) << 21)) == UInt64(0)
    m = ifelse(need32, m << 32, m)
    e = ifelse(need32, e - Int64(32), e)

    need16 = (m & (UInt64(0xFFFF) << 37)) == UInt64(0)
    m = ifelse(need16, m << 16, m)
    e = ifelse(need16, e - Int64(16), e)

    need8 = (m & (UInt64(0xFF) << 45)) == UInt64(0)
    m = ifelse(need8, m << 8, m)
    e = ifelse(need8, e - Int64(8), e)

    need4 = (m & (UInt64(0xF) << 49)) == UInt64(0)
    m = ifelse(need4, m << 4, m)
    e = ifelse(need4, e - Int64(4), e)

    need2 = (m & (UInt64(0x3) << 51)) == UInt64(0)
    m = ifelse(need2, m << 2, m)
    e = ifelse(need2, e - Int64(2), e)

    need1 = (m & (UInt64(1) << 52)) == UInt64(0)
    m = ifelse(need1, m << 1, m)
    e = ifelse(need1, e - Int64(1), e)

    # Restore zero: byte-identical for m != 0 (m_zero is false, ifelse
    # picks the CLZ result); for m == 0 returns (0, e_orig).
    m_final = ifelse(m_zero, UInt64(0), m)
    e_final = ifelse(m_zero, e_orig, e)
    return (m_final, e_final)
end
```

<< 21` and its five siblings are literal shifts of literals and become `const cq_bit`
tables under §2.0 rule 3, exactly as `_sf_normalize_clz`'s six do (K15 §5.3's
*"constant-folded constants … and not shift rows at all"*).

## 2. Gate sequence as an indexed block table

### 2.0 Grain, spans, and the three representation rules

Identical to **K15 §2.0**, which states them at length; named here only so §2.2 is
readable, because restating them in full would be the second copy that goes stale.

1. **Grain is LITERAL** (PRD-v2 §7.2) — one block per operator occurrence as the
   source spells it, every intermediate a 64-bit span, no CSE, no narrowing towards
   the field width. A `Bool` is a **one-bit** span; `Int64` and `UInt64` are the same
   64 `cq_bit`s and a reinterpret is wiring.
2. **A constant-amount shift and a reinterpret are VIEWS** — zero gates, zero qubits,
   rebuilt from the step index on every call, never carried in mutable state
   (K12.md §2.1, *"must be recomputed from `t`, never carried in mutable state"*).
3. **A constant is a SOURCE, never scratch** (PRD-v2 §7.3) — `FRAC_MASK`, `IMPLICIT`,
   `INF_BITS`, `INDEF`, `QUIET_BIT`, `0x7FF`, `0x3F`, `3`, `1`, `0` and `BIAS` are
   file-static `cq_bit[64]` tables costing **zero qubits**, and the §3 fold table
   elides or demotes every gate they control.

> **K15's §7.3-vs-K12 disagreement about constant masks is live here too and is worth
> more here than there.** K21 has **68** `and`-by-a-constant rows against K15's 15,
> because `(a_hi >> 62) & UInt64(3)` is one of them at every one of 64 iterations.
> Under §7.3 each is a block (`C_and(64)` slots, 64 scratch qubits); under the reading
> K12 uses for a constant relabel each costs nothing. §2.2 follows the **PRD**, as K15
> does. The delta is **68 × 64 = 4,352 scratch qubits** and it is a **PRD amendment**,
> not a kernel choice, so it belongs in PRD-v2 §7.3 or nowhere. Do not settle it in
> `fsqrt.c`, and do not settle it differently from whatever `9ve.21` settles it as.

**One thing is specific to K21 and is not in K15, because K15's compute half is
straight-line and K21's is not: the fold pattern of a view can be a function of the
ITERATION INDEX.** §2.3 states which views that happens to, which it does not, and
what follows for the slot scan.

### 2.1 Scratch layout — flat, one tape, offsets in 64-bit spans

**FLAT, per PRD §15 D9's precedent: one region, everything live for the whole compute
half, peak = total.** D9 chose flat for K12 against two *measured* alternatives and
K15 followed it; K21 follows it too and **re-derives nothing** — no pebbling, no
recomputation schedule, no narrowing of the digit loop's spans towards their provable
widths. Rule 1 and D9 both forbid it and §6's risk 2 is that it looks like an
optimisation every one of 64 times.

The per-block sizes are their modules', read out of the siblings and not re-derived:

| block | scratch it needs, inclusive of its output | authority |
|---|---|---|
| bitwise (`and`/`or`/`xor`) | `W` — the target span only | K01/K02/K03 §2 |
| `eq` / `ne` | `2W − 1` (`diff` `W`, `orr` `W−1`); the flag is `orr[W−2]` | K09 §7.1, `cmp.h` |
| `ult` family | `3W + 1` (`nb` `W`, `carry` `W+1`, `axnb` `W`); the flag is `carry[W]` | K09 §2.2, `cmp.h` |
| `add` (K6) | `2W` (`t` the sum and output, `c` the carry chain) | K06 §2 — **export owed, `9ve.30`** |
| `sub` (K7) | `3W` (`nb`, `d` the output, `c`) | `add.h`, K07 |
| `mux` (K10) | `2W` (`r` the output, `d`) | `mux.h`, K10 §2.1 |
| round-and-pack | `S_round(64)` — **M32's, ask `9ve.19`** | PRD-v2 §5 |
| normalise-to-bit-52 | `S_norm52(64)` — **unassigned, §5.3** | — |

**The digit loop's per-iteration tape, which is the whole of the layout that matters.**
Iteration `t ∈ [0, 64)` owns fifteen spans, laid contiguously in §2.2's phase-G row
order, and the offset of iteration `t` is `t · 961` from the loop region's base:

| span | bits | what it is | produced by |
|---|---:|---|---|
| `top2[t]` | 64 | `(a_hi >> 62) & 3` | G2 `and` target |
| `ahi[t]` | 64 | the next `a_hi` | G5 `or` target |
| `rs[t]` | 64 | `(r << 2) \| top2` — the shifted remainder | G8 `or` target |
| `tt[t]` | 64 | `(q << 2) \| 1` — the trial subtrahend | G10 `or` target |
| `nb[t]` | 64 | `~tt`, inside the comparator | `cq_ult_block.nb` |
| `ucar[t]` | **65** | comparator carry chain — **`ucar[t][64]` IS `fits[t]`** | `cq_ult_block.carry` |
| `axnb[t]` | 64 | `rs ⊕ ~tt`, inside the comparator | `cq_ult_block.axnb` |
| `nsb[t]` | 64 | `~tt`, inside the subtractor | `cq_sub_block.nb` |
| `diff[t]` | 64 | `rs − tt` | `cq_sub_block.d` |
| `scar[t]` | 64 | subtractor carry chain | `cq_sub_block.c` |
| `rnext[t]` | 64 | the next `r` | mux 1's `r` |
| `mdiff[t]` | 64 | mux 1's `t ⊕ f` | mux 1's `d` |
| `qbit[t]` | 64 | `ifelse(fits, 1, 0)` | mux 2's `r` |
| `mqb[t]` | 64 | mux 2's `t ⊕ f` | mux 2's `d` |
| `qnext[t]` | 64 | the next `q` | G16 `or` target |

**`14 × 64 + 65 = 961` bits per iteration**, `64 × 961 = 61,504` for the loop.

> **THERE IS NO `fits[t]` WIRE, AND THAT IS D9(b), NOT A PEEPHOLE.** `fsqrt.jl:87` is
> `fits = r >= t`, a `uge`, and `cq_ult_block`'s `carry[W]` *already holds* `a >=u b`
> (`cmp.h`, *"carry[W] IS `a >=u b`"*). So `fits[t]` is `ucar[t][64]` read in place,
> with **no inversion X and no separate wire** — the same call M16's own `cq_kernel_uge`
> makes and the same one K12's comparator makes. A port that reaches for
> `not1(ult(…))` because Bennett's generic `lower_icmp!` dispatcher does is spending
> `4W` gates and `2W` qubits per iteration — **64 iterations of it here** — to
> reproduce an IR shape libcqops already declines.

`r_0` and `q_0` — `fsqrt.jl:78-79`'s `q = UInt64(0)` and `r = UInt64(0)` — are **real
pre-materialised scratch registers, not runs of literal `CQ_BIT_ZERO`**, which is
**D9(d)** applied verbatim: as literals they would fold, iteration `t = 0` would stop

### 2.2 The block table — 63 rows, in SOURCE ORDER

**Reading instructions.** One row per **operator occurrence** in §1's Julia. `V` = view
(rule 2: zero slots, zero gates, zero qubits). `C_x(w)` is the cost of block `x` at
width `w`, **asked of its module and never written down** — §3.0. `Kn` denotes a
`const cq_bit[64]` constant source (rule 3). Every `ifelse` row names its `cond` first.
**Phase G's sixteen rows are written ONCE and stand for all 64 iterations**; every
other phase's rows run once.

**`==` is `C_eq(W) + 1` and `!=` is `C_eq(W)`.** The eq/ne block's raw flag holds
`a != b` (K09 §7.2, *"it holds `a != b` — the NEGATION of `eq`"*), so `!=` reads it
directly and `==` flips it in place — one `X` on the block's own flag bit, which is
scratch and therefore I6(a)-legal and self-inverse. The comparator runs the other way:
the `ult`-family raw flag holds `a >=u b`, so K21's one `>=` costs **no** inversion.

### 2.3 The one view whose fold pattern moves with the iteration index

**K15 §2.0 rule 2's third rider accepts literal `CQ_BIT_ZERO` in a view's vacated
lanes, and says the cost is that "slot index is not stream index". In a LOOP that
rider needs one more sentence, and this is it.**

Of phase G's seven views, six are **uniform across the 64 iterations** — they relabel a
full-width span by a fixed literal amount every time, so the same lanes fold at every
`t`:

- `G7` (`r << 2`) and `G9` (`q << 2`) vacate exactly two lanes, `G14` (`q << 1`)
  exactly one, at every iteration, because `r` and `q` are full spans (D9(d)'s
  `r_0`/`q_0` are why, and this is the payoff for insisting on them).
- `G1`/`G3` view `a_hi`, which is G5's `or` target — a real 64-bit scratch span at
  every `t ≥ 1` and F1's view over `ma_adj` at `t = 0`.
- `G2`'s `and` against `K3` folds **identically at every iteration**: lanes 2-63 have a
  constant `ZERO` control and emit nothing, lanes 0-1 have a constant `ONE` and demote
  `CCX → CX`. So `top2` costs exactly two `CX` at every `t`, which is a clean
  illustration of §7.3 and not a special case.

**`a_lo` (G4, G6) is the exception, and its degeneration is intrinsic to the
algorithm.** `a_lo` is a **chain of views**: `a_lo[t] = a_lo[t−1] << 2`, so `a_lo[t]`
is `a_lo₀`'s span with `2t` literal-`CQ_BIT_ZERO` lanes at the bottom. At `t ≥ 32` it
is **entirely** literal zeros, G4 is all zeros, and G5's `or` folds its `a_lo` operand
away completely; from `t ≥ 33` the low lanes of `a_hi` are provably zero too and G5
folds further. **The radicand is being consumed — that is what the loop is for.**

**Three things follow and none of them is a defect.**

1. **The SLOT count is unchanged.** `K` is the same at every `t`, so §2.6's modulus
   decode is intact and the driver visits every slot in both directions. K12 states the
   rule: *"The driver must index slots, not gates, so that a slot emitting nothing
   forward is still visited backward."*
2. **The GATE count per iteration is a function of `t`**, and it is still a pure
   function of `t` — deterministic, identical at every operand mask, identical forward
   and backward. So L4's golden is stable and the sandwich still cancels.
3. **§2.7's slot-scan prediction must therefore take `t`**, not just the within-
   iteration index `j`. A scan that predicts from `j` alone goes red at `t = 32` and
   stays red, and the reflex fix — relaxing the prediction to "or nothing" everywhere —
   is what turns the instrument off.

> **AND THE TEMPTING FIX IS THE WRONG ONE.** Making `a_lo` a real scratch register per
> iteration — spelling `a_lo << 2` as a block instead of a view — would buy a uniform
> gate count for **`64 × 64 = 4,096` extra qubits**, and it would not make the value
> any less provably zero; it would only hide the zero from the fold table. It is also a
> re-derivation: the source spells a constant shift, and rule 2 makes a constant shift a
> view. **D9(d) does not reach this case** — D9(d) is about an *initial* value whose
> literal spelling would make `t = 0` differ from `t ≥ 1`, and it is applied above to
> `r_0`/`q_0` where it belongs. Do not extend it to `a_lo` without a PRD amendment.

### 2.4 Copy-out

```
copyout(c) for c in [0, 64):    CX( result[c] -> dst[c] )
```

**64 CX**, `result` being J12's mux output, and `dst` is written nowhere else. That is
Rule 7's `^=`, and it is the whole reason the compute half may leave ~64.8k scratch
bits dirty for the reverse to clean: `dst` never enters the sandwich extent.

### 2.5 I6(a) and I6(b)

**I6(a) — every compute-half gate target a kernel names is scratch. YES, by
construction and not by inspection.** Every row of §2.2 is either a view (emits
nothing) or a block whose targets are the block's own vectors, laid inside K21's one
scratch region. The rail `a` appears in rows A1, A2, A4, J7, J11 and **only ever as a
`const cq_bit *` control**, which `cq_emit_*`'s signature makes structural (Rule 8's
first enforcement mechanism). The constant tables are `const` for the same reason. The
two hand-off rows D1 and I1 inherit the obligation and must be checked in their own
beads, not here.

**I6(b) — every scratch bit is `CQ_BIT_Q` for the whole compute half. YES, and it is
the driver's doing.** `cq_sandwich` pre-materialises the whole region before step 0
(plan §0.2) at zero gates, because scratch is born `CQ_BIT_ZERO`. Two consequences
specific to K21:

- **No fold ever fires on a scratch bit**, so the digit loop's comparator, subtractor
  and muxes emit their full schedules at every iteration regardless of the operand.
- **The folds that DO fire are exactly the constant-source ones and §2.3's `a_lo`
  chain** — identical at every operand mask, identical forward and backward. A
  constant-elided slot is still a slot, visited in both directions, so the palindrome
  is unaffected.

**The I6(a) extent must cover the views' *underlying* spans, and a view is not a
separate allocation.** `rs[t]`'s operand `r << 2` reads `rnext[t−1]`, which is inside
the extent. Nothing targets a view. **And the operand views deliberately ALIAS spans an
earlier iteration wrote** — that is K12 §2.1a's sanctioned shape, sound for its reason:
every use of a previous iteration's output is a **control**, and `cq_ult_block`,
`cq_sub_block` and `cq_mux_block` take their operands as `const cq_bit *` (`cmp.h`,
`add.h`, `mux.h` all say *"controls only; may be scratch views, may overlap"*). **The
reflex "assert the operands are disjoint objects" would reject the correct layout** —
guards compare **ranges**, never base pointers.

**One K21-specific note on contiguity.** K12 needed a deliberate tape layout to make
`r_in[t]` contiguous, because its shifted remainder was a pure relabel spanning two
allocations (`z[t] ++ rnext[t−1]`). **K21 needs no such trick**: under the literal
grain `(r << 2) | top2` is an `or` **block**, so `rs[t]` is a fresh contiguous 64-bit
span that the comparator and subtractor can index directly. The contiguity K12 paid
attention to is free here, and the reason is the grain — which is worth knowing before
someone ports K12's tape arithmetic across and cannot find what it is for.

### 2.6 The step dispatch — a prefix sum, then a modulus, then a prefix sum

**K21 is the first kernel in this catalogue that needs both decodes.** K15's compute
half is straight-line, so its decode is a static prefix sum over named rows; K12's is
`W` identical iterations, so its decode is `t = s / K(W)`, `j = s % K(W)`. K21's is a
prologue, then 64 identical iterations, then a tail.

```
/* built once, at kernel entry, from §2.2's tables — all three parts */
static int pre[32];    /* pre[0] = 0; pre[n+1] = pre[n] + slots(prologue row n)   */
static int tail[17];   /* likewise over phases H, I, J                            */
n_pre  = pre[31]                                    /* the SEAM, §2.2's box       */
K      = slots of phase G's 16 rows                 /* per iteration              */
n_loop = 64 * K
n_compute = n_pre + n_loop + tail[16]

step(s):
    if s < n_pre:                                   /* PRE-NORMALISE half         */
        n = upper_bound(pre, s) - 1;  u = s - pre[n]
        dispatch on prologue row n
    else if s < n_pre + n_loop:                     /* THE DIGIT LOOP             */
        v = s - n_pre;  t = v / K;  j = v % K       /* t in [0, 64)               */
        rebuild the six operand views from t        /* §2.0 rule 2, §2.3          */
        dispatch j into phase G's 16 rows
    else:                                           /* the tail                   */
        n = upper_bound(tail, s - n_pre - n_loop) - 1
        dispatch on tail row n
```

**Four things about this that are load-bearing.**

1. **`pre[]`, `tail[]` and `K` must be pure functions of `W` and of nothing else.** The
   driver replays indices in reverse and a table rebuilt from mutable state would
   desynchronise the halves. Build them at entry from `cq_ult_steps(64)`,
   `cq_sub_steps(64)`, `cq_eq_steps(64)`, `cq_mux_steps(64)`, … — the **measurements**,
   never the literals — which is what makes §3.0's composition identity hold by
   construction rather than by coincidence.
2. **The iteration's six operand views are rebuilt from `t` on every call**, never
   carried across steps (K12.md §2.1). That includes `a_lo`'s `2t` zero lanes (§2.3),
   which is the one whose reconstruction actually has arithmetic in it.
3. **`n_pre` is the seam and the seam is `n_pre`.** If the file splits, the two halves
   must not each own a table. §2.2's seam box says the same thing from the other side.
4. **There is no cursor.** A cached "which row am I in" across steps is mutable state
   across the reversal and is exactly the hazard (1) forbids — the same note K15 §2.5
   makes about its binary search.

### 2.7 The slot-scan derivation — four-valued, and over 64 iterations

**What a K12-shaped kernel gets wrong is the slot arithmetic, not the gates**
(CLAUDE.md's callout, and PRD-v2 §7.1 repeats it for the port). The instrument is
K12's `the_phase_boundaries_match_an_independent_slot_scan`: re-derive the **op KIND**
of every compute-half slot from the blocks' own structure and compare against the
recorded stream at the all-quantum operand mask. It records only which of `X`/`CX`/`CCX`
each slot emits — what a boundary error moves and what a gate-list error does not — so
it is not a second transcription of anything.

**TWO THINGS CHANGE FROM K12'S SCAN AND NEITHER IS OPTIONAL.**

**(a) The kind is FOUR-VALUED**, as K15 §2.6 establishes: `{NONE, X, CX, CCX}`. K12's
scan asserts a 1:1 slot↔stream correspondence; that is **false for K21**, because
§2.0 rule 3's constants make some slots emit nothing and demote others. The scan must
predict per slot and walk the stream with a separate cursor that advances only on
non-`NONE`. A scan that keeps the 1:1 assumption goes red on row A3 and stays red.

**(b) The prediction inside the loop takes `t` as well as `j`**, for §2.3's reason:
`a_lo`'s view degenerates as the radicand is consumed, so G4/G5's fold pattern is a
function of the iteration. This is the fsqrt-specific clause and it is the one a reader
carrying K15's scan across will not have.

```
/* per-block op-kind sub-schedules — each read out of its module's own K-doc,
   none of them re-derived here. Identical to K15 §2.6's list; K21 uses six.   */
sched_and (W, m, v)   /* K02 §2 — one gate per bit; a constant operand mask m  */
sched_or  (W, m, v)   /* K03 §2 — three per bit: CX, CX, CCX                   */
sched_xor (W, m, v)   /* K01 §2 — two CX per bit                               */
sched_eq  (W, v)      /* K09 §2.1 / §7 — the eq/ne compute half                */
sched_ult (W, v)      /* K09 §2.2 — divrem's sched_ult verbatim                */
sched_sub (W, v)      /* K07 / add.h — divrem's sched_sub verbatim             */
sched_mux (v)         /* K10 §2.1 — four slots per bit                         */

/* the boundaries — ASKED of the modules, never written as closed forms */
K       = C_and(64) + 4·C_or(64) + C_ult(64) + C_sub(64) + 2·C_mux(64)
base(t) = n_pre + t·K

predict(slot s):
    decode s as §2.6 does, giving (row r, within-row index v, and t if in the loop)
    kind = sched_<r.block>(64, r.mask, v)
    for each CONTROL lane c the gate reads:
        if c is a constant ZERO lane          -> return NONE      /* gate vanishes */
        if c is a constant ONE  lane          -> demote kind (CCX->CX, CX->X)
    /* the loop-only clause, §2.3 */
    if r in {G4, G5} and the lane comes from a_lo[t]:
        treat lanes [0, 2t) as constant ZERO  /* and, at t >= 32, all 64 lanes  */
    return kind
```

**Three boundaries are worth a named case**, because an off-by-one there produces a
plausible gate rather than a crash:

1. **The `n_pre` seam (F2 ↔ G1 at `t = 0`)** — where the decode switches from prefix
   sum to modulus. Both sides begin with an `and` row, so an off-by-one lands on a
   `CX` either way and only the **operands** differ.
2. **Every iteration boundary, all 63 of them.** This is K21's version of K15's
   *"six identical J-stage groups"* hazard with **sixty-four** groups: an off-by-one
   inside `K` is absorbed by the next iteration and keeps emitting plausible gates all
   the way to the end. §6's risk 1.
3. **The two hand-off rows, D1 and I1**, where M40's slot space ends and another
   bead's module begins — the place contracts go to be assumed.

## 3. Gate-count formula

### 3.0 Symbolic form — substitute, do not re-derive

K21 is a **composition**, not a construction. State it symbolically and substitute; if
a sibling's number moves, re-substitute here rather than re-deriving anything.

```
compute(W) =  n_and64 · C_and(W)  +  n_and1 · C_and(1)
           +  n_or64  · C_or(W)
           +  n_xor1  · C_xor(1)
           + (n_eq + n_ne) · C_eq(W)   +  n_eq      /* the `==` inversions */
           +  n_uge  · C_ult(W)                     /* NO inversion — raw carry[W] */
           +  n_add  · C_add(W)
           +  n_sub  · C_sub(W)
           +  n_mux  · C_mux(W)
           +  C_norm52(W)                           /* row D1 — UNASSIGNED, §5.3   */
           +  C_round(W)                            /* row I1 — M32's, one call    */

sandwiched(W) = 2 · compute(W)  +  W                /* + W copy-out CX */
```

with every `C` **asked of its module at width `W`** and never written down:

| symbol | module | what it is | how it is obtained |
|---|---|---|---|
| `C_and`, `C_or`, `C_xor` | **M10** | one / three / two gates per bit | K02 §2, K03 §2, K01 §2; emitted directly in K21's step function (PRD-v2 §7.10) |
| `C_eq(W)` | **M16** | the eq/ne compute half; raw flag is `a != b` | `cq_eq_steps(W)` — **SHIPPED**, bead `9ve.1` |
| `C_ult(W)` | **M16** | `lower_ult!` minus its `r`/`not1` tail; raw flag `carry[W]` is `a >=u b` | `cq_ult_steps(W)` — shipped |
| `C_sub(W)` | **M14** | `k7_compute` | `cq_sub_steps(W)` — shipped |
| `C_add(W)` | **M14** | `k6_compute`, the out-of-place ripple | `cq_add_steps(W)` — **DOES NOT EXIST**, bead `9ve.30`, §5.4 |
| `C_mux(W)` | **M17** | `lower_mux!` | `4W` via `CQ_MUX_STEPS_PER_BIT`; `cq_mux_steps(W)` would be cleaner |
| `C_norm52(W)` | **nobody** | `_sf_normalize_to_bit52` | **UNASSIGNED — §5.3 is the blocker** |
| `C_round(W)` | **M32** | `_sf_round_and_pack` | `cq_round_steps(W)` — bead `9ve.19` |

**K21 needs no barrel and no multiplier.** Its only shifts are by literals (§5.2), and
it contains no `*` — measured. That is two of PRD-v2 §7.10's three owed exports that
K21 does *not* wait on, and it is the reason `9ve.26` can in principle land before
`9ve.2` and `9ve.3` even though it sits last in §7.15's order.

> ### THE COMPOSITION IDENTITY IS THE ASSERTION THAT SURVIVES `CQOPS_UPDATE_GOLDENS`
>
> `compute(64) = Σ (row's block cost, asked of its module)` over §2.2's 63 rows with
> phase G counted 64 times, using §3.1's occurrence counts. It reads **no golden**, so
> `CQOPS_UPDATE_GOLDENS=1` cannot bless a reduction. CLAUDE.md's K11 callout is the
> reason and K21 offers the trade in a sharper form than K15 does, because K21's
> narrowable spans are inside a **loop**: at iteration `t` the meaningful width of `r`,
> `q` and `tt` is bounded by `2t + 2` (upstream's own invariant, `fsqrt.jl:72`,
> *"0 ≤ r ≤ 2q"*), so narrowing the comparator, subtractor and both muxes towards
> `2t + 2` bits takes the loop from `~64 × 961` scratch bits towards `~64 × 500` and the
> slot count with it. **That is K12's own recorded mutant** — *"the comparator,
> subtractor and mux could be narrowed towards `t + 2` bits … a re-derivation rather
> than a peephole (Rule 1)"* (K12.md's callout in CLAUDE.md) — and it will look like an
> optimisation every time, and **L1/L2/L3/L5 stay green for all of it** because the
> values are right. **Build this check before writing M40.**
>
> It lives in **two** cases, as K11's and K12's do: one that runs **no kernel** and pins
> the eight `C_*` symbols against the modules, and one that pins K21 against what those
> just measured. A sibling's cost moving then reddens the first and **names the block**,
> instead of reddening K21 and looking like K21's bug.

### 3.3 What the composition check is, concretely

Three cases, and none reads a golden:

1. **`the_eight_block_costs_are_what_the_modules_report`** — runs **no kernel**. Calls
   the per-bit costs of `and`/`or`/`xor`, `cq_eq_steps(64)`, `cq_ult_steps(64)`,
   `cq_sub_steps(64)`, `cq_add_steps(64)`, `cq_mux_steps(64)`, `cq_round_steps(64)` and
   whatever `_sf_normalize_to_bit52`'s owner exports, and pins each. A sibling moving
   reddens **this** case and names the block.
2. **`the_digit_loop_is_sixty_four_identical_iterations`** — pins `K` against case 1's
   measurements and pins `cq_fsqrt_steps(64) − n_pre − n_tail == 64 · K`. This is the
   one that catches §6's risk 1: an iteration that is one slot short still divides
   evenly into *something*, but not into `64 · K`.
3. **`the_compute_half_is_the_sum_of_the_sixty_three_rows`** — pins `cq_fsqrt_steps(64)`
   against §3.1's occurrence counts multiplied by case 1's measurements.

Plus **`the_phase_boundaries_match_an_independent_slot_scan`** (§2.7) and
**`the_working_format_handed_to_m32_is_grs_in_bits_2_1_0`**, which is the only
instrument that can see the phase-I encoding contract.

## 4. Ancilla count

**Flat, per PRD §15 D9's precedent: one region, everything live for the whole compute
half, peak = total.** Hand-counted off §2.1's per-block sizes and §3.1's occurrence

| block | `n` | bits each | bits |
|---|---:|---:|---:|
| `and` at 64 — target span | 68 | 64 | 4,352 |
| `and` at 1 | 6 | 1 | 6 |
| `or` at 64 | 259 | 64 | 16,576 |
| `xor` at 1 | 3 | 1 | 3 |
| `eq`/`ne` — `2W − 1` | 11 | 127 | 1,397 |
| `ult` family — `3W + 1` | 64 | 193 | 12,352 |

| `sub` — `3W` | 65 | 192 | 12,480 |
| `mux` — `2W` | 136 | 128 | 17,408 |

**THE DIGIT LOOP IS 95% OF IT AND THAT IS THE ONE SENTENCE THIS SECTION EXISTS FOR.**
64 iterations × **961** bits = **61,504**, against **3,326** for the whole
straight-line prologue and tail. The peak is not driven by the IEEE special-case
machinery, by the class predicates or by the select chain; it is driven by *keeping
every iteration's comparator, subtractor and two muxes live simultaneously*, which is
what FLAT means. Constants contribute **zero** (§2.0 rule 3); views contribute **zero**
(they are relabellings).

**`S_norm52(64)` is not small either, and §5.3 counts it**: six CLZ stages each
carrying an `and` target, an eq extent, a `sub` and two muxes — `6 × 639 + 255 + 256 =
4,345` bits, arithmetic over the same per-block table. If it is transcribed rather than
called, five modules pay it.

**D2's implication, stated and not hedged.** ~64.8k qubits is **3×** K15's 21,310,
**16×** K18's 4,056 peak, and roughly **120×** K12 at i8. D2/D20's pool ceiling is a
**hard** one, and PRD-v2 §4's R11 already records the disposition: the abort comes
**from the pool during pre-materialisation**, unswallowed at the opcode surface, and
**D25's prohibition is the live one — the shim must never grow its own "that will not
fit" check.** Do not add one to M40 either, and do not read this figure as a reason to
narrow the loop (§3.0's box).

**One honest caveat on FLAT.** K21 is the strongest case in the catalogue for the
alternative D9 rejected, because a digit loop's iterations are genuinely sequential and
`rnext[t]`/`qnext[t]` are the only things iteration `t + 1` reads. **That does not
reopen D9.** D9 was decided against *measured* alternatives for K12 and its reasoning —
a nested scheme is not asymptotically better, and a genuinely linear scheme is **filed
for v2** — carries over unchanged. Recomputation is a *re-derivation of the
construction* (Rule 1), it changes the uncompute story, and PRD-v2 does not scope it.
**No pebbling. If the peak is the problem, that is a v2-of-v2 bead, not a kernel
choice.**

## 5. Deltas from upstream

### 5.1 `cq_divrem_step` IS NOT COMPOSABLE HERE, and the reason is in the source

**This is the first question `9ve.26` will ask**, because PRD-v2 §5's M40 row says
*"compose M14/M16/M17's step blocks **as M35 does**"* and M35's own row says *"compose
M19's exported step block, not transcribe it"*. A reader chaining those two sentences
concludes that M40 should use `cq_divrem_step` too. **It cannot, and PRD-v2 is right:
the M40 row names M14/M16/M17 and deliberately does not name M19.** *"As M35 does"*
means *compose an exported step block rather than transcribing gates*; it does not mean
*compose the same block*.

**Three independent reasons, each sufficient on its own.**

1. **THE SUBTRAHEND IS LOOP-VARIANT.** `cq_divrem_block` holds the divisor as a single
   field — `divrem_u.h`'s `const cq_bit *a, *b; /* dividend and divisor; controls only
   */` — bound once for the whole loop, and K12's step function binds `ub = b` into the
   comparator and `b = b` into the subtractor at **every** iteration (K12.md §2.2's P1
   and P2 bindings). `soft_fdiv` can be driven by that because `fdiv.jl:93` compares
   against `mb`, which is loop-invariant. **`soft_fsqrt` compares against `t = (q << 2)
   | UInt64(1)` (`fsqrt.jl:86`) — a function of the partial root accumulated so far,
   different at every iteration.** There is no binding of `cq_divrem_block` that
   expresses a per-iteration subtrahend, and widening it to take one would fork the
   block M19 and M20 already ship against ten pinned goldens.

2. **TWO BITS PER ITERATION, NOT ONE, FROM A SOURCE THE BLOCK HAS NO FIELD FOR.**
   `cq_divrem_step`'s P0 is a single `CX( a[i] -> r[0] )` shifting in one dividend bit
   at index `i = W − 1 − t` (K12.md §2.2). `soft_fsqrt` consumes `top2` — **two** bits
   — per iteration, and it obtains them by shifting a **128-bit `(a_hi, a_lo)` pair**
   left by two (`fsqrt.jl:81-83`), so the radicand is *mutated* every iteration rather
   than indexed. `cq_divrem_block`'s `a` is a `W`-bit dividend read by index. There is
   nowhere in the block for `a_lo` to live, and nothing in `cq_divrem_step` that would
   shift it.

3. **THE ITERATION COUNT IS NOT THE OPERAND WIDTH.** `cq_divrem_steps(W, with_q)` and
   `cq_divrem_region(W, with_q)` are functions of `W` alone and the loop runs `W`
   times. `soft_fsqrt` runs **64** iterations over **64-bit** spans, which coincide,
   over a **112-bit** radicand in a 128-bit conceptual register, which does not
   (`fsqrt.jl:19-21`). Feeding `W = 64` would give the right iteration count for the
   wrong reason — and a reason that stops being right the moment anyone asks what K21
   does at another width.

**A fourth difference that is not a reason but is worth seeing:** K12 writes the
quotient with `CX( ucar[t][W] -> q[i] )` into a fixed register at index `i` (P4), while
`fsqrt.jl:89` spells `q = (q << 1) | ifelse(fits, 1, 0)` — a view, a mux and an `or`,
three rows where K12 has one. That is the IR shape against the source shape, and
§7.2's literal grain settles it in favour of the source.

**What K21 composes instead:** `cq_ult_block`/`cq_ult_step` (M16) for G11,
`cq_sub_block`/`cq_sub_step` (M14) for G12, and `cq_mux_block`/`cq_mux_step` (M17)
twice for G13 and G15 — **the same three blocks K12's own iteration composes**, driven
from K21's own per-iteration slot arithmetic. K21 transcribes **no gate list**; the
only gates it emits directly are the bitwise ones, which are one-to-three gates per bit
and which PRD-v2 §7.10 already assigns to the fp step function (*"Bitwise ops are one
gate per bit and are emitted directly in the fp step function, as K12 emits its two
CNOTs"*). **Rule 1 is satisfied by construction: no gate in the result is ours.**

### 5.5 KAHAN'S THEOREM MAKES M32's TIE BRANCH DEAD IN THIS CALLER

**Upstream states the theorem in the docstring** (`fsqrt.jl:11-15`) and restates the
mechanism at the sticky bit (`fsqrt.jl:93-95`):

> *"Kahan's theorem (no-midpoint property of sqrt on floats): the true real-valued sqrt
> of a binary64 input is never exactly halfway between two binary64s. A sticky bit from
> `remainder != 0` combined with the standard round-to-nearest-even in
> `_sf_round_and_pack` therefore produces correctly-rounded output — no Markstein
> correction or Tuckerman post-test needed."*

**What it buys the port is a row that does not exist, not a row that is cheap.** There
is no correction step to transcribe after phase I — no Markstein iteration, no Tuckerman
test — so the tail is phases H, I and J and nothing else. That is the whole reason K21's
row count is 63 and `fdiv`'s tail is longer.

**And it has a consequence for §5.x that is easy to get backwards.** `_sf_round_and_pack`
decides `round_up = (grs > 4) | ((grs == 4) & (frac odd))`, and `grs == 4` is exactly
guard 1, round 0, sticky 0 — *an exact halfway case*. Kahan says the true root is never
one, so:

> **`grs == 4` IS UNREACHABLE FROM `soft_fsqrt`, SO THE TIES-TO-EVEN BRANCH GETS NO K21
> ANCHOR — AND SAYING SO IS THE POINT.** PRD-v2 §7.12 asks for *"a tie-to-even case in
> each direction"*; for `fsqrt` there is no such input, in either direction. An anchor
> list that carries one is carrying a row that can never go red, and an implementer who
> tries to construct one will spend real time failing to. The **derivation** is
> upstream's theorem, not ours; the **claim that it makes the branch dead in this
> caller** is a hand inference from it and is **UNVERIFIED-BY-EXECUTION** (§6).
> Consequences: M32's `(grs == 4) & (frac odd)` term is **dead but still emitted**
> (literal grain, and the helper is shared with `fadd`/`fmul`/`fdiv`/`fma` where it is
> live), and the nearest reachable substitutes — `grs` just above and just below 4 —
> are anchors 11 and 12, which test the *comparison* rather than the tie.
>
> If `9ve.26` constructs a `grs == 4` witness for `fsqrt`, this box is wrong, upstream's
> `:11-15` is wrong with it, and the finding belongs in a bead rather than in a quiet
> fix.

### 5.8 The classical short-circuit — a C transcription, never the host `sqrt()`

Risk R9's short-circuit applies: an all-classical operand never enters the sandwich and
`dst` is written as constants. **PRD-v2 §7.4 forbids computing those constants with the
host operator**, on a measurement, and **one of its five IEEE-unspecified cells is
reachable from `fsqrt` by name**:

| cell | reached from | this box (x86_64) | the circuit |
|---|---|---|---|
| `sqrt(−1)` | `fsqrt.jl:115`'s `INDEF` arm | `fff8000000000000` | `INDEF` |
| `sqrt(sNaN)` | `fsqrt.jl:116` | the quietened operand, sign and payload preserved | `a \| QUIET_BIT` |
| `sqrt(−qNaN)` | `fsqrt.jl:116` | sign preserved | sign preserved |

They agree **on this box** — §7.4's own table carries the `sqrt(−1)` row measured at
`fff8000000000000` — and they would not on arm64, whose default NaN is positive and
which canonicalises rather than preserving the payload. **So a host-operator
short-circuit gives a program whose classical mode and quantum mode return different
bits on the same input, on some hosts only**, which is the exact failure §7.4 refuses.

**Therefore `cq_fsqrt_classical(uint64_t)` is a C transcription of §1.1's Julia over
`uint64_t`** — the same source, evaluated on constants. Four riders:

- **Never `sqrt()` from `<math.h>`**, not even "just for the normal path": the normal
  path is where rows 11, 12, 14 and 15 live and where a 1-ulp host disagreement would
  be a silent value divergence rather than a NaN-cell one.
- **`-ffp-contract=off`'s reason does not reach here**: the transcription is integer
  only and touches no `double`. The library's only contact with a C `double` in the fp
  surface is the `memcpy` at `cqrt_alloc_f64`/`cqrt_measure_f64` (PRD-v2 §3.1).
- **L1's oracle stays INDEPENDENT**: it is the host `double` `sqrt()` with the three

  transcription. An oracle sharing code with the implementation is blind to what that
  code gets wrong.
- **`tests/support/`'s host probe** (PRD-v2 §7.4, bead `9ve.4`) — round-to-nearest,
  FTZ/DAZ off — must be in place before anchors 17, 18 and 19, or a host with FTZ set

**Cost: ~50 lines**, which is less than K15's ~60 because `fsqrt` is unary and has no
`_sf_propagate_nan2`. The digit loop transcribes as the Julia `for` loop, unrolled by

### 6.5 Ranked risks

1. **THE SLOT ARITHMETIC ACROSS 64 IDENTICAL ITERATIONS.** K15's risk 1 in its worst
   form: an off-by-one inside `K` is **absorbed by the next iteration** and keeps
   emitting plausible gates for the remaining sixty-three, so there is no crash and no
   obviously wrong slot — just a wrong root. K15 has six repeating groups and calls them
   its worst case; K21 has sixty-four. Two specific hazards inside the instrument: the
   kind must be **four-valued** (§2.7(a)), and the prediction must take **`t`** as well
   as `j` (§2.7(b), which K15's scan has no analogue of). §3.3's case 2 —
   `cq_fsqrt_steps(64) − n_pre − n_tail == 64 · K` — is the cheapest detector and should
   exist before any gate is emitted.
2. **THE NARROWING MUTANT, IN A LOOP.** Upstream's own invariant (`:72`, *"0 ≤ r ≤ 2q"*)
   makes `r`, `q` and `tt` provably narrower than 64 bits at every iteration, so the
   "shorten it" mutant is available **64 times**, looks like an optimisation every time,
   and leaves L1/L2/L3/L5 green because the values are right. This is K12's own recorded
   mutant at a larger scale, and **L4 is not a durable detector** because
   `CQOPS_UPDATE_GOLDENS=1` blesses the reduction. The composition check (§3.0's box)
   is the only thing that holds, and it must be written **before** M40.
3. **THE THREE TRANSPOSITIONS IN PHASE G** (§2.2's box) — `top2` read after the shift
   instead of before, `q << 2` swapped with `q << 1`, G13's mux arms swapped. All three
   are invisible to L4, to the palindrome, to the slot scan and to L2/L3, and the only
   detector is L1 against a reference not derived from the kernel. Anchors 9, 10 and 16,
   and **16 is a requirement rather than a pattern**, which means it is the anchor most
   likely to be quietly skipped.
4. **`_sf_normalize_to_bit52` IS UNASSIGNED** (§5.3). It is 34 emitting rows against
   K21's 46 non-loop ones, it has five callers, and leaving it unassigned means four
   modules transcribe it. It changes K21's LOC budget and its row count, so it must be
   decided in PRD-v2 §5 **before** `9ve.26` starts — not discovered in code.
5. **THE M40 ↔ M32 CONTRACT** (§2.2's phase-I box). The G/R/S working format is an
   encoding no C type expresses, and a one-bit disagreement is right on every input that
   does not round. §5.5 makes this *worse* for K21 than for K15 in one specific way:
   the tie branch is unreachable here, so the anchors that would have exercised the
   boundary hardest **do not exist**, and rows 11 and 12 are the nearest available. Plus
   the constant-`result_sign` clause, which is K21's alone among M32's callers.
6. **`9ve.30` IS NOT A LISTED DEPENDENCY OF `9ve.26`** (§5.4). One `+`, one bead, two
   silently-wrong substitutes — and the K8 one is a right forward with a wrong `_unc`,
   which is a miscompile rather than a test failure.
7. **THE ANCILLA FIGURE HAS NO CROSS-CHECK** (§3.2, §4). ~64.8k bits is the largest
   peak proposed in this catalogue and `BENCHMARKS.md` publishes nothing to compare it
   against. R11 is live and its disposition is already decided (PRD-v2 §4, D25: the
   abort comes from the pool during pre-materialisation, and **neither the shim nor M40
   may grow its own "that will not fit" check**), but the *number* is a hand count that
   nothing corroborates.
8. **§7.3's CONSTANT-MASK QUESTION IS WORTH 4,352 QUBITS HERE** (§2.0's box) against
   K15's 960, because `(a_hi >> 62) & 3` runs 64 times. Resolvable only in PRD-v2 §7.3,
   easy to settle silently in code in either direction, and **it must be settled the
   same way for `9ve.21` and `9ve.26`** or two kernels will disagree about what a
   constant mask costs.

### 6.6 What this document is for

It is the specification `9ve.26` implements against, and the thing the composition check
and the slot scan are written from **before** M40 exists. It is not a status claim:
nothing here is on disk, `cq_fsqrt_steps` does not exist, and two of the eight `C_*`
symbols §3.0 depends on are exports that have not been written — one of them by a module
that has not been chosen. Read `bd ready` and the filesystem for what is true today.
