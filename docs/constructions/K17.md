## 1. Julia source excerpt

### 1.1 `soft_fdiv` — `fdiv.jl:44-139`, verbatim

```julia
@inline function soft_fdiv(a::UInt64, b::UInt64)::UInt64
    BIAS      = Int64(1023)

    sa = a >> 63
    ea = (a >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK
    sb = b >> 63
    eb = (b >> 52) & UInt64(0x7FF)
    fb = b & FRAC_MASK

    result_sign = sa ⊻ sb

    a_nan = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    b_nan = (eb == UInt64(0x7FF)) & (fb != UInt64(0))
    a_inf = (ea == UInt64(0x7FF)) & (fa == UInt64(0))
    b_inf = (eb == UInt64(0x7FF)) & (fb == UInt64(0))
    a_zero = (ea == UInt64(0)) & (fa == UInt64(0))
    b_zero = (eb == UInt64(0)) & (fb == UInt64(0))

    inf_result = (result_sign << 63) | INF_BITS
    zero_result = result_sign << 63

    ma = ifelse(ea != UInt64(0), fa | IMPLICIT, fa)
    mb = ifelse(eb != UInt64(0), fb | IMPLICIT, fb)
    ea_eff = ifelse(ea != UInt64(0), Int64(ea), Int64(1))
    eb_eff = ifelse(eb != UInt64(0), Int64(eb), Int64(1))

    (ma, ea_eff) = _sf_normalize_to_bit52(ma, ea_eff)
    (mb, eb_eff) = _sf_normalize_to_bit52(mb, eb_eff)

    result_exp = ea_eff - eb_eff + BIAS

    q = UInt64(0)
    r = ma  # start with full mantissa as initial remainder
    for i in 0:55
        # Check if current remainder can subtract divisor
        fits = r >= mb
        r = ifelse(fits, r - mb, r)
        q = (q << 1) | ifelse(fits, UInt64(1), UInt64(0))
        # Shift remainder left for next iteration (multiply by 2)
        r = r << 1
    end

    # Sticky from remainder
    sticky = ifelse(r != UInt64(0), UInt64(1), UInt64(0))
    wr = q | sticky

    # ── Normalize: leading 1 should be at bit 55 ──
    need_shift = (wr >> 55) == UInt64(0)
    wr = ifelse(need_shift, wr << 1, wr)
    result_exp = ifelse(need_shift, result_exp - Int64(1), result_exp)

    # ── Normalize (subnormal CLZ) ──
    (wr, result_exp) = _sf_normalize_clz(wr, result_exp)

    # ── Subnormal result ──
    (wr, result_exp, flushed_result, subnormal, flush_to_zero) =
        _sf_handle_subnormal(wr, result_exp, result_sign)

    # ── Round + pack ──
    (normal_result, _, exp_overflow, exp_overflow_after_round) =
        _sf_round_and_pack(wr, result_exp, result_sign)

    # ── Select chain ──
    result = normal_result
    result = ifelse(exp_overflow | exp_overflow_after_round, inf_result, result)
    result = ifelse(subnormal & flush_to_zero, flushed_result, result)
    # 0/0 and Inf/Inf are invalid — emit x86 INDEF (Bennett-r84x / U08).
    result = ifelse(a_zero & b_zero, INDEF, result)
    result = ifelse(a_zero & (!b_zero), zero_result, result)
    result = ifelse(b_zero & (!a_zero), inf_result, result)
    result = ifelse(a_inf & b_inf, INDEF, result)
    result = ifelse(a_inf & (!b_inf), inf_result, result)
    result = ifelse(b_inf & (!a_inf), zero_result, result)
    result = ifelse(a_nan | b_nan, _sf_propagate_nan2(a, b, a_nan, b_nan), result)

    return result
end
```

### 1.2 The docstring's four structural claims — `fdiv.jl:8-42`

Each is quoted because the port depends on it and because **only the first is
enforced** by anything in the routine itself.

1. **Both operands are pre-normalised, and it is a bug fix.** *"Both inputs are
   pre-normalized so the leading 1 sits at bit 52 (Bennett-r6e3 fixed a subnormal-divisor
   bug where this was assumed but not enforced — the fix prepends
   `_sf_normalize_to_bit52` to both ma and mb)"* (`:10-13`). The in-body comment at
   `:71-77` repeats the reason: *"without this step the loop overflows and the result's
   low 52 bits zero out"*. **A port that drops either call reproduces a bug upstream
   already found**, and the anchors that catch it are §5.10's subnormal rows.
2. **The loop invariant, which is what makes 56 iterations enough.** *"After
   normalization, ma, mb ∈ [2^52, 2^53), so the true quotient ma/mb ∈ [1/2, 2) and fits
   in 56 bits with 55 fractional bits"* (`:13-14`), maintained as *"`r < 2·mb` before
   each iteration"* (`:16-21`). **This is the claim that makes `r << 1` never lose a
   bit** — and nothing in the circuit checks it, so an implementer who narrows the
   remainder span on the strength of it is doing exactly what K12's and K11's recorded
   findings forbid.
3. **The sticky bit.** *"The final remainder `r` carries the rounded-off tail. We
   collapse any non-zero r into a single **sticky bit** OR'd into the quotient LSB"*
   (`:25-27`).
4. **The one-bit re-normalisation.** *"Then a single normalization shift moves the
   leading 1 from bit 54 to bit 55 if ma < mb"* (`:30-31`) — which is `:106-108`, phase
   J below, and is the row whose polarity is easiest to get backwards.

`fdiv.jl:40-42` records the upstream verification: bit-exact against `Base./` over 5000
random `UInt64` pairs plus the canonical edge cases. **That is upstream's evidence for
upstream's Julia, not ours for our circuit** (Rule 17); it is quoted so nobody cites it
as coverage.

**They are the same algorithm and they are not the same source.** Five differences, in
the order a transcription meets them:

| | `soft_fdiv` (`fdiv.jl:91-98`) | `_soft_udiv_compile` (`divider.jl:26-33`) |
|---|---|---|
| iteration count | **56**, decoupled from the 64-bit spans | **W** = the operand width |
| initial remainder | `r = ma` (`:90`) | `r = 0` (`divider.jl:25`); D9(d) makes it a pre-materialised zero register |

| the middle three | `fits = r >= mb`; `r = ifelse(fits, r − mb, r)` | `fits = r >= b`; `r = ifelse(fits, r − b, r)` — **identical, operator for operator** |
| the quotient | `q = (q << 1) \| ifelse(fits, 1, 0)` — a view, a mux and an `or`, **three rows** | `q = ifelse(fits, q \| (1 << i), q)`, lowered by K12 to **one `CX`** into `q[i]` (P4) |

are not K12's at all.** That asymmetry is §5.1.

## 2. Gate sequence as an indexed block table

### 2.0 Eight decisions the transcription rests on

All follow PRD-v2 §7. Five need a reading and are marked **[DERIVED]**; one is the
**[DECISION FOR THE MAINTAINER]** §5.1 states in full. **None may be settled silently
in code** (CLAUDE.md, *Open blockers*).

**D-K17-1 — the grain is LITERAL and "the Julia type's width" is the rule.** PRD-v2
§7.2, one block per *"operator occurrence as the source spells it"*
(PRD-v2.md:620 @ 5e51ec1), with K18's D-K18-1 clarification: `a_nan`, `b_nan`, `a_inf`, `b_inf`,
`a_zero`, `b_zero`, `fits`, `need_shift`, `subnormal`, `flush_to_zero`,
`exp_overflow`, `exp_overflow_after_round` and every `p_*` of phase N are **`Bool` and
one bit**; `sa`, `ea`, `ma`, `q`, `r`, `wr`, `result_exp`, `result_sign` and every
`res*` are **64**.

**D-K17-2 — a compile-time-constant mask or shift is a VIEW.** PRD-v2 §7.3 as amended,
*"COMPILE-TIME CONSTANT is WIRING, not a block"* (PRD-v2.md:644 @ 5e51ec1). In K17 that
is the six unpack rows, both `<< 63`s, `q << 1` and `r << 1` in every iteration, and
`wr >> 55` / `wr << 1` — **124 of 462 rows**. There is **no runtime mask in `fdiv`'s
own body**; the one in the port is inside M32's `_sf_handle_subnormal` (K23 §2.2.3 row
H14).

**D-K17-3 — [DECISION FOR THE MAINTAINER] the loop is transcribed per operator over
M14/M16/M17's blocks, OR composed from M19's `cq_divrem_step`.** §5.1 has both tables,
both slot identities and both costs. **This document's §2.2 phase H is written against
the first**, and says exactly what changes under the second.

**D-K17-4 — `q`'s seed and the `r << 1` fill lane: literal `CQ_BIT_ZERO`, or a
pre-materialised zero register? [DERIVED]** `q = UInt64(0)` (`:89`) makes iteration 0's
`q << 1` an **all-constant** view, so H6's `or` folds to one `CX` per lane where every
later iteration's costs three slots and two gates; and `r_in(0) = ma` has **no**
constant lane where every `r_in(t ≥ 1)` has exactly one, at lane 0. **Slots are
uniform either way; gates are not**, and K12's D9(d) chose the register *precisely* to
keep a loop uniform — *"as literals they would fold, iteration `t = 0` would stop
costing what every other iteration costs, and the slot decode would need a `t = 0`
branch"* (K12 §2.1). **K18's D-K18-4 chose the opposite for a straight-line kernel,
with the reason stated: no loop, so no uniformity to buy.** K17 has a loop, so K12's
ground applies and K18's does not — but the cost of the register is 64 qubits for `q_0`
and 56 more for the fill lanes, and the decode branch K12 feared is avoidable here
because the non-uniformity is **only at `t = 0`**. This document takes the **literal**
reading and makes §2.3's scan take `t` as well as `j`; `9ve.25` may overturn it **here,
not in code**.

**D-K17-5 — the three class predicates compose M31's `cq_fp_class_block`. [DERIVED]**
`fdiv.jl:56-61` spells six predicates in 28 operator occurrences, and M31 **already
ships** that construction as a block with its own slot count, its own region and its
own tested step function (`fpclass.h`, K22 §2.2). Composing it is plan §0.4 / D9(e)
applied — *"a kernel needing another's construction inside its own compute half calls
that module's exported STEP function"* — and it transcribes the identical operators,
because K22 §2.2's table **is** those 28 occurrences. **K15's phase B transcribes the
same rows inline** (its draft predates M31 shipping), so the two documents disagree
about the row count and not about the circuit; whoever reconciles them should move K15
to the block, not K17 to the inline rows.

**D-K17-6 — `!x` on a `Bool` is `lower_not1!`. [DERIVED, and K15 spells it
differently.]** `fdiv.jl:131-135` writes `(!b_zero)`, `(!a_zero)`, `(!b_inf)`,
`(!a_inf)` — Julia's `Bool` negation, which lowers through `lower_not1!`
(`arith.jl:474-478`): a `CX` into a fresh wire, then an `X`, two slots and one bit.
**K15's phase M rows M8/M11/M16/M19 spell the same negation as `xor`(1) against the
constant `1`** — also two slots and one bit, and a different gate list. **Note that
this is NOT the same occurrence as `fcmp.jl`'s `UInt64(1) − x`**, which the maintainer
decided on 2026-09-18 is M14's `sub` block (PRD-v2 §7.2's amendment, overruling K18's
D-K18-2): that is a `UInt64` subtraction the source spells as arithmetic, where this is
a `Bool` negation the source spells as `!`. The two must not be conflated, and K17
takes `not1`, with K22's and K18's precedent.

**D-K17-7 — the composition identity is over SLOTS, never gates.** K18's D-K18-6, *"the
composition identity is over SLOTS, not gates"* (K18.md:392 @ 5e51ec1). 124 view rows
and every constant operand put classical lanes inside block operands at **every** mask.

**D-K17-8 — the mux arm order is `t = diff`, `f = r`, and nothing structural can check
it.** `r = ifelse(fits, r − mb, r)` binds the *subtracted* value to the true arm. **The
arm swap is invisible to every structural check** — same tuple, same palindrome, clean
scratch, K10's recorded finding — and here it is worse than in K10 because a swapped
arm still divides *something*: it computes a non-restoring recurrence whose value is
wrong only on the iterations where `fits` is true. **Only L1 against a reference not
derived from the kernel sees it.**

### 2.1 Views and constant spans

```
sa   = { a[63] } ++ ZERO[1..63]        /* a >> 63          fdiv.jl:47 */
ea   = a[52..62] ++ ZERO[11..63]       /* (a>>52) & 0x7FF  fdiv.jl:48  — ELEVEN lanes */
fa   = a[0..51]  ++ ZERO[52..63]       /* a & FRAC_MASK    fdiv.jl:49 */
sb, eb, fb  likewise from b            /*                  fdiv.jl:50-52 */

q_in(t+1)  = { ZERO } ++ q_out(t)[0..62]     /* q << 1   fdiv.jl:95 */
r_in(t+1)  = { ZERO } ++ rsel(t)[0..62]      /* r << 1   fdiv.jl:97 */
wr_hi      = wr0[55..63] ++ ZERO[9..63]      /* wr >> 55 fdiv.jl:106 */
```

**ELEVEN LANES FOR THE EXPONENT, NOT TWELVE**, which is K22 §2.1's measured trap:
`a >> 52` is lanes 52..63 and the `& 0x7FF` drops lane 63, the sign. A twelve-lane view
is right for every positive operand and wrong for every negative one, and it survives a
golden, a palindrome and a positive-specials anchor table. M31's `cq_fp_view_exp`
already gets this right and K17 uses it rather than re-assembling the view.

Constant spans, all `cq_fp_const` (`fpfield.h`) and owning nothing: `K_ZERO`, `K_ONE`,
`K_0x7FF`, `K_IMPLICIT`, `K_INF`, `K_INDEF`, `K_QUIET`, `K_BIAS`.

### 2.3 The slot scan — written BEFORE the kernel

**Four-valued, with its own stream cursor** (D-K17-7), on K22 §2.3's and K18 §2.7's
shape, and reusing `sched_ult`, `sched_sub` and `sched_mux` from
`tests/test_kernel_divrem_schedule.inc` rather than re-deriving them.

**And it must take `t` as well as `j`, which K12's does not.** Two rows of phase H fold
differently at `t = 0`:

| row | at `t = 0` | at `t ≥ 1` |
|---|---|---|
| H*t*1, H*t*2 (operand `r_in(t)`) | `ma`: **no** constant lane | one constant `ZERO` lane, at lane 0 |
| H*t*6 (operand `q_in(t) << 1`) | **all 64 lanes constant `ZERO`** — `or(K_ZERO, x)` keeps one `CX` per lane and elides the other two | one constant lane |

That is K21's recorded finding — *a view's fold pattern can depend on the iteration
index* — in its mildest form: a `t = 0` / `t ≥ 1` split rather than a monotone
degeneration. **A scan that predicts from `j` alone goes red on iteration 0 and green
everywhere else, and the reflex fix — dropping the constant rows from the prediction —
turns the instrument off.**

**Non-vacuity is asserted exactly, never as an inequality.** `folded` is the count of
constant-`ZERO` control lanes and is derivable from the view lane maps and the
constants' `popcount`; K22 §2.3 measured that a blanket `demoted > 0` goes red on rows
whose constant is zero.

### 2.3a The span-disjointness scan

**Mandatory, and for K22 §2.3a's measured reason**: collapsing two blocks onto one
offset leaves the value right, the palindrome intact, the pool restored and every gate
count identical (K22.md:204 @ 5e51ec1). K17 has **338 emitting rows with their own
extents and 56 instances of one four-block shape**, so an off-by-one in the per-row
offset table lands inside a *different iteration of the same block* — plausible gates, a
surviving palindrome, and only the value moves.

The scan walks the same slot→stream cursor and asserts that **no qubit index is written
by two spans**, with one addition K22 did not need: **`r_in(t)` and `q_in(t)` are views
over spans an earlier row wrote, and that is legal** (plan §0.4 obligations 3 and 4;
K12 §2.1a). The scan must exempt **reads** and check **writes** only; the reflex
"assert the operands are disjoint objects" rejects the correct layout.

### 2.4 Scratch layout — flat, one region, offsets a compile-time prefix sum

**FLAT** (PRD §15 D9), one `cq_scratch` region, laid out in §2.2's row order, every
span `off`-relative. The per-phase sizes are their blocks', asked of their modules
(K23 §2.4's table for M32's, `cq_fp_class_region` for M31's, and the prose-published
sizes §5.8 flags for M14/M16/M17's):

```
S_fdiv = 64                                                   /* B  xor output      */
       + Σ over C1..C6 cq_fp_class_region(cls)                /* C  M31             */
       + 64                                                   /* D2 or output       */
       + 4·S_eq + 2·64 + 4·S_mux                              /* E                  */
       + 2·S_norm52                                           /* F  M32             */
       + S_sub + S_add                                        /* G                  */
       + 56·( S_ult + S_sub + 2·S_mux + 64 )                  /* H  the loop        */
       + S_eq + S_mux + 64                                    /* I                  */
       + S_eq + 1 + S_mux + S_sub + S_mux                     /* J                  */
       + S_clz + S_subnorm + S_round                          /* K, L, M  M32       */
       + 2·1 + 7·1 + 4·1 + 2·64 + 10·S_mux                    /* N                  */
```

**Phase H is 60% of it**, which is what makes §5.1's decision a pool-ceiling question
as well as a Rule 1 question.

### 2.5 The copy-out

```
copyout(c) for c in [0, 64):    CX( result[c] -> dst[c] )
```

**64 CX**, and `dst` is written nowhere else — Rule 7's `^=`, and the reason the
compute half may leave ~65k scratch bits dirty for the reverse to clean.

### 2.6 I6(a) and I6(b)

**I6(a) — every target a kernel names is scratch. Yes, by construction.** Every row is
a view (emits nothing) or a block whose targets are its own vectors inside K17's one
region. The rails `a` and `b` appear in phases A, C and at N22/N23, and **only ever as
`const cq_bit *` controls**, which `cq_emit_*`'s signature makes structural. The
constant tables are `const` for the same reason. The eleven hand-off rows inherit the
obligation and discharge it in `9ve.18` (shipped) and `9ve.19`.

**I6(b) — every scratch bit is `CQ_BIT_Q` for the whole compute half.** The driver
pre-materialises the whole region before step 0, at zero gates, because scratch is born
`CQ_BIT_ZERO`. So no fold fires on a scratch bit, and the folds that DO fire are exactly
the constant-source and view ones — identical forward and backward, so a constant-elided
slot is still a slot and the palindrome is unaffected.

**The I6(a) extent covers the views' underlying spans, and a view is not a separate
allocation.** `r_in(t)` reads `rsel_{t−1}`, which is inside the extent.

### 2.7 The step dispatch — a prefix sum, a modulus, and a prefix sum

K15's is a pure prefix sum (straight-line) and K12's is a pure modulus (one repeated
iteration). **K17 is both**, which is K21 §2.6's shape:

```
/* built once at kernel entry, from §2.2's table */
static uint32_t pre[N_PRE + 1];    /* phases A..G          */
static uint32_t post[N_POST + 1];  /* phases I..N          */
static int      loop_base, loop_K; /* loop_K = C_ult + C_sub + 2·C_mux + C_or */

step(s):
    if (s < loop_base)                       -> row = upper_bound(pre, s) - 1 ...
    else if (s < loop_base + 56·loop_K)      -> u = s - loop_base;
                                                t = u / loop_K;  j = u % loop_K;
                                                dispatch j into H t 1..H t 6
    else                                     -> row = upper_bound(post, s - …) - 1 ...
```

**`loop_K`, `pre[]` and `post[]` must be pure functions of the block costs and of
nothing else** — the driver replays indices in reverse and a step must be an involution
(plan §0.1, `ckd.14(a)`). **And `loop_K` is ASKED, never written**: it is
`cq_ult_steps(64) + cq_sub_steps(64) + 2·CQ_MUX_STEPS_PER_BIT·64 + 3·64`, which is
§3.4's composition check in one line.

## 3. Gate-count formula

### 3.0 Symbolic form — substitute, do not re-derive

```
compute(64) =  C_xor(64)                                           /* B  */
            +  2·C_class(NAN) + 2·C_class(INF) + 2·C_class(ZERO)   /* C  — M31 */
            +  62·C_or(64) + 2·C_or(1)
            +  6·C_eq(64) + 5·C_not1
            +  129·C_mux(64)
            +  56·C_ult(64)
            +  58·C_sub(64) + C_add(64)
            +  7·C_and(1)
            +  2·C_norm52(64) + C_clz(64) + C_subnorm(64) + C_round(64)   /* M32 */

sandwiched(64) = 2 · compute(64) + 64                              /* + 64 copy-out CX */
```

with every `C` **asked of its module at width 64** and never written down:

## 5. Deltas from upstream

### 5.1 [DECISION FOR THE MAINTAINER] — compose `cq_divrem_step`, or transcribe the loop per operator?

**The two instructions.** PRD-v2 §5's M35 row: the loop *"should compose M19's exported
step block, not transcribe it"* (PRD-v2.md:454 @ 5e51ec1). PRD-v2 §7.2: *"One block per
operator occurrence as the source spells it"* (PRD-v2.md:620 @ 5e51ec1). **Both are
live, and here they select different constructions**, because the thing §5 calls "K12's
shape" is a *different upstream function* from the one `soft_fdiv` contains.

**What the source says, measured (§1.3).** The loop's **middle three lines are
operator-for-operator K12's P1/P2/P3 at `W = 64`, with the same operand bindings and the
same raw-flag convention.** Its **two ends are not K12's**: there is no dividend bit to
shift in (`r << 1` is a pure view where K12 has a `CX`), and the quotient is
`q = (q << 1) | ifelse(fits, 1, 0)` — a view, a mux and an `or` — where K12 has one `CX`
into `q[i]`. And **the iteration count is 56 while the spans are 64**, whereas
`cq_divrem_steps(W, with_q)` and `cq_divrem_region(W, with_q)` are functions of `W`
alone and the loop runs `W` times (`divrem_u.h`).

---

**OPTION A — COMPOSE M19.** Three sub-variants; none is a drop-in.

**A1 — `cq_divrem_block` at `W = 64`.** Fails on three counts at once: 64 iterations
where the source has 56; no field for `r_0 = ma` (K12's initial remainder is a
pre-materialised **zero** register, PRD §15 D9(d) / K12 §3.6); and P4 writes a quotient
bit into a fixed register at index `i`, which is not the `q << 1` accumulation the
source spells. **Not available.**

**A2 — `cq_divrem_block` at `W = 112`, dividend `ma << 55`.** This one *works
mathematically*. With `A = ma·2^55` and the loop's own invariant
`r_k = 2^k·ma − 2·mb·q_k` (`fdiv.jl:16-21`), after 56 iterations
`q_56 = floor(ma·2^55 / mb) = floor(A / mb)` — K12's quotient — and
`r_56 = 2·(A mod mb)`, so `r != 0` and `(A mod mb) != 0` agree and the sticky bit is
preserved. Its block table is **one row**:

| # | occurrence | block | operands | output | slots |
|---:|---|---|---|---|---|
| H1 | `fdiv.jl:89-98`, the whole loop | **M19 `cq_divrem_block`** at `W = 112` | `ma << 55` (a 112-lane view), `mb` (a 112-lane view) | `cq_divrem_quotient` (low 56 lanes), `cq_divrem_remainder` | `cq_divrem_steps(112, 1)` |

and its slot identity is `compute(64) = … + cq_divrem_steps(112, 1) + …` with
`cq_divrem_region(112, 1)` bits. **On the published closed forms in `divrem_u.h` —
`W(17W + 2)` slots and `8W² + 4W − 1` bits — that is ≈ 2.1 × 10⁵ slots and ≈ 1.0 × 10⁵
qubits against option B's ≈ 8.6 × 10⁴ and ≈ 3.9 × 10⁴**: roughly **2.5× the slots and
2.6× the qubits**, because roughly half the 112 iterations produce a quotient bit that
is provably zero and are paid for in full.

**Three things A2 costs beyond the arithmetic.** It is a **re-derivation**: the
equivalence above is a proof of ours, not a line of the source, and Rule 1 forbids
substituting a construction on our own authority — the same objection D9 raised to
narrowing K12 and K11's finding raises to every optimisation-shaped mutant. It puts
`divrem` at a width the **ABI never ships** (`opcode_table.yaml` gives `udiv` at
`i1/i8/i16/i32/i64/i128`; 112 is ours alone), so K12's ten pinned goldens say nothing
about the path K17 would take. And it makes **R11's pool ceiling materially worse** at
the one kernel already near the top of the catalogue.

**A3 — call `cq_divrem_step` for phases P1–P3 only, 56 times.** The index space is flat
(`t = s / K(W)`, K12 §2.2), so a caller *can* address `[t·K + 1, t·K + 17W]`. What it
cannot do is seed `r_0 = ma`: the block's remainder tape starts at `r_in(0) = z[0] ++
r0_hi` with `r0` a pre-materialised zero register the block exposes no accessor for.
Adding an initial-remainder field **forks a block M19 and M20 already ship against ten
pinned goldens** — which is K21 §5.1's reason 1, applied to a different field
(K21.md:1144 @ 5e51ec1).

---

**OPTION B — TRANSCRIBE PER OPERATOR over M14/M16/M17's blocks.** §2.2's phase H: seven
rows per iteration, five emitting, `C_ult(64) + C_sub(64) + 2·C_mux(64) + C_or(64)` per
iteration and `56 ×` that in total. **K17 still transcribes no gate list** — every gate
comes from `cq_ult_step`, `cq_sub_step`, `cq_mux_step` or the inline `or`, which is
plan §0.4 / D9(e) satisfied, and it is exactly what `divrem_u.h` says M19 itself is:
*"M19 TRANSCRIBES NO GATE LIST AT ALL … every gate of the loop body comes out of a
sibling module's EXPORTED step block"*.

Its costs relative to A2: **2.5× fewer slots, 2.6× fewer qubits, three extra row kinds
per iteration** (the `q` view, the 0/1 mux and the `or`), and **56 instances of a
four-block group** for §2.3a's scan to police.

---

**WHAT K21 ALREADY FORCED FOR THE SIBLING, AND WHY ITS REASONS ONLY PARTLY TRANSFER.**
K21 §5.1, *"`cq_divrem_step` IS NOT COMPOSABLE HERE, and the reason is in the source"*
(K21.md:1132 @ 5e51ec1), takes option B for `fsqrt` on three grounds, and reads the M40
row's *"as M35 does"* as meaning *compose an exported step block*, not *compose the same
block*. **Two of its three grounds do not apply to `fdiv` and the third does:**

| K21's ground | `fsqrt` | `fdiv` |
|---|---|---|
| 1. the subtrahend is loop-variant | `t = (q << 2) \| 1`, different every iteration | **does not apply** — `fdiv.jl:93` compares against `mb`, and K21 §5.1 says so in as many words: `soft_fdiv` can be driven by the block because it compares *"against `mb`, which is loop-invariant"* (K21.md:1149 @ 5e51ec1) |
| 2. two bits per iteration from a mutated `(hi, lo)` pair | yes | **does not apply** — one bit, one 64-bit span |
| 3. the iteration count is not the operand width | 64 iterations over a 112-bit radicand | **applies** — 56 iterations over 64-bit spans, and `cq_divrem_*` are functions of `W` alone |

So **`fdiv` is the case K21 explicitly set aside**, and the question is genuinely open
for it in a way it was not for `fsqrt`.

Option B, on four grounds: it is what the *source* spells (§7.2), which is the rule with

### 5.5 The pre-normalisation is a BUG FIX and must not be elided

§1.2 claim 1. `Bennett-r6e3` prepends `_sf_normalize_to_bit52` to **both** `ma` and
`mb` because the 56-iteration loop requires `ma, mb ∈ [2^52, 2^53)` and *"without this
step the loop overflows and the result's low 52 bits zero out"* (`fdiv.jl:71-77`).

**Two things an implementer will be tempted by, and both are wrong.** (i) *"It is a
no-op for normal inputs, so skip it when the operand is normal"* — there is no "when"
in a branchless circuit; the helper is emitted unconditionally and its own `m == 0`
guard handles the zero operand (K23 §1.4). (ii) *"`fdiv` never sees a subnormal because
the select chain catches those"* — false: the select chain catches **zero**, not
subnormal, and `a_zero`/`b_zero` require `fa == 0` as well as `ea == 0`. A subnormal
operand reaches the loop and is exactly the input `Bennett-r6e3` was filed about.

### 5.6 The NaN / Inf / zero predicate rows — sources are views, tests are blocks

Phase C composes M31, phase N reads its six flags. Three things about that boundary:

- **The views are M31's and are eleven lanes for the exponent** (§2.1).
- **`INDEF` is x86's, not IEEE's**, and upstream says so at `fdiv.jl:129`
  (`Bennett-r84x` / U08): `0/0` and `Inf/Inf` give `0xFFF8000000000000`, a **negative**
  quiet NaN. PRD-v2 §7.4's table pins the same cell for the host oracle. A port that
  emits `QNAN` instead is right on the exponent and wrong on the sign bit, which no
  structural check sees.
- **`x/0` with `x != 0` is `inf_result`, which carries `result_sign`** (`:132`), so
  `−1.0 / +0.0` is `−Inf`. The `!b_zero` / `!a_zero` guards at `:131-132` are what make
  the two zero rows exclusive, and they are the four `not1` rows N7/N10/N15/N18
  (D-K17-6).

### 5.11 The classical short-circuit — a C transcription, never the host `/`

PRD-v2 §7.4: the R9 row is a *"transcription of the Julia body over `uint64_t`"*
(PRD-v2.md:681 @ 5e51ec1), never the host `double` operator, because the
IEEE-unspecified cells (`0/0`, `Inf/Inf`, the NaN payload rule) are x86's on this box
and differ on arm64 — *"a program whose classical mode and quantum mode return different
bits on the same input, on some hosts only"*.

**So `cq_fdiv_eval(uint64_t a, uint64_t b)` is §1.1's body over `uint64_t`**, and it
composes M31's `cq_fp_class_eval` and M32's four `_eval` functions (K23's D-K23-9) rather
than transcribing them a fifth time.

**L1's oracle stays independent**: the host `/`, with rows 1, 5, 8–11 of §5.10 asserted
as **literals** so an arm64 box reaches the same verdict. An oracle that shared the
transcription would be blind to exactly what the transcription gets wrong (the Step 18
trap).

### 5.13 THREE THINGS MEASURED AT THE LANDING THAT §5.10 DID NOT HAVE — 2026-09-19

**(1) BINARY DIVISION CANNOT PRODUCE AN EXACT TIE WITH A NORMAL RESULT, so §5.10's
rows 19-20 are subnormal quotients and nothing else will do.** §5.10 asks for "a pair
whose exact quotient has exactly 54 significant bits" and leaves the bit patterns to
the implementer; there are none. After `_sf_normalize_to_bit52` both significands are
integers `ma, mb ∈ [2^52, 2^53)`, and a tie is `q_sig · 2^53 = N` odd, i.e.
`ma · 2^53 = N · mb`. Taking 2-adic valuations, `v2(ma) + 53 = v2(mb) ≥ 53`, and
`mb < 2^53` forbids it. **The tie rows that DO exist are in the subnormal range**,
where the precision is reduced and the rounding position is not bit 53 of the
significand: `5·2^-75 / 2^1000 = 5·2^-1075` ties DOWN and `7·2^-75 / 2^1000` ties UP.
`_sf_round_and_pack` reads the same G/R/S either way, so nothing is lost — but a
search for a NORMAL-result tie never terminates, which is what this note exists to
stop.

**(2) THE SAME COUNT MAKES §5.10's ROW 25 — `exp_overflow_after_round` WITHOUT
`exp_overflow` — UNREACHABLE FOR `fdiv`, so it has no anchor and that is not a hole.**
That flag needs `round_up & mant_overflow` at `result_exp == 0x7FE`
(`softfloat_common.jl:215-221`), and `mant_overflow` needs an all-ones 52-bit fraction
that rounds UP. From `ma ≤ 2·mb − 1` we get `q_sig ≤ 2 − 1/mb < 2 − 2^-53`, strictly
below the midpoint below 2, so an all-ones significand ALWAYS rounds down in the normal
range. `mant_overflow` is reachable from `fdiv` on exactly one path — the
subnormal→normal carry, where the shift has moved the rounding position — and
`(2^53−1)·2^-75 / 2^1000` is the anchor that fires it, landing on `MIN_NORMAL`. The
catalogue's coverage of the normal-range cell is `fmul`'s `FM_OVFAFT` row.

**(3) THE HOST `/` ANSWERS `0/0` AND `Inf/Inf` DIFFERENTLY DEPENDING ON WHETHER IT
EXECUTES, so §7.4's pin-by-table is load-bearing on THIS box and not only on arm64.**
Measured while writing `ref_fdiv`, this x86_64 box, Apple clang 17,
`-std=c11 -ffp-contract=off`: with the operands `volatile`, both cells give
`fff8000000000000` — x86's INDEF and Bennett's — at `-O0` and `-O2` alike; with the
operands visible to the optimiser as constants, clang FOLDS the division and returns
`7ff8000000000000`, LLVM's positive default NaN, with **the sign bit the other way
up**. That is M34's finding (the host `*` returns a different NaN payload at `-O0` and
`-O2`) in a new dress, and the variable is not the payload but whether the expression
was executed at all. `ref_fdiv` answers the NaN rows, `0/0` and `Inf/Inf` from a TABLE
and calls the host only where IEEE specifies the result; a case in
`the_classical_row_agrees_with_the_oracle_on_every_anchor` asserts the two INDEF rows
directly, so an oracle rewritten to call the host with literals goes red.

**(4) A RIDER ON §5.10 ROWS 15-16, and it is a correction rather than an addition.**
`need_shift` is `(wr >> 55) == 0`, and bit 55 of `q` is iteration 0's `fits`, so it is
`ma < mb` **on the significands** and not on the values. §5.10's named pairs
`(1.0, 2.0)` and `(4.0, 2.0)` both have `ma == mb` and are therefore BOTH the
`need_shift == FALSE` side; the shipped matched pair is `(1.0, 1.5)` and `(1.5, 1.0)`.
`(1.0, 2.0)` is kept, as the exact-quotient row.

**(5) §5.10's ROW 18 — "sticky SET, an inexact quotient" — DOES NOT DISCRIMINATE, AND A
MUTANT FOUND THAT RATHER THAN A REVIEW.** Pinning `sticky` to 0 left **all 167** L1
cases green and was seen only by `l4_goldens` — the detector K11's finding says is not
durable, because `CQOPS_UPDATE_GOLDENS=1` blesses it. `_sf_round_and_pack` rounds up on
`grs > 4` or on `grs == 4 & frac odd`, so with `q`'s bit 0 clear the two readings differ
**exactly** when `g == 1`, `r == 0` and `frac` is EVEN: 5 rounds up where 4 is a tie an
even `frac` sends down. `1.0/3.0` is inexact and its retained LSB is odd, so both
readings agree. The shipped list gains a 29th row — **`0x3ffd333d0241c32b` over
`0x3ff5eac5652ef033`**, found with an independent integer model of `fdiv.jl:91-98` and
written down as the patterns it printed — and `l1_sweep` now kills the mutant. K15's own
anchor note already asked for "a sticky bit that is SET AND LOAD-BEARING"; §5.10's row 18
is the weaker claim and this is what the difference is worth.

**(6) THE `need_shift` ROW'S TWO FAILURE DIRECTIONS ARE NOT SYMMETRIC, and ONE OF THEM IS
AN EQUIVALENT MUTANT — recorded at the site in `fdiv.c` rather than "fixed".** Shifting
LESS than it should (`wr >> 54` in place of `wr >> 55`) leaves the leading 1 at bit 54
with `result_exp` one higher, and `_sf_normalize_clz` at `:111` then normalises exactly
that: `(wr, exp)` and `(wr << 1, exp − 1)` denote the same number. MEASURED: every L1
case green, only the golden moves. So `:106-108` is a **fast path** for a row CLZ would
otherwise walk — and it is transcribed all the same, because it is in the source
(Rule 1). Shifting MORE than it should — reading the raw `eq` flag instead of
`need_shift` — pushes a leading 1 already at bit 55 up to bit 56, which CLZ only shifts
LEFT and therefore cannot recover: MEASURED, killed by `l1_sweep` and by nothing else,
not even by L4. **The paired mutation is what proves the first half equivalent rather
than leaving it untested** (CLAUDE.md's recorded shape), and the second half is why the
`not1` stays.

### 6.5 Ranked risks

1. **THE [DECISION FOR THE MAINTAINER] ITSELF (§5.1).** It moves phase H between 392
   rows and 1, the compute half by a factor of ~2.5, the ancilla peak by ~2.6, and the
   meaning of ten of K12's pinned goldens. **It must be settled in PRD-v2 §5 before
   `9ve.25` starts**, because an implementer who meets it mid-kernel will settle it by
   whichever is easier to write that afternoon.
2. **THE SLOT ARITHMETIC — 462 boundaries, 56 of them the same four-block group.**
   §2.3's four-valued scan **with `t` in the prediction**, plus §2.3a's disjointness
   scan. An off-by-one inside the loop lands in a neighbouring iteration and emits a
   plausible gate rather than crashing.
3. **THE G/R/S AND BIT-52 HAND-OFFS (§1.7 of K23, phases F/L/M here).** Five hand-off
   sites across a bead boundary, wrong only on ties, detected only by anchors 19–21 and

   And the reference must not be derived from the kernel — `ref_fdiv` is a C
   transcription plus the host `/`, not the kernel's own recurrence.
5. **THE PRE-NORMALISATION (§5.5).** Dropping it reproduces a bug upstream already
   found and fixed, and it looks like dead code on every normal operand — which is every
   operand a random draw of 32 produces.
6. **`9ve.30` IS MISSING FROM `bd 9ve.25`'s DEPENDS-ON (§5.9)**, and the substitute an

8. **R11's POOL CEILING (§4).** ≈ 6.5 × 10⁴ scratch bits on the literal reading and
