**Clean or sandwich:** **sandwich.** Every inner block is dirty by design — `lower_eq!`
leaves `diff` and the OR-prefix, `lower_ult!` leaves `nb`, the whole carry chain and
`axnb`, `lower_mux!` leaves `diff` — and on top of that the port's own 64-bit intermediates
(`ea`, `fa`, `abs_a`, …) are never uncomputed by the source, because Julia has no notion of
uncomputing them. Bennett-in-the-small applies (Rule 2, PRD §5): compute the flag into
scratch, XOR it into `dst`, replay the compute half in reverse, release scratch. Cost is
2× the compute half and **that is not negotiable down** — every "narrow this field to 11
bits" saving is refused in §5.

**Result shape — K9's, exactly.** `fcmp` produces **one bit**. Upstream calls the
`soft_fcmp_*` callee at width `w` and immediately truncates:
`IRCall(call_dest, callee, [op1, op2], [w, w], w)` then
`IRCast(dest, :trunc, ssa(call_dest), w, 1)` (`instructions.jl:7739-7742`), under the
comment *"soft_fcmp returns UInt64 (0 or 1), but fcmp result is i1"*
(`instructions.jl:7736-7737`). So the signature is PRD-v2 §7.11's *"K9's shape (`dst` one
bit, `W` the operand width, the adapter passing `sh->w[0]`)"*:

```c
void cq_kernel_fcmp_olt(cq_ctx*, cq_bit *dst, const cq_bit *a, const cq_bit *b, int W);
/* … one entry point per predicate; W == 64 is the only shipped width (PRD-v2 §1). */
```

`a` and `b` are `W` bits; **`dst` is exactly one `cq_bit`**; the copy-out is **1 CX (+ at
most 1 X)**, never `W` CNOTs. The kernel asserts its own extent with
`cq_kernel_check_n(dst, 1, src, w, 2)`, as `cmp.c` does — `cq_kernel_check_dst`'s arity-2
wrapper would compare `dst`'s one bit against `W` and is wrong here. The test spec needs
K9's adapter: `cq_kd_case`'s default call path is defined only for the arity-2, one-width
shape and `shape_of` **refuses** anything else, so a spec with `w_dst = 1` and no `call`
adapter is a hard error rather than a suite that silently runs every case at `W = 1`.

## 1. Julia source excerpt

`fcmp.jl`, verbatim at `980805de`. Docstrings retained where they carry a semantic claim
the port depends on (the `+0 == −0` rule, the `une ≡ !oeq` identity, the first-operand NaN
convention).

```julia
# fcmp.jl:8-47 — soft_fcmp_olt
function soft_fcmp_olt(a::UInt64, b::UInt64)::UInt64
    SIGN_MASK = UInt64(0x8000000000000000)
    ABS_MASK  = UInt64(0x7FFFFFFFFFFFFFFF)

    sa = a >> 63
    sb = b >> 63
    ea = (a >> 52) & UInt64(0x7FF)
    eb = (b >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK
    fb = b & FRAC_MASK
    abs_a = a & ABS_MASK
    abs_b = b & ABS_MASK

    # NaN check: exponent all-ones with non-zero fraction
    a_nan = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    b_nan = (eb == UInt64(0x7FF)) & (fb != UInt64(0))
    either_nan = a_nan | b_nan

    # Both zero (±0 == ±0)
    both_zero = (abs_a == UInt64(0)) & (abs_b == UInt64(0))

    # Same sign comparison
    # For positive: a < b iff abs_a < abs_b
    # For negative: a < b iff abs_a > abs_b
    pos_lt = abs_a < abs_b      # |a| < |b|
    neg_lt = abs_a > abs_b      # |a| > |b| (more negative)

    # Different sign: negative < positive (unless both zero)
    diff_sign_lt = (sa > sb)    # a is negative, b is positive

    same_sign = sa == sb
    result = ifelse(same_sign,
                    ifelse(sa == UInt64(0), pos_lt, neg_lt),
                    diff_sign_lt)

    # Override: NaN → false, both zero → false
    result = result & (!both_zero) & (!either_nan)

    return UInt64(result)
end
```

```julia
# fcmp.jl:50-82 — soft_fcmp_oeq
#   "IEEE 754 ordered equal comparison on raw bit patterns.
#    Returns 1 if a == b (and neither is NaN), 0 otherwise.
#    Note: +0.0 == -0.0 per IEEE 754.  Fully branchless."
function soft_fcmp_oeq(a::UInt64, b::UInt64)::UInt64
    ABS_MASK  = UInt64(0x7FFFFFFFFFFFFFFF)

    ea = (a >> 52) & UInt64(0x7FF)
    eb = (b >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK
    fb = b & FRAC_MASK
    abs_a = a & ABS_MASK
    abs_b = b & ABS_MASK

    # NaN check
    a_nan = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    b_nan = (eb == UInt64(0x7FF)) & (fb != UInt64(0))
    either_nan = a_nan | b_nan

    # +0.0 == -0.0: both absolute values zero
    both_zero = (abs_a == UInt64(0)) & (abs_b == UInt64(0))

    # Bitwise equal or both zero
    result = (a == b) | both_zero

    # NaN != anything
    result = result & (!either_nan)

    return UInt64(result)
end
```

```julia
# fcmp.jl:111-125 — _either_nan
#   "Branchless test: at least one of `a`, `b` is a (quiet or signalling) NaN
#    in IEEE 754 binary64. NaN encoding: exponent = `0x7FF` AND fraction != 0."
@inline function _either_nan(a::UInt64, b::UInt64)::Bool
    ea = (a >> 52) & UInt64(0x7FF)
    eb = (b >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK
    fb = b & FRAC_MASK
    a_nan = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    b_nan = (eb == UInt64(0x7FF)) & (fb != UInt64(0))
    return a_nan | b_nan
end
```

```julia
# fcmp.jl:89-91, :101-103, :133-135, :143-145, :153-155, :163-165, :173-175, :183-185
@inline function soft_fcmp_ole(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_olt(a, b) | soft_fcmp_oeq(a, b)
end

#   "`une` ≡ `uno | one` ≡ `!oeq` (the latter holds because both unordered
#    operands AND ordered-not-equal operands have `oeq == 0`)."
@inline function soft_fcmp_une(a::UInt64, b::UInt64)::UInt64
    return UInt64(1) - soft_fcmp_oeq(a, b)
end

function soft_fcmp_ord(a::UInt64, b::UInt64)::UInt64
    return UInt64(!_either_nan(a, b))
end

function soft_fcmp_uno(a::UInt64, b::UInt64)::UInt64
    return UInt64(_either_nan(a, b))
end

#   "IEEE 754 ordered not-equal: both operands are non-NaN AND `a != b`.
#    Note `+0.0 == -0.0` per IEEE 754, so `one(+0, -0)` returns 0."
@inline function soft_fcmp_one(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_ord(a, b) & (UInt64(1) - soft_fcmp_oeq(a, b))
end

@inline function soft_fcmp_ueq(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_uno(a, b) | soft_fcmp_oeq(a, b)
end

@inline function soft_fcmp_ult(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_uno(a, b) | soft_fcmp_olt(a, b)
end

@inline function soft_fcmp_ule(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_uno(a, b) | soft_fcmp_ole(a, b)
end
```

**FOUR SWAP AND ZERO INVERT, AND THAT IS THE HEADLINE DIFFERENCE FROM K9.** K9's
`lower_icmp!` dispatch has *both* axes — four swaps (`ugt`, `ule`, `sgt`, `sle`) and five
`lower_not1!` inversions (`ne`, `ule`, `uge`, `sle`, `sge`; CLAUDE.md's callout states the
inverting set as `eq`, `ult`, `ugt`, `slt`, `sgt` because it is talking about the polarity
of the *raw scratch wire*, which is the complementary reading of the same fact). The fp
dispatch has **no `not1` arm at all**: every one of the fourteen rows is a bare callee, four
of them with the arguments exchanged. The inversion has not vanished — it has moved
**inside** the exported bodies (`une` is `1 − oeq` at `fcmp.jl:102`, `ord` is
`!_either_nan` at `:134`, and `one` contains the same `1 − oeq` at `:154`) — but it is no
longer a property of the dispatch table, and an implementer who copies K9's two-axis
dispatch across will write a table that is wrong in eight rows.

**THREE NEAR-MISSES, EACH OF WHICH LOOKS RIGHT.**

1. **`ugt` is a swap in BOTH tables and `ule` is a swap in K9 and NOT in fp.** K9 swaps
   `{ugt, ule, sgt, sle}`; fp swaps `{ogt, oge, ugt, uge}`. The intersection is `{ugt}`
   alone. Carrying K9's set over gives `ule` a spurious swap — and `ule` is symmetric
   enough in its NaN behaviour that the error survives every ordered pair where the
   operands compare equal, which is exactly the kind of case a 32-sample draw is full of.
2. **The two sets are DISJOINT here, where K9's overlap.** K9's swap and invert sets share
   `ugt` and `sgt`. For fp the swap set is `{ogt, oge, ugt, uge}` and the body-level
   inverting set is `{ord, one, une}` — no element in common. "The two sets are not the
   same set" is true for both tables and for *different reasons*, so the sentence cannot be
   reused as a check.
3. **The swap is `ole`, not `olt`, for `oge`.** `oge ≡ ole(b, a)` and `ogt ≡ olt(b, a)`;
   the analogous unordered pair is `uge ≡ ule(b, a)` and `ugt ≡ ult(b, a)`. Pairing `oge`
   with `olt` (or `uge` with `ult`) is off by the equality case only — it differs on
   exactly the inputs where `a == b`, and is invisible to every structural check.

**THE NaN COLUMN IS THE SECOND THING TO GET RIGHT, AND IT IS A FAMILY PROPERTY.** Every
`o*` predicate is *(the ordered relation)* **AND NOT unordered**; every `u*` predicate is
*(the ordered relation)* **OR unordered**. In the source that shows up as two different
spellings, and both must be transcribed as they stand:

- `olt` and `oeq` carry the override **inside** the body — `result & (!both_zero) &
  (!either_nan)` (`fcmp.jl:44`) and `result & (!either_nan)` (`:79`). `ole` inherits it
  from both of its disjuncts and adds nothing.
- `ord` / `uno` are the override alone (`:134`, `:144`).
- `ult` / `ule` / `ueq` add it as a **disjunct** (`uno | …`, `:174`, `:184`, `:164`).
- `one` is the only row that uses `ord` as a **conjunct** (`:154`).
- `une` gets it for free: `1 − oeq` is 1 whenever `oeq` is 0, which includes every
  unordered pair (the docstring at `:98-99` states exactly this and it is worth reading
  before "simplifying" `une` into `one | uno`).

**AND THE `both_zero` OVERRIDE IS `olt`-ONLY.** `soft_fcmp_olt` kills its result when
`|a| == |b| == 0` (`fcmp.jl:44`); `soft_fcmp_oeq` does the opposite and *adds* `both_zero`
as a disjunct (`:76`). That asymmetry is IEEE `+0 == −0` and it is the single most
load-bearing line in the file: drop `both_zero` from `olt` and `olt(−0.0, +0.0)` returns
**true**, because `sa > sb` holds. Drop it from `oeq` and `oeq(+0.0, −0.0)` returns
**false**. Neither error moves a gate count.

**WHERE K9'S TABLE DOES CARRY OVER, AND IT IS ONE ROW.** The operand swap costs nothing —
it is an argument-order change at the entry point, not a circuit — exactly as in K9.
Nothing else transfers.

## 2. Gate sequence as indexed pseudo-code

### 2.0 Six decisions the transcription rests on

All six follow PRD-v2 §7; three of them are places where §7's general rule needs a reading,
and those are marked **[DERIVED]** and re-listed in §6.2. None may be settled silently in
code (CLAUDE.md, *Open blockers*).

**D-K18-1 — the grain is LITERAL, and "64-bit span" means *the Julia type's width*.**
PRD-v2 §7.2 fixes *"one block per operator occurrence as the source spells it; every
intermediate a 64-bit span (the Julia type's width); no common-subexpression sharing; no
narrowing towards the field width."* For `fadd` those two clauses agree because every
intermediate there is a `UInt64`. **`fcmp.jl` is the file where they come apart**: `a_nan`,
`b_nan`, `either_nan`, `both_zero`, `pos_lt`, `neg_lt`, `diff_sign_lt`, `same_sign` and
`result` are all `Bool`. The parenthetical is the rule, so a `Bool` intermediate is **one
bit** and a `UInt64` intermediate is **64 bits**. **[DERIVED]** — and the alternative
(padding every `Bool` to 64) is refused twice over: it multiplies the scratch by ~60 for no
value, and it makes the two `ifelse` rows a 64-bit mux whose `cond` is one bit and whose
arms are 63 lanes of nothing, which is not what `lower_mux!` does. What the rule *does*
forbid, and what stays forbidden, is narrowing `ea` to 11 bits or `sa` to 1 bit because the
value happens to fit (§5 delta 6).

**D-K18-2 — `UInt64(1) - x` on a `soft_fcmp_*` result is `lower_not1!`, not a 64-bit
subtractor. [DERIVED]** The occurrence is at `fcmp.jl:102` (`une`) and `:154` (`one`).
Read as a general `-`, it is M14's `sub` block at `W = 64`; read as what the file's own
docstring calls it — *"`une` ≡ … ≡ `!oeq`"* (`fcmp.jl:98`) — it is a logical NOT on a 0/1
value. The two agree in **all sixty-four lanes** (`1−0 = 1`, `1−1 = 0`, every higher lane
zero either way), so this is not a correctness fork; it is a cost fork of one `C_sub(64)`
per site, and the source states the identity itself. **Draft decision: `lower_not1!` — OVERRULED 2026-09-18 by the maintainer (PRD-v2 §7.2, amended the same day): the occurrence is transcribed as M14's `sub` block with the constant `1` as a source, one block per operator occurrence. §5 delta 7 now records `lower_not1!` as the refused alternative.**

**D-K18-3 — constants are `const cq_bit` SOURCES and the fold table elides the gates they
control.** PRD-v2 §7.3, verbatim, and its cited ground is `arith.jl:202` — *"Constants are
always safe (their wires are freshly allocated by resolve!)"* — which is what upstream does
and what we deliberately do not. The four constants K18 needs are `0x7FF` (the exponent
compare and the mask), `FRAC_MASK`, `ABS_MASK` and an all-zero span. §7.3's consequence is
explicit: *"Our peak is therefore BELOW upstream's ancilla figure for the same
construction, and the difference is not a bug to chase in either direction."*

**D-K18-4 — a constant shift is WIRING, and its vacated lanes are literal `CQ_BIT_ZERO`
entries of a read-only view. [DERIVED]** Upstream's `lower_lshr!` (`arith.jl:314-320`)
allocates a fresh `W`-wide vector and emits `W − k` CNOTs into it. K12 already declines
that for its shifted remainder — *"a view, not a register … the left shift is therefore a
relabelling of `cq_bit` array entries and costs zero gates and zero qubits"* (K12.md §2.1)
— and K18 takes the same view. **Where K18 parts from K12 is the FILL.** K12's D9(d) makes
the vacated lanes a real pre-materialised scratch register `r0_hi`, on the ground that
literal zeros *"would fold, iteration `t = 0` would stop costing what every other iteration
costs, and the slot decode would need a `t = 0` branch."* **That ground does not carry
here, because K18 has no loop**: every block occurrence has a *statically known* operand
lane map, so the slot decode needs no branch and §2.6's scan can predict every elision at
compile time. Taking D9(d)'s answer instead would cost 64 qubits per shift occurrence to
buy uniformity that K18 already has for free. Both readings are self-consistent; this
document takes literal `CQ_BIT_ZERO`, and **9ve.20 may overturn it only here, not in
code.** Two riders that make it safe: a view is only ever a *source* (I6 — sources appear
only as controls), and a `CCX` whose two controls are both constant `ZERO` is a **legal
fold**, not a distinctness violation (`cq_bit_coincident` has no pointer-identity clause,
and PRD §3 says the check *"cannot fire on two constants"*), so one shared all-zero
constant span may serve every fill and every `== 0` operand.

**D-K18-5 — the inner blocks' RAW wires are read directly, and the polarity is fixed per
occurrence.** M16's `cq_ult_block` publishes *"`carry[W]` IS `a >=u b`"* (`src/kernels/cmp.h`)
and `cq_kernel_uge` copies it out unchanged — Bennett's `lower_not1!(lower_ult!(…))` double
negation folded into the copy-out, K09.md §5 delta 2, ratified as PRD §15 D9(b) when K12
made the same choice. K18 follows: an `eq` block's raw wire is `a != b`, an `ult` block's
raw wire is `a >=u b`. Therefore

| source occurrence | what the raw wire gives | extra |
|---|---|---|
| `x != y` (`fcmp.jl:22`, `:23`, `:68`, `:69`, `:122`, `:123`) | exactly the value | **none** |
| `x == y` (`:22`, `:23`, `:27`, `:38`, `:40`, `:68`, `:69`, `:73`, `:76`, `:122`, `:123`) | the complement | one `lower_not1!` |
| `x < y` (`:32`) | the complement | one `lower_not1!` |
| `x > y` (`:33`, `:36`) | the complement, on swapped operands | one `lower_not1!` |

The alternative — transcribing `lower_icmp!`'s own `r`-wire tail and then `lower_not1!` on
top — puts **two different realisations of `eq` in one library**, with the more expensive
one inside the kernel that calls it eight times. K12.md §3.0's second trap records exactly
that mistake being made and corrected.

**D-K18-6 — the composition identity is over SLOTS, not gates. [DERIVED]** K12's identity
`compute = W·(2 + C_ult + C_sub + C_mux)` is a *gate* identity because at the all-quantum
mask no fold can fire inside it — every operand of every K12 block is a pre-materialised
scratch bit. **K18 is the first kernel where that is false**: D-K18-3 and D-K18-4 put
classical lanes *inside* block operands (a constant mask, a shift's zero fill), and those
lanes fold at **every** operand mask including the all-quantum one L4 pins. So a compute
slot may legitimately emit **nothing**, or emit a `CX` where the schedule says `CCX`. The
durable identity is therefore over slot counts:

> `n_compute(pred) = Σ over §2.3's table of each block's own step count, asked of its
> module at width 64` — never written down as a closed form, and never compared against a
> gate total.

The gate total is the golden's business, and §2.6's slot scan is what pins the *shape*.
**Do not "fix" a red slot scan by asserting one-gate-per-slot**; that assertion is K12's
and it does not hold here.

### 2.1 Vocabulary

`W = 64` throughout (PRD-v2 §1: `f64` only). Lane `i` is bit `i` of the IEEE pattern, lane
63 the sign. Three kinds of thing appear as a block operand:

| kind | owns qubits? | example |
|---|---|---|
| **rail** — the caller's `a` / `b` | yes, and they are `CQ_BIT_Q` at the L4 mask | `a`, `b` |
| **scratch span** — pre-materialised by `cq_sandwich` at step 0 under I6(b), so `CQ_BIT_Q` for the whole compute half | yes | `ea`, `fa`, every block's internals, every 1-bit flag |
| **constant span / view** — `const cq_bit` of `CQ_BIT_ZERO`/`CQ_BIT_ONE`, or a read-only view mixing rail lanes with constant lanes | **no** | `K_0x7FF`, `K_FRAC`, `K_ABS`, `K_ZERO`, `sa`, `sb`, `a_hi`, `b_hi` |

The four constant spans, built once per call as `const cq_bit[64]` and owning nothing:

```
K_ZERO   all 64 lanes CQ_BIT_ZERO          — the `== 0` operand AND every shift's fill
K_0x7FF  lanes 0..10 ONE, 11..63 ZERO      — the exponent mask and the `== 0x7FF` operand
K_FRAC   lanes 0..51 ONE, 52..63 ZERO      — FRAC_MASK
K_ABS    lanes 0..62 ONE, lane 63 ZERO     — ABS_MASK
```

`SIGN_MASK` (`fcmp.jl:9`) gets **no span**: it is assigned and never read in the body
(verified by scanning `fcmp.jl:8-47`). A port that allocates it has added a wire upstream
does not have; a port that *uses* it has invented a construction.

The four shift views, zero gates and zero qubits each:

```
sa   = { a[63] } ++ K_ZERO[0..62]      /* a >> 63,  fcmp.jl:12 */
sb   = { b[63] } ++ K_ZERO[0..62]      /* b >> 63,  fcmp.jl:13 */
a_hi = a[52..63] ++ K_ZERO[0..51]      /* a >> 52,  fcmp.jl:14, :60, :118 */
b_hi = b[52..63] ++ K_ZERO[0..51]      /* b >> 52,  fcmp.jl:15, :61, :119 */
```

### 2.2 Block vocabulary — what each row of §2.3 costs and what it emits

Six block types, each a port of one pinned function. **Every cost is a symbol to be ASKED
of the owning module at width 64; not one of them is written as a number anywhere in this
document or in the kernel** (K11's recorded finding: the one mutant L1 cannot see is the
one that looks like an optimisation, and `CQOPS_UPDATE_GOLDENS=1` blesses it).

| block | upstream | libcqops owner | step count symbol | scratch the CALLER must budget | op-kind schedule (from the pinned loop) |
|---|---|---|---|---|---|
| `and`(n) | `lower_and!`, `arith.jl:268-272` | M10 shape, emitted inline in the fp step function (PRD-v2 §7.10) | `C_and(n)` — one slot per lane | the `n`-bit output span | every slot `CCX` |

Two notes on this table, both source-verified. `lower_eq!` has a **separate `W == 1`
branch** (`arith.jl:431-435`) with no OR-prefix at all — irrelevant at `W = 64` but it is
what makes `S_eq(1)` degenerate, and K18 never instantiates `eq` at `n = 1`. And `ult`'s
schedule is the one `tests/test_kernel_divrem_schedule.inc` already encodes as
`sched_ult`; K18 reuses it verbatim rather than re-deriving it, which is the whole point of
composing a shipped block.

**`and`, `or` and `not1` are emitted directly by the fp step function, one gate per slot**,
exactly as M19 emits its two CNOTs — PRD-v2 §7.10: *"Bitwise ops are one gate per bit and
are emitted directly in the fp step function."* They are **not** calls to
`cq_kernel_and/or/xor`: those are whole Rule 7 kernels, and although `bitwise.h` records
that they are safe to call from inside a compute half with `dst = scratch`, calling one
would emit `n` gates in a single slot and break the driver's one-involution-per-step
contract. `eq`, `ult` and `mux` are reached through their **step functions** — never the
kernels, which are themselves sandwiches and `cq_sandwich` refuses nesting in both
configurations.

### 2.4 Scratch layout — flat, and every span named

Flat, as K12's is (PRD §15 D9). Every span below is allocated from one `cq_scratch` region
and pre-materialised at step 0 under I6(b), which emits **no gates**: scratch is born
`CQ_BIT_ZERO` and `cq_materialise` emits an `X` only for a constant `1`.

`B_olt`'s region, in allocation order:

| span | bits | role |
|---|---:|---|
| `ea`, `eb`, `fa`, `fb`, `abs_a`, `abs_b` | 6 × 64 | O4, O6, O7, O8, O9, O10 |
| 8 × `eq` block internals | 8 × `S_eq(64)` | O11, O13, O15, O17, O20, O22, O31, O33 — each `diff`(64) + `or`(63) |
| 3 × `ult` block internals | 3 × `S_ult(64)` | O25, O27, O29 — each `nb`(64) + `carry`(65) + `axnb`(64) |
| 2 × `mux` block internals | 2 × `S_mux(1)` | O35, O36 — each `r`(1) + `d`(1) |
| 11 × `not1` outputs | 11 | O12, O16, O21, O23, O26, O28, O30, O32, O34, O37, O39 |
| 5 × `and`(1) outputs | 5 | O14, O18, O24, O38, O40 |

`B_oeq`'s region: `6 × 64` + `7 × S_eq(64)` + `6` (not1) + `4` (and) + `2` (or).
`B_nan`'s region: `4 × 64` + `4 × S_eq(64)` + `2` + `2` + `1`.

A composite predicate's region is the concatenation of its bodies' regions plus its
combining bits — **no sharing**, per D-K18-1/§7.2. §4 does the arithmetic.

**`S_eq` and `S_ult` are budgeted by the CALLER, and `carry` is `n+1` bits, not `n`.**
`cmp.h` states it: *"a consumer's layout must budget `3W + 1` for the three vectors"*, and
an off-by-one there writes past the caller's sub-array, which `cq_scratch_span` cannot
catch because it hands out a bare pointer. At `W = 64` the `ult` carry chain is **65 bits**
— and the matching CLAUDE.md callout (`CQ_REG_WIDTH_MAX` is 128 and a `W+1` chain cannot be
a register at the top width) is *not* a hazard here, because K18 hands the block scratch
spans, never registers.

### 2.5 The copy-out

```
copyout:  CX( <pred>_flag  ->  dst[0] )          /* the "^=" of Rule 7's contract */
          X ( dst[0] )                           /* iff the fold of §2.5 is taken */
```

One CX and at most one X, into the single-bit `dst`. `dst` is **not** part of the scratch
region and is **not** pre-materialised; `cq_sandwich` disarms the I6 extent for the copy-out
precisely because `dst` lies outside scratch, and the tempting wrong fix — widening the
extent to cover `dst` — silently disables I6(a) for both compute halves.

**THE COPY-OUT FOLD IS AVAILABLE FOR EXACTLY TWO PREDICATES, AND THAT SET IS NEITHER OF
§1.1's. [DERIVED]** `ord` and `une` are the only predicates whose body *ends* in a
`lower_not1!` over a flag nothing else reads (`fcmp.jl:134`, `:102`). For those two the
trailing `not1` may be dropped from the compute half and spelled as the copy-out's `X`,
which is K9's shipped shape — `cq_kernel_ne` and `cq_kernel_uge` carry **0 X** and one CX
because the raw wire already is the answer (K09.md §5 delta 2). It saves one CX in the
compute half (doubled by Rule 2) and costs one X at the copy-out. `one`'s `not1` is **not**
trailing — it feeds the `&` at `:154` — so `one` cannot take the fold. **Recommended:
take it for `ord` and `une`, and record in the module header that the set is `{ord, une}`
and that it is a third set, distinct from both the swap set `{ogt, oge, ugt, uge}` and from
K9's inverting set.** Soundness: the X is emitted on both the forward and the uncompute
call, so `dst ^= !f` twice is `dst`, exactly as `dst ^= f` twice is.

### 2.6 I6(a) and I6(b)

**I6(a) — every gate target a kernel names is a bit of the scratch region.** Row by row:
every `and`/`or`/`not1` row targets its own freshly-allocated output span; every `eq`,
`ult` and `mux` block targets only its own internals (`diff`/`or`, `nb`/`carry`/`axnb`,
`r`/`d`), which cmp.h and mux.h both state as a contract — *"every gate below targets one
of them and nothing else, which is I6(a) discharged by construction rather than by
inspection."* The rails `a` and `b`, the four constant spans and the four shift views are
**only ever controls**: they reach the emitter through `cq_emit_*`'s `const cq_bit *`
parameters, so a source cannot be materialised by construction. Nothing in K18 writes a
view, which is also what makes D-K18-4's shared `K_ZERO` fill safe.

**I6(b) — every scratch bit is `CQ_BIT_Q` from step 0.** The driver pre-materialises the
whole region before any gate. Consequence for K18, and it is the one that differs from
every v1 kernel: pre-materialisation removes the *scratch* side's dependence on bit-kinds,
but **the constant spans and the views are not scratch** and keep their classical lanes at
every mask. That is D-K18-6, and §2.7 is how it is tested.

### 2.7 The slot scan — written BEFORE the kernel

PRD-v2 §7.1: *"What such a kernel can get wrong is the slot arithmetic, not the gates … The
instrument is K12's — a case that re-derives the op KIND of every compute-half slot from
the blocks' own structure and compares it against the recorded stream at the all-quantum
mask — and it is written **before** the kernel, with the composition check."* K18 has ~40
block boundaries per predicate against K12's four, so this matters more here, not less.

The form `tests/test_kernel_divrem_schedule.inc` already uses carries over with **one
structural change** (D-K18-6): the prediction per slot is a *kind or nothing*, because a
classical operand lane folds. The fold is statically determined by §2.1's lane table, so
nothing has to be measured to write it.

```
/* per-block kind schedules — straight loop counts off the pinned Julia, NOT counts */
sched_and (v)     = CCX                                     /* arith.jl:268-272        */
sched_or  (v)     = (v % 3 == 2) ? CCX : CX                 /* arith.jl:274-282        */
sched_not1(v)     = (v == 0)     ? CX  : X                  /* arith.jl:474-478        */
sched_eq  (n, v)  = v < 2n       ? CX
                                 : (((v - 2n) % 3 == 2) ? CCX : CX)   /* arith.jl:424-447 */
sched_ult (n, v)  = <verbatim tests/test_kernel_divrem_schedule.inc's sched_ult>
sched_mux (v)     = (v % 4 == 3) ? CCX : CX                 /* arith.jl:522-532        */

/* the boundaries — ASKED of the modules, never written as closed forms (D-K18-6) */
base(row r) = Σ over the rows before r in §2.3's table of steps(row)
steps(row)  = C_and(n) | C_or(n) | C_not1 | cq_eq_steps(n) | cq_ult_steps(n)
            | CQ_MUX_STEPS_PER_BIT * n

/* the fold, from §2.1's lane table alone */
predict(slot s):
    r    = the row containing s;  v = s - base(r)
    kind = sched_<r.block>(r.n, v)
    for each CONTROL lane c that gate reads:
        if c is a constant ZERO lane  ->  return NONE          /* the gate vanishes  */
        if c is a constant ONE  lane  ->  demote kind (CCX->CX, CX->X)
    return kind
```

Then: run at the all-quantum operand mask, walk the recorded stream and the slot range
together, skipping every slot whose prediction is `NONE`, and compare kinds. **The scan
records only which of X / CX / CCX (or nothing) each slot emits** — which is what a
boundary error moves and what a gate-list error does not — so it is not a second
transcription of anything. A red scan means a boundary; it does **not** mean the fold
prediction should be relaxed.

The companion is K11/K12's composition check, in **two** cases deliberately, so that a
sibling's cost moving reddens the first and NAMES the block: one case that runs **no
kernel** and pins `C_eq(64)`, `C_ult(64)`, `C_mux(64→1)` by asking M16 and M17; and one
that pins `cq_fcmp_steps(pred)` against the sum of what those just returned. Neither reads
a golden, so `CQOPS_UPDATE_GOLDENS=1` cannot bless a narrowing.

## 3. Gate-count formula

### 3.1 Symbolic form — substitute, do not re-derive

K18 is a **composition**. Every `C_*` below is obtained by asking the owning module at
width 64 — `cq_eq_steps(64)`, `cq_ult_steps(64)`, `CQ_MUX_STEPS_PER_BIT * 1`, and the
inline per-lane counts that follow from the pinned loops. **No number appears in this
section, and none may appear in the kernel.**

```
C_Bnan  = 4·C_and(64) + 4·C_eq(64)  + 2·C_not1  + 2·C_and(1) + 1·C_or(1)

C_Boeq  = 6·C_and(64) + 7·C_eq(64)  + 6·C_not1  + 4·C_and(1) + 2·C_or(1)

C_Bolt  = 6·C_and(64) + 8·C_eq(64)  + 3·C_ult(64)
                                    + 11·C_not1 + 5·C_and(1) + 1·C_or(1) + 2·C_mux(1)
```

and per predicate (slots in the compute half; `f = 1` if the §2.5 copy-out fold is taken
for that row, else 0):

```
n_compute(oeq) = C_Boeq
n_compute(olt) = C_Bolt
n_compute(ole) = C_Bolt + C_Boeq + C_or(1)
n_compute(uno) = C_Bnan
n_compute(ord) = C_Bnan + (1-f)·C_not1
n_compute(une) = C_Boeq + (1-f)·C_not1
n_compute(ueq) = C_Bnan + C_Boeq + C_or(1)
n_compute(ult) = C_Bnan + C_Bolt + C_or(1)
n_compute(ule) = C_Bnan + C_Bolt + C_Boeq + 2·C_or(1)
n_compute(one) = C_Bnan + C_Boeq + 2·C_not1 + C_and(1)

n_slots(pred)  = 2 · n_compute(pred) + 1 + f         /* Rule 2, + the copy-out */
n_compute(ogt) = n_compute(olt)    /* and likewise oge≡ole, ugt≡ult, uge≡ule: the */
                                   /* swap is an argument order, never a circuit   */
```

**`n_slots` IS NOT THE GATE COUNT** (D-K18-6). The emitted total at any mask is
`n_slots` minus the slots whose gate vanishes on a constant-`ZERO` control, with
constant-`ONE` controls demoting rather than removing. The L4 golden pins the **gate**
tuple at the all-quantum operand mask; the composition check pins the **slot** count; the
slot scan pins the shape. Three instruments, three units, and none of them substitutes for
another.

### 3.2 The copy-out

1 CX into `dst[0]`, plus 1 X for `ord` and `une` if §2.5's fold is taken. Not `W` CNOTs —
K9's shape, and the one place PRD §5's generic sandwich sketch has to be read with its own
2026-08-16 correction in hand.

### 3.3 There is NO upstream magnitude for `fcmp`, and the number people will reach for is a call count

**Measured 2026-09-18 by reading `third_party/bennett/BENCHMARKS.md`: the gate-count table
has rows for `soft_fadd`, `soft_fmul` and `soft_fma` and for no other softfloat routine.
There is no `soft_fcmp` row, at any width.** So unlike `fadd`, K18 has no published
upstream total that could be mistaken for a golden.

What *will* be mistaken for one is **6,799**. That figure is PRD-v2 §3.3's `fcmp` row as
corrected by §0a — the number of `fcmp` **template calls in the CQ_lang corpus**, measured

(§0a: *"it was a transcription error, not the corpus"*). It is a *liveness* figure. It is
not a gate count, not an ancilla count and not a golden, and it must never be written into

Risk **R14** stands for the two `BENCHMARKS.md` magnitudes K18 *can* see through its

## 5. Deltas from upstream

**The K-doc §5 convention:** these are differences between the pinned Julia and what M36
will emit. They are *not* a claim that ours is cheaper — CLAUDE.md records that the K-docs'
§5 comparison numbers were `fold_constants=false` figures while Bennett folds by default,
so **no comparison figure appears here at all**.

1. **Literal grain against LLVM's CSE.** Bennett compiles LLVM-optimised IR; we transcribe
   the Julia. `ea`, `eb`, `fa`, `fb` and the whole two-operand NaN test are computed in
   `B_olt`, in `B_oeq` and in `B_nan` independently, so `ule` carries **three** copies of
   the NaN test and **two** copies of `abs_a`/`abs_b`. PRD-v2 §7.2 decides this: D9's K12
   precedent refused exactly this class of narrowing because it is a re-derivation rather
   than a port, and K11's finding stands that the one mutant L1 cannot see is the one that
   looks like an optimisation.
2. **Constants are sources, not wires.** Upstream's `resolve!` freshly allocates 64 wires
   per constant (`arith.jl:202`); we pass `const cq_bit` spans and the §3 fold table elides
   every gate they control. §4's totals are therefore below what the same construction
   would cost upstream, by construction (PRD-v2 §7.3).
3. **Constant shifts are wiring.** `lower_lshr!` allocates a fresh `W`-wide vector and
   emits `W − k` CNOTs (`arith.jl:314-320`); K18's four shifts emit nothing and allocate
   nothing (D-K18-4). This is K12.md §2.1's precedent for the *view* and a deliberate
   departure from its D9(d) for the *fill*; the ground is in D-K18-4 and the alternative is
   one 64-bit scratch span per shift occurrence.
4. **The raw-wire convention (D-K18-5).** `!=` and `>=u` are read straight off the block's
   own wire; `==`, `<` and `>` add one `lower_not1!`. Upstream's `lower_icmp!` would route
   every one of them through a result wire and a second negation. K09.md §5 delta 2 and
   PRD §15 D9(b) are the precedent, and the ground is that two realisations of `eq` in one
   library — with the expensive one inside the kernel that calls it eight times — is the
   anomaly, not the saving.
5. **The copy-out fold for `{ord, une}` (§2.5).** Upstream has no copy-out; the concept
   only exists because Rule 2 localises the wrap.
6. **No narrowing towards the field width, anywhere.** `ea`/`eb` stay 64 bits although the
   exponent is 11; `sa`/`sb` stay 64 although only lane 0 can be set; `abs_a`/`abs_b` stay
   64 although lane 63 is provably zero; and O29's `sa > sb` is a full 64-bit `ult` block
   although a single Toffoli computes it. **All four are refused**, on PRD-v2 §7.2 and on
   K11's recorded finding. The `sa > sb` one is the K11-shaped mutant of this kernel: it
   leaves L1, L2, L3 and L5 green, and the only durable detector is §2.7's composition
   check, which asks M16 what `ult` costs at 64 instead of writing it down.
7. **`UInt64(1) - x` as `lower_not1!` (D-K18-2).** The refused alternative is a full
   `C_sub(64)` block at `fcmp.jl:102` and `:154`. Recorded so it is not re-proposed; the
   two agree in all 64 lanes and the source's own docstring names the operator.
8. **`SIGN_MASK` is dead and stays dead.** `fcmp.jl:9` assigns it inside `soft_fcmp_olt`
   and nothing in `:8-47` reads it (verified by scanning the range). No span, no wire, no
   use.
9. **`EXP_MASK` and `QUIET_BIT` are never referenced by `fcmp.jl`.** The exponent is
   extracted by shift-and-mask, and the quiet bit is **not** consulted — which is why an
   sNaN is a NaN to every one of the fourteen predicates, and why §5.x's sNaN anchor is the
   only instrument that would catch a port that "helpfully" tested it.
10. **The i1 result.** Upstream calls at width `w` and truncates (`instructions.jl:7739-7742`);
    our `dst` is one bit, so the source's `UInt64(result)` zext and the extractor's `trunc`
    collapse into wiring. K9's shape, K9's test adapter.

### 5.2 L1's anchor list for `fcmp` — PRD-v2 §7.12

§7.12: the budget stays `cq_kd_samples()` = 32 and the **anchors are forced into every
draw** rather than pooled, *"because each is a branch of the `ifelse` tree that a random

source's own special-case predicates. `fcmp.jl` names **eight** of them in `soft_fcmp_olt`
(`a_nan`, `b_nan`, `either_nan`, `both_zero`, `pos_lt`, `neg_lt`, `diff_sign_lt`,
`same_sign`), **four** in `soft_fcmp_oeq` (`a_nan`, `b_nan`, `either_nan`, `both_zero`) and
**two** in `_either_nan` (`a_nan`, `b_nan`), plus the unnamed `sa == 0` branch selector at
`:40`. Each needs an anchor that makes it **true** and one that makes it **false**.

| # | anchor pair `(a, b)` | what it forces | which named predicate it discriminates |
|---|---|---|---|
| A1 | `(+0.0, −0.0)` and `(−0.0, +0.0)` | `both_zero` TRUE | **the whole of `both_zero`.** `oeq` must be **1** (`:76` disjunct), `olt` must be **0** (`:44` override), `one` must be **0** (`:151` says so outright), `une` must be **0**. Without A1 both overrides can be deleted and nothing reddens |

| A13 | `(DBL_TRUE_MIN, +0.0)`, `(DBL_TRUE_MIN, DBL_MIN)` | subnormal, `both_zero` FALSE | that subnormals are ordinary magnitudes here. **Needs §7.4's host probe** — a host with DAZ set flushes the operand and the *oracle* returns the wrong answer, in the oracle rather than in the port |

**The oracle is the host C operator, and for `fcmp` it is genuinely host-independent.**
PRD-v2 §7.4's hazard — the IEEE-*unspecified* NaN cells, which are x86's choice and differ
on ARM — **does not reach K18**: IEEE 754 specifies the *result* of every comparison
including every NaN case, so `<`, `<=`, `>`, `>=`, `==`, `!=` and `isnan` give the same
answers on every conforming host. That is a real difference from `fadd` and it should be
recorded in the module header so nobody imports `fadd`'s pinned-by-table machinery here.
Three riders. (i) The oracle must **not** share the port's decomposition (Step 18's trap):
the port computes `ult` as `uno | olt`, so the reference must spell `ult` as `!(a >= b)`
and `ord` as `!isnan(a) && !isnan(b)` — the LLVM definitions — rather than rebuilding
`uno | olt`. (ii) `==` and `<` are the *signalling* predicates for an sNaN operand: they
raise the invalid flag, and the returned value is still specified, so A11 is safe as long
as nothing enables trapping. (iii) A13 needs §7.4's host probe (round-to-nearest, FTZ/DAZ
off) for the reason given in its row.

### 5.3 The classical short-circuit

Risk R9's short-circuit applies: an all-classical operand pair never enters `cq_sandwich`
and `dst[0]` is written as a constant. **The C computation is a transcription of the same
Julia body over `uint64_t`, not the host `<` or `==`** — PRD-v2 §7.4, *"the library's only
contact with a C `double` is the `memcpy` at `cqrt_alloc_f64`/`cqrt_measure_f64`."*

For `fcmp` specifically the transcription is short (the bodies are bit-twiddling already,
so it is a near-verbatim C rewrite of §1's excerpt) and the *motivating* hazard is weaker
than for `fadd`, since §5.2 has just established that comparisons have no IEEE-unspecified
cells. **The rule still holds and must not be relaxed here**, for two reasons that survive:
the short-circuit and the circuit must agree bit-for-bit *by construction* rather than by a
shared belief about IEEE, and a `double` comparison in `src/` is exactly the kind of thing
that acquires `-ffast-math` or x87 excess precision on a host nobody tested. L1 checks the
transcription against the circuit on every mixed-mask case, and against the independent
host oracle on every case.

Under a **quantum** control, L5's "zero gates, zero qubits" becomes false and that is the
correct answer, not a regression: the short-circuit still writes `dst[0]` through
`cq_emit_x`, whose constant row cannot fire inside a promoted region, so the one `dst` lane
becomes a wire driven by a real `CX`. K18 has exactly **one** `dst` lane, so the claim to
assert at `CQ_KD_CTRL_Q0` is `live` grew by exactly 1.
