**Clean or sandwich:** **sandwich.** Every inner block is dirty by design — `lower_eq!`
leaves `diff` and the OR-prefix, `lower_ult!` leaves `nb`, the whole carry chain and
`axnb`, `lower_mux!` leaves `diff` — and on top of that the port's own 64-bit intermediates
(`ea`, `fa`, `abs_a`, …) are never uncomputed by the source, because Julia has no notion of
uncomputing them. Bennett-in-the-small applies (Rule 2, PRD §5): compute the flag into
scratch, XOR it into `dst`, replay the compute half in reverse, release scratch. Cost is
2× the compute half and **that is not negotiable down** — every "narrow this field to 11
bits" saving is refused in §5.

**Result shape — K9's, exactly.** `fcmp` produces **one bit**. Upstream calls the
`soft_fcmp_*` callee at width `w` and immediately truncates:
`IRCall(call_dest, callee, [op1, op2], [w, w], w)` then
`IRCast(dest, :trunc, ssa(call_dest), w, 1)` (`instructions.jl:7739-7742`), under the
comment *"soft_fcmp returns UInt64 (0 or 1), but fcmp result is i1"*
(`instructions.jl:7736-7737`). So the signature is PRD-v2 §7.11's *"K9's shape (`dst` one
bit, `W` the operand width, the adapter passing `sh->w[0]`)"*:

```c
void cq_kernel_fcmp_olt(cq_ctx*, cq_bit *dst, const cq_bit *a, const cq_bit *b, int W);
/* … one entry point per predicate; W == 64 is the only shipped width (PRD-v2 §1). */
```

`a` and `b` are `W` bits; **`dst` is exactly one `cq_bit`**; the copy-out is **1 CX (+ at
most 1 X)**, never `W` CNOTs. The kernel asserts its own extent with
`cq_kernel_check_n(dst, 1, src, w, 2)`, as `cmp.c` does — `cq_kernel_check_dst`'s arity-2
wrapper would compare `dst`'s one bit against `W` and is wrong here. The test spec needs
K9's adapter: `cq_kd_case`'s default call path is defined only for the arity-2, one-width
shape and `shape_of` **refuses** anything else, so a spec with `w_dst = 1` and no `call`
adapter is a hard error rather than a suite that silently runs every case at `W = 1`.

## 1. Julia source excerpt

`fcmp.jl`, verbatim at `980805de`. Docstrings retained where they carry a semantic claim
the port depends on (the `+0 == −0` rule, the `une ≡ !oeq` identity, the first-operand NaN
convention).

```julia
# fcmp.jl:8-47 — soft_fcmp_olt
function soft_fcmp_olt(a::UInt64, b::UInt64)::UInt64
    SIGN_MASK = UInt64(0x8000000000000000)
    ABS_MASK  = UInt64(0x7FFFFFFFFFFFFFFF)

    sa = a >> 63
    sb = b >> 63
    ea = (a >> 52) & UInt64(0x7FF)
    eb = (b >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK
    fb = b & FRAC_MASK
    abs_a = a & ABS_MASK
    abs_b = b & ABS_MASK

    # NaN check: exponent all-ones with non-zero fraction
    a_nan = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    b_nan = (eb == UInt64(0x7FF)) & (fb != UInt64(0))
    either_nan = a_nan | b_nan

    # Both zero (±0 == ±0)
    both_zero = (abs_a == UInt64(0)) & (abs_b == UInt64(0))

    # Same sign comparison
    # For positive: a < b iff abs_a < abs_b
    # For negative: a < b iff abs_a > abs_b
    pos_lt = abs_a < abs_b      # |a| < |b|
    neg_lt = abs_a > abs_b      # |a| > |b| (more negative)

    # Different sign: negative < positive (unless both zero)
    diff_sign_lt = (sa > sb)    # a is negative, b is positive

    same_sign = sa == sb
    result = ifelse(same_sign,
                    ifelse(sa == UInt64(0), pos_lt, neg_lt),
                    diff_sign_lt)

    # Override: NaN → false, both zero → false
    result = result & (!both_zero) & (!either_nan)

    return UInt64(result)
end
```

```julia
# fcmp.jl:50-82 — soft_fcmp_oeq
#   "IEEE 754 ordered equal comparison on raw bit patterns.
#    Returns 1 if a == b (and neither is NaN), 0 otherwise.
#    Note: +0.0 == -0.0 per IEEE 754.  Fully branchless."
function soft_fcmp_oeq(a::UInt64, b::UInt64)::UInt64
    ABS_MASK  = UInt64(0x7FFFFFFFFFFFFFFF)

    ea = (a >> 52) & UInt64(0x7FF)
    eb = (b >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK
    fb = b & FRAC_MASK
    abs_a = a & ABS_MASK
    abs_b = b & ABS_MASK

    # NaN check
    a_nan = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    b_nan = (eb == UInt64(0x7FF)) & (fb != UInt64(0))
    either_nan = a_nan | b_nan

    # +0.0 == -0.0: both absolute values zero
    both_zero = (abs_a == UInt64(0)) & (abs_b == UInt64(0))

    # Bitwise equal or both zero
    result = (a == b) | both_zero

    # NaN != anything
    result = result & (!either_nan)

    return UInt64(result)
end
```

```julia
# fcmp.jl:111-125 — _either_nan
#   "Branchless test: at least one of `a`, `b` is a (quiet or signalling) NaN
#    in IEEE 754 binary64. NaN encoding: exponent = `0x7FF` AND fraction != 0."
@inline function _either_nan(a::UInt64, b::UInt64)::Bool
    ea = (a >> 52) & UInt64(0x7FF)
    eb = (b >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK
    fb = b & FRAC_MASK
    a_nan = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    b_nan = (eb == UInt64(0x7FF)) & (fb != UInt64(0))
    return a_nan | b_nan
end
```

```julia
# fcmp.jl:89-91, :101-103, :133-135, :143-145, :153-155, :163-165, :173-175, :183-185
@inline function soft_fcmp_ole(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_olt(a, b) | soft_fcmp_oeq(a, b)
end

#   "`une` ≡ `uno | one` ≡ `!oeq` (the latter holds because both unordered
#    operands AND ordered-not-equal operands have `oeq == 0`)."
@inline function soft_fcmp_une(a::UInt64, b::UInt64)::UInt64
    return UInt64(1) - soft_fcmp_oeq(a, b)
end

function soft_fcmp_ord(a::UInt64, b::UInt64)::UInt64
    return UInt64(!_either_nan(a, b))
end

function soft_fcmp_uno(a::UInt64, b::UInt64)::UInt64
    return UInt64(_either_nan(a, b))
end

#   "IEEE 754 ordered not-equal: both operands are non-NaN AND `a != b`.
#    Note `+0.0 == -0.0` per IEEE 754, so `one(+0, -0)` returns 0."
@inline function soft_fcmp_one(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_ord(a, b) & (UInt64(1) - soft_fcmp_oeq(a, b))
end

@inline function soft_fcmp_ueq(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_uno(a, b) | soft_fcmp_oeq(a, b)
end

@inline function soft_fcmp_ult(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_uno(a, b) | soft_fcmp_olt(a, b)
end

@inline function soft_fcmp_ule(a::UInt64, b::UInt64)::UInt64
    return soft_fcmp_uno(a, b) | soft_fcmp_ole(a, b)
end
```

**FOUR SWAP AND ZERO INVERT, AND THAT IS THE HEADLINE DIFFERENCE FROM K9.** K9's
`lower_icmp!` dispatch has *both* axes — four swaps (`ugt`, `ule`, `sgt`, `sle`) and five
`lower_not1!` inversions (`ne`, `ule`, `uge`, `sle`, `sge`; CLAUDE.md's callout states the
inverting set as `eq`, `ult`, `ugt`, `slt`, `sgt` because it is talking about the polarity
of the *raw scratch wire*, which is the complementary reading of the same fact). The fp
dispatch has **no `not1` arm at all**: every one of the fourteen rows is a bare callee, four
of them with the arguments exchanged. The inversion has not vanished — it has moved
**inside** the exported bodies (`une` is `1 − oeq` at `fcmp.jl:102`, `ord` is
`!_either_nan` at `:134`, and `one` contains the same `1 − oeq` at `:154`) — but it is no
longer a property of the dispatch table, and an implementer who copies K9's two-axis
dispatch across will write a table that is wrong in eight rows.

**THREE NEAR-MISSES, EACH OF WHICH LOOKS RIGHT.**

1. **`ugt` is a swap in BOTH tables and `ule` is a swap in K9 and NOT in fp.** K9 swaps
   `{ugt, ule, sgt, sle}`; fp swaps `{ogt, oge, ugt, uge}`. The intersection is `{ugt}`
   alone. Carrying K9's set over gives `ule` a spurious swap — and `ule` is symmetric
   enough in its NaN behaviour that the error survives every ordered pair where the
   operands compare equal, which is exactly the kind of case a 32-sample draw is full of.
2. **The two sets are DISJOINT here, where K9's overlap.** K9's swap and invert sets share
   `ugt` and `sgt`. For fp the swap set is `{ogt, oge, ugt, uge}` and the body-level
   inverting set is `{ord, one, une}` — no element in common. "The two sets are not the
   same set" is true for both tables and for *different reasons*, so the sentence cannot be
   reused as a check.
3. **The swap is `ole`, not `olt`, for `oge`.** `oge ≡ ole(b, a)` and `ogt ≡ olt(b, a)`;
   the analogous unordered pair is `uge ≡ ule(b, a)` and `ugt ≡ ult(b, a)`. Pairing `oge`
   with `olt` (or `uge` with `ult`) is off by the equality case only — it differs on
   exactly the inputs where `a == b`, and is invisible to every structural check.

**THE NaN COLUMN IS THE SECOND THING TO GET RIGHT, AND IT IS A FAMILY PROPERTY.** Every
`o*` predicate is *(the ordered relation)* **AND NOT unordered**; every `u*` predicate is
*(the ordered relation)* **OR unordered**. In the source that shows up as two different
spellings, and both must be transcribed as they stand:

- `olt` and `oeq` carry the override **inside** the body — `result & (!both_zero) &
  (!either_nan)` (`fcmp.jl:44`) and `result & (!either_nan)` (`:79`). `ole` inherits it
  from both of its disjuncts and adds nothing.
- `ord` / `uno` are the override alone (`:134`, `:144`).
- `ult` / `ule` / `ueq` add it as a **disjunct** (`uno | …`, `:174`, `:184`, `:164`).
- `one` is the only row that uses `ord` as a **conjunct** (`:154`).
- `une` gets it for free: `1 − oeq` is 1 whenever `oeq` is 0, which includes every
  unordered pair (the docstring at `:98-99` states exactly this and it is worth reading
  before "simplifying" `une` into `one | uno`).

**AND THE `both_zero` OVERRIDE IS `olt`-ONLY.** `soft_fcmp_olt` kills its result when
`|a| == |b| == 0` (`fcmp.jl:44`); `soft_fcmp_oeq` does the opposite and *adds* `both_zero`
as a disjunct (`:76`). That asymmetry is IEEE `+0 == −0` and it is the single most
load-bearing line in the file: drop `both_zero` from `olt` and `olt(−0.0, +0.0)` returns
**true**, because `sa > sb` holds. Drop it from `oeq` and `oeq(+0.0, −0.0)` returns
**false**. Neither error moves a gate count.

**WHERE K9'S TABLE DOES CARRY OVER, AND IT IS ONE ROW.** The operand swap costs nothing —
it is an argument-order change at the entry point, not a circuit — exactly as in K9.
Nothing else transfers.

## 2. Gate sequence as indexed pseudo-code

### 2.0 Eight decisions the transcription rests on

All eight follow PRD-v2 §7. The draft listed six; **D-K18-7 and D-K18-8 were added at
implementation** and are marked as such. Three of the first six were places where §7's
general rule needed a reading and were marked **[DERIVED]**; §6.2 says what happened to each.
None may be settled silently in code (CLAUDE.md, *Open blockers*).

**D-K18-1 — the grain is LITERAL, and "64-bit span" means *the Julia type's width*.**
PRD-v2 §7.2 fixes *"one block per operator occurrence as the source spells it; every
intermediate a 64-bit span (the Julia type's width); no common-subexpression sharing; no
narrowing towards the field width."* For `fadd` those two clauses agree because every
intermediate there is a `UInt64`. **`fcmp.jl` is the file where they come apart**: `a_nan`,
`b_nan`, `either_nan`, `both_zero`, `pos_lt`, `neg_lt`, `diff_sign_lt`, `same_sign` and
`result` are all `Bool`. The parenthetical is the rule, so a `Bool` intermediate is **one
bit** and a `UInt64` intermediate is **64 bits**. **[DERIVED]** — and the alternative
(padding every `Bool` to 64) is refused twice over: it multiplies the scratch by ~60 for no
value, and it makes the two `ifelse` rows a 64-bit mux whose `cond` is one bit and whose
arms are 63 lanes of nothing, which is not what `lower_mux!` does. What the rule *does*
forbid, and what stays forbidden, is narrowing `ea` to 11 bits or `sa` to 1 bit because the
value happens to fit (§5 delta 6).

**D-K18-2 — `UInt64(1) - x` on a `soft_fcmp_*` result is `lower_not1!`, not a 64-bit
subtractor. [DERIVED]** The occurrence is at `fcmp.jl:102` (`une`) and `:154` (`one`).
Read as a general `-`, it is M14's `sub` block at `W = 64`; read as what the file's own
docstring calls it — *"`une` ≡ … ≡ `!oeq`"* (`fcmp.jl:98`) — it is a logical NOT on a 0/1
value. The two agree in **all sixty-four lanes** (`1−0 = 1`, `1−1 = 0`, every higher lane
zero either way), so this is not a correctness fork; it is a cost fork of one `C_sub(64)`
per site, and the source states the identity itself. **Draft decision: `lower_not1!` — OVERRULED 2026-09-18 by the maintainer (PRD-v2 §7.2, amended the same day): the occurrence is transcribed as M14's `sub` block with the constant `1` as a source, one block per operator occurrence. §5 delta 7 now records `lower_not1!` as the refused alternative.**

**D-K18-3 — constants are `const cq_bit` SOURCES and the fold table elides the gates they
control.** PRD-v2 §7.3, verbatim, and its cited ground is `arith.jl:202` — *"Constants are
always safe (their wires are freshly allocated by resolve!)"* — which is what upstream does
and what we deliberately do not. **As shipped K18 needs exactly TWO constant spans** — an
all-zero one (every `== 0` operand) and `UInt64(1)` (the subtrahend of `fcmp.jl:102`) — plus
the two views `a & ABS_MASK` and `a >> 63`; `0x7FF` and `FRAC_MASK` moved inside M31's class
block with D-K18-8 and the draft's `and`(64) rows disappeared with the §7.3 amendment.
§7.3's consequence is
explicit: *"Our peak is therefore BELOW upstream's ancilla figure for the same
construction, and the difference is not a bug to chase in either direction."*

**D-K18-4 — a constant shift is WIRING, and its vacated lanes are literal `CQ_BIT_ZERO`
entries of a read-only view. [DERIVED]** Upstream's `lower_lshr!` (`arith.jl:314-320`)
allocates a fresh `W`-wide vector and emits `W − k` CNOTs into it. K12 already declines
that for its shifted remainder — *"a view, not a register … the left shift is therefore a
relabelling of `cq_bit` array entries and costs zero gates and zero qubits"* (K12.md §2.1)
— and K18 takes the same view. **THE §7.3 AMENDMENT SETTLED THE FILL BEFORE THE KERNEL WAS
WRITTEN**, so the draft's choice between literal `CQ_BIT_ZERO` and K12's D9(d)
pre-materialised `r0_hi` never had to be made here: a view keeps the lanes the mask leaves
at ONE and `CQ_BIT_ZERO` elsewhere, and M31's `cq_fp_view_*` are the implementation.
D9(d)'s ground — that literal zeros would make iteration `t = 0` cost less than every other
iteration and force a branch in the slot decode — does not carry here anyway, **because K18
has no loop**: every row has a *statically known* operand lane map, so §2.7's scan predicts
every elision at compile time. Taking D9(d)'s answer instead would have cost 64 qubits per
shift occurrence to buy uniformity K18 already has for free. Two riders that make it safe: a view is only ever a *source* (I6 — sources appear
only as controls), and a `CCX` whose two controls are both constant `ZERO` is a **legal
fold**, not a distinctness violation (`cq_bit_coincident` has no pointer-identity clause,
and PRD §3 says the check *"cannot fire on two constants"*), so one shared all-zero
constant span may serve every fill and every `== 0` operand.

**D-K18-5 — the inner blocks' RAW wires are read directly, and the polarity is fixed per
occurrence.** M16's `cq_ult_block` publishes *"`carry[W]` IS `a >=u b`"* (`src/kernels/cmp.h`)
and `cq_kernel_uge` copies it out unchanged — Bennett's `lower_not1!(lower_ult!(…))` double
negation folded into the copy-out, K09.md §5 delta 2, ratified as PRD §15 D9(b) when K12
made the same choice. K18 follows: an `eq` block's raw wire is `a != b`, an `ult` block's
raw wire is `a >=u b`. Therefore

| source occurrence | what the raw wire gives | extra |
|---|---|---|
| `x != y` (`fcmp.jl:22`, `:23`, `:68`, `:69`, `:122`, `:123`) | exactly the value | **none** |
| `x == y` (`:22`, `:23`, `:27`, `:38`, `:40`, `:68`, `:69`, `:73`, `:76`, `:122`, `:123`) | the complement | one `lower_not1!` |
| `x < y` (`:32`) | the complement | one `lower_not1!` |
| `x > y` (`:33`, `:36`) | the complement, on swapped operands | one `lower_not1!` |

The alternative — transcribing `lower_icmp!`'s own `r`-wire tail and then `lower_not1!` on
top — puts **two different realisations of `eq` in one library**, with the more expensive
one inside the kernel that calls it eight times. K12.md §3.0's second trap records exactly
that mistake being made and corrected.

**D-K18-6 — the composition identity is over SLOTS, not gates. [DERIVED, and MEASURED at
implementation: `ule` is 7,253 slots and 10,907 gates where one-gate-per-slot would be
14,507].** K12's identity `compute = W·(2 + C_ult + C_sub + C_mux)` is a *gate* identity
because at the all-quantum mask no fold can fire inside it — every operand of every K12
block is a pre-materialised scratch bit. **M31 was the first module where that is false and
K18 is the first KERNEL**: D-K18-3 and D-K18-4 put
classical lanes *inside* block operands (a constant mask, a shift's zero fill), and those
lanes fold at **every** operand mask including the all-quantum one L4 pins. So a compute
slot may legitimately emit **nothing**, or emit a `CX` where the schedule says `CCX`. The
durable identity is therefore over slot counts:

> `n_compute(pred) = Σ over §2.3's table of each block's own step count, asked of its
> module at width 64` — never written down as a closed form, and never compared against a
> gate total.

The gate total is the golden's business, and §2.7's slot scan is what pins the *shape*.
**Do not "fix" a red slot scan by asserting one-gate-per-slot**; that assertion is K12's
and it does not hold here.

**D-K18-7 — the ORDERED CORE splits again, at ROW TABLES ↔ STEP MACHINE. [ADDED AT
IMPLEMENTATION]** PRD-v2 §5 records one seam for M36 (ORDERED CORE ↔ PREDICATE TABLE) and
that seam was taken: `fcmp_pred.c` holds the ten compositions, the fourteen-row dispatch,
the entry points and the classical row. **Measured, the other half still came to 298 of
Rule 12's 300 non-blank non-comment lines**, so a second split was taken the same day —
`fcmp.c` keeps the three row tables of §2.3 and nothing else; `fcmp_step.c` turns a row into
spans and gates. The seam is real rather than arithmetic: every cost in `fcmp_step.c` is
ASKED of another module and not one line of it would move if a body table changed. It is
named here because PRD-v2 §5 did **not** record it in advance, which is the one thing
Rule 12 asks a split not to be.

**D-K18-8 — the NaN test is COMPOSED from M31, not transcribed a second time. [ADDED AT
IMPLEMENTATION]** `(ea == UInt64(0x7FF)) & (fa != UInt64(0))` occurs six times in `fcmp.jl`
(`:22`, `:23`, `:68`, `:69`, `:122`, `:123`) and is byte-identical to `fadd.jl:29`, which
`src/kernels/fpclass.c` already ports as `CQ_FP_IS_NAN`. M31's own header asks for exactly
this — *"M36 `fcmp` and M33 `fadd` … reach this construction through `cq_fp_class_step` and
nothing else"* — and it is Rule 1 applied to the call graph, the same answer M12-over-M17
gives. **It is NOT common-subexpression sharing**: each of the six occurrences gets its own
block at its own offset, and §7.2's prohibition is on sharing an occurrence, not on reusing
a construction. What it buys is that `ea`, `eb`, `fa` and `fb` need no spans at all and that
the one place `(ea == 0x7FF)`'s polarity is decided is M31's table. What it costs is one
indirection in the slot scan, which has to know the class block's internal schedule.

### 2.1 Vocabulary — AS SHIPPED

`W = 64` throughout and **any other width is a hard error in both configurations**
(PRD-v2 §1: `f64` only, and every `soft_fcmp_*` is `(UInt64, UInt64)`). Lane `i` is bit `i`
of the IEEE pattern, lane 63 the sign. Three kinds of thing appear as a block operand:

| kind | owns qubits? | example |
|---|---|---|
| **rail** — the caller's `a` / `b` | yes, and they are `CQ_BIT_Q` at the L4 mask | `CQ_FC_A`, `CQ_FC_B` |
| **scratch span** — pre-materialised by `cq_sandwich` at step 0 under I6(b), so `CQ_BIT_Q` for the whole compute half | yes | every block's internals, every 1-bit flag, the sub's `d` |
| **constant span / view** — M31's, `const cq_bit` only | **no** | `CQ_FC_ABS_A`, `CQ_FC_SIGN_A`, `CQ_FC_K_ZERO`, `CQ_FC_K_ONE` |

**THE EIGHT OPERAND CODES ARE THE WHOLE VOCABULARY, and six of them cost nothing.**
`src/kernels/fcmp.h` names them; `op64` in `fcmp_step.c` is the one place they are
resolved.

```
CQ_FC_A      the rail a                          CQ_FC_B      the rail b
CQ_FC_ABS_A  a & ABS_MASK  — cq_fp_view(a, 0, 63, buf), lane 63 CQ_BIT_ZERO
CQ_FC_ABS_B  b & ABS_MASK
CQ_FC_SIGN_A a >> 63       — cq_fp_view_sign(a, buf), lanes 1..63 CQ_BIT_ZERO
CQ_FC_SIGN_B b >> 63
CQ_FC_K_ZERO UInt64(0)     — cq_fp_const_zero(buf)
CQ_FC_K_ONE  UInt64(1)     — cq_fp_const(buf, 1); the subtrahend of fcmp.jl:102
```

A ninth kind of operand exists and is not a code: a **row reference**, `>= 0`, naming an
earlier row of the same program. Where a 1-bit operator reads it, it is that row's wire;
where a 64-lane block reads it (only the `sub` of `1 − oeq`), `op64` zero-extends it to
the Julia type's width through `cq_fp_view(flag, 0, 1, buf)` — again zero gates.

**`ea`, `eb`, `fa` and `fb` HAVE NO SPANS AT ALL IN THE SHIPPED MODULE**, and that is the
composition of D-K18-8 rather than a narrowing: the only thing `fcmp.jl` ever does with
them is `(ea == 0x7FF) & (fa != 0)`, which IS M31's `CQ_FP_IS_NAN` row, and M31 builds its
own views inside the block. `SIGN_MASK` gets no span either — it is assigned at
`fcmp.jl:9` and never read in `:8-47` (verified by scanning the range), and `EXP_MASK` and
`QUIET_BIT` do not occur in the file at all.

### 2.4 Scratch layout — flat, and computed by one prefix walk

Flat, as K12's is (PRD §15 D9). **There is no layout table in the module**: `offsets()` in
`fcmp_step.c` walks the program once per step, summing `row_region` of every earlier row,
and that single walk is the ONE place `k->off` is added. Every span is therefore
`off`-relative by construction rather than by inspection.

Each row's own bits, in the order the owning module states them:

```
CLASS_NAN   cq_fp_class_region(IS_NAN)  = 256   (M31's contract)
EQ          diff(64) ++ orr(63)         = 127   (cmp.h: budget 2W - 1)
ULT         nb(64) ++ carry(65) ++ axnb(64) = 193  (cmp.h: budget 3W + 1)
SUB         nb(64) ++ d(64) ++ c(64)    = 192   (add.h)
MUX         r(1) ++ d(1)                = 2     (mux.h)
NOT1 / AND1 / OR1                       = 1     (one output bit each)
```

**`carry` IS `W+1` BITS, NOT `W`, AND `d` LIES BETWEEN `nb` AND `c`.** Both are stated as
contracts by their headers and both are off-by-one hazards `cq_scratch_span` cannot catch,
because it hands out a bare pointer. The flags are read through the owning module's
accessor wherever there is one — `cq_eq_flag` is `orr[W−2]` in general and `diff[0]` at
`W == 1`, so a consumer spelling the rule inline reads `orr[-1]` at the bottom of the
ladder.

**THE PEAK IS `ule`/`uge` AT 3,032 SCRATCH BITS PLUS `dst`'s ONE**, measured through the
pool by `dst_owns_one_qubit_and_the_scratch_comes_back`. Risk **R11** is live at that size:
3,033 qubits is three orders of magnitude past D20's measured shipped QEC configs
(`n_logical ∈ {1, 3, 4, 6, 7}`), so a `-DCQOPS_QEC_DIR=` build hits D2's pool ceiling
**during pre-materialisation**, from the pool, loudly. That is D25's already-settled
behaviour and **the shim must never grow its own "that will not fit" check**.

### 2.5 The copy-out, and why the fold is REFUSED

```
copyout:  CX( <pred>_flag  ->  dst[0] )          /* the "^=" of Rule 7's contract */
```

**ONE CX AND NO X, for every one of the fourteen.** `dst` is not part of the scratch region
and is not pre-materialised; `cq_sandwich` disarms the I6 extent for the copy-out precisely
because `dst` lies outside scratch, and the tempting wrong fix — widening the extent to
cover `dst` — silently disables I6(a) for both compute halves.

**THE DRAFT'S `{ord, une}` COPY-OUT FOLD IS REFUSED, AND THAT IS A DECISION.** The draft
proposed dropping the trailing `lower_not1!` of `ord` (`fcmp.jl:134`) and the trailing
`1 − x` of `une` (`:102`) and spelling them as an X at the copy-out, as `cq_kernel_ne`
does. It is refused on the maintainer's 2026-09-18 ruling for D-K18-2: the grain is *"one
block per OPERATOR occurrence, no reading of what the operator means"*, and the fold is
exactly such a reading. Three consequences, all of them simplifications: every predicate's
copy-out is one CX, the slot scan needs no per-predicate exception, and there is no third
set to keep straight beside the swap set and the body-level inverting set. §5 delta 5
records the fold as the refused alternative so it is not re-proposed.

### 2.6 I6(a) and I6(b)

**I6(a) — every gate target a kernel names is a bit of the scratch region.** Every target
is a bit of the caller's region: an inner block's own internals, a `lower_not1!` wire, an
`and`/`or` output, a mux's `r`. The rails, M31's views over them and the constant spans are
**only ever controls** — they reach the emitter through `cq_emit_*`'s `const cq_bit *`
parameters, so a source cannot be materialised by construction. Nothing in K18 writes a
view, which is what makes the shared `CQ_FC_K_ZERO` span safe in eight places at once.

**I6(b) — every scratch bit is `CQ_BIT_Q` from step 0.** The driver pre-materialises the
whole region before any gate. The consequence that differs from every v1 kernel is D-K18-6:
pre-materialisation removes the *scratch* side's dependence on bit-kinds, but **the
constant spans and the views are not scratch** and keep their classical lanes at every
mask.

### 2.7 The slot scan and the composition check — WRITTEN BEFORE THE KERNEL, AND SHIPPED

Both live in `tests/test_kernel_fcmp_slots.inc`, with the three LAYOUT instruments next
door in `tests/test_kernel_fcmp_spans.inc` — a split on a real seam, because M31 measured
that the schedule and the layout come apart. **None of the six reads a golden.**

The composition check is in **two cases deliberately**, so a sibling's cost moving reddens
the first and NAMES the block:
`the_blocks_cost_what_their_modules_say_they_cost` runs no kernel and pins §2.2's five slot
counts and four region contracts; `each_predicate_is_the_sum_of_its_blocks` pins
`cq_fcmp_steps`, `cq_fcmp_region` and the row count of all fourteen against a **second,
independent** count of each body's block multiset, with every `C_*` asked of its module.

The slot scan is K12's, with D-K18-6's one structural change: the prediction per slot is a
**kind or nothing**, four-valued `{NONE, X, CX, CCX}`, walked with a **separate stream
cursor**.

```
/* per-row kind schedules — straight loop reads off the pinned Julia, NOT counts */
sched_or1 (v)     = (v == 2) ? CCX : CX                     /* arith.jl:274-282 */
sched_not1(v)     = (v == 0) ? CX  : X                      /* arith.jl:474-478 */
sched_and1        = CCX                                     /* arith.jl:268-272 */
sched_mux (v)     = (v % 4 == 3) ? CCX : CX                 /* arith.jl:522-532 */
sched_eq  (v)     = v < 2W ? fold(CX, operand lane v/2) : (3-cycle CX,CX,CCX)
sched_ult (v)     = 2W complement, 1 seed, then a 4-cycle   /* arith.jl:449-463 */
sched_sub (v)     = 2W complement, 1 seed, then a 5-cycle   /* adder.jl:149-172 */
sched_class(v)    = eq(exp view, 0x7FF) ++ not1 ++ eq(frac view, 0) ++ and

fold(kind, controls):
    for each CONTROL lane c:
        if c is CQ_BIT_ZERO -> NONE        /* the gate vanishes  */
        if c is CQ_BIT_ONE  -> kind--      /* CCX->CX, CX->X     */
```

Then: run at the all-quantum operand mask, walk the program's rows and the recorded stream
together with independent cursors, skip every slot whose prediction is `NONE`, and compare
kinds. **The scan records only which of X / CX / CCX (or nothing) each slot emits** — which
is what a boundary error moves and what a gate-list error does not — so it is not a second
transcription of anything. A red scan means a boundary; it does **not** mean the fold
prediction should be relaxed.

Three more instruments ship beside it, each with its own reason:

- `the_programs_spans_are_pairwise_disjoint` — no qubit index is written by two different
  ROWS. Written because the identical M31 mutant (two blocks collapsed onto one offset)
  survived value, palindrome, pool, counts and the slot scan.
- `two_programs_in_one_region_do_not_collide` — **the sole detector for a program that
  ignores its own `off`.** Measured 2026-09-18: with `offsets()`'s `k->off` replaced by
  `0`, that one case is the ONLY red in the suite, because the kernel always passes
  `off = 0` and the mutation is behaviourally inert from everywhere else.
- `the_compute_half_is_a_palindrome_at_an_asymmetric_mask` — at `a` all `Q` / `b` all
  `CQ_BIT_ZERO` and the mirror, the stream reads `[head] [1 CX] [head reversed]`. An
  all-classical pair is **not** a palindrome case, it is an L5 case: the R9 short-circuit
  never enters `cq_sandwich`, so the stream does not exist.

## 3. Gate-count formula

### 3.1 Symbolic form — substitute, do not re-derive

K18 is a **composition**. Every `C_*` below is obtained by asking the owning module at
width 64, and **no number appears in this section or in the kernel**.

```
C_Bnan  = 2·C_class + C_or
C_Boeq  = 2·C_class + 3·C_eq + 4·C_not1 + 2·C_and + 2·C_or
C_Bolt  = 2·C_class + 4·C_eq + 3·C_ult + 2·C_mux + 9·C_not1 + 3·C_and + C_or

n_compute(oeq) = C_Boeq                     n_compute(uno) = C_Bnan
n_compute(olt) = C_Bolt                     n_compute(ord) = C_Bnan + C_not1
n_compute(ole) = C_Bolt + C_Boeq + C_or     n_compute(une) = C_Boeq + C_sub
n_compute(ueq) = C_Bnan + C_Boeq + C_or     n_compute(ult) = C_Bnan + C_Bolt + C_or
n_compute(ule) = C_Bnan + C_Bolt + C_Boeq + 2·C_or
n_compute(one) = C_Bnan + C_not1 + C_Boeq + C_sub + C_and

n_slots(pred)  = 2 · n_compute(pred) + 1          /* Rule 2, + the one-CX copy-out */
n_compute(ogt) = n_compute(olt)   /* and oge≡ole, ugt≡ult, uge≡ule: the swap is an */
                                  /* argument order, never a circuit               */
```

**`n_slots` IS NOT THE GATE COUNT** (D-K18-6), and the shipped module proves it: at the
all-quantum mask `ule` runs 7,253 compute slots and the whole sandwich emits 10,907 gates,
where `2·7253 + 1 = 14,507` would be the one-gate-per-slot figure. The 3,600-gate gap is
the fold table eliding gates whose control is a constant lane of a view or of a constant
span. The L4 golden pins the **gate** tuple; the composition check pins the **slot** count;
the slot scan pins the shape. Three instruments, three units, none substituting for
another.

## 5. Deltas from upstream

**The K-doc §5 convention:** these are differences between the pinned Julia and what M36
emits. They are *not* a claim that ours is cheaper — the K-docs' §5 comparison numbers were
`fold_constants=false` figures while Bennett folds by default, so **no comparison figure
appears here at all**.

1. **Literal grain against LLVM's CSE.** Bennett compiles LLVM-optimised IR; we transcribe
   the Julia. The two-operand NaN test is computed in `B_olt`, in `B_oeq` and in `B_nan`
   independently, so `ule` carries **three** copies of it and **two** of
   `abs_a`/`abs_b`. PRD-v2 §7.2 decides this: D9's K12 precedent refused exactly this class
   of narrowing because it is a re-derivation rather than a port.
2. **Constants are sources, not wires.** Upstream's `resolve!` freshly allocates 64 wires
   per constant (`arith.jl:202`); we pass `const cq_bit` spans and the §3 fold table elides
   every gate they control.
3. **Constant masks and shifts are WIRING, not blocks.** `lower_lshr!` allocates a fresh
   `W`-wide vector and emits `W − k` CNOTs (`arith.jl:314-320`) and `lower_and!` one
   Toffoli per lane (`:268-272`); K18's `& ABS_MASK`, `>> 63`, `>> 52` and `& 0x7FF`
   occurrences emit **nothing** and allocate **nothing** (PRD-v2 §7.3 as amended; M31's
   `cq_fp_view_*` are the implementation). This is what took `B_olt` from the draft's 41
   rows to 24 and its region from 2,000 bits to 1,616.
4. **The raw-wire convention (D-K18-5).** `!=` and `>=u` are read straight off the block's
   own wire; `==`, `<` and `>` add one `lower_not1!`. Upstream's `lower_icmp!` would route
   every one of them through a result wire and a second negation. K09.md §5 delta 2 and
   PRD §15 D9(b) are the precedent.
5. **NO copy-out fold, and the draft's `{ord, une}` is the refused alternative** (§2.5).
   Upstream has no copy-out at all; the concept only exists because Rule 2 localises the
   wrap.
6. **No narrowing towards the field width, anywhere.** `abs_a`/`abs_b` stay 63-lane views
   although the top lane is provably zero; `sa`/`sb` are full 64-lane operands of a full
   `ult` block although a single Toffoli computes `sa > sb`; the class block runs its two
   `eq` comparisons at 64 although the exponent is 11 bits and the fraction 52. **All are
   refused**, on PRD-v2 §7.2 and on K11's recorded finding, and the durable detector is the
   composition check — measured in §6.5, mutant M6.
7. **`UInt64(1) − x` is M14's `sub` block with the constant 1 as a source (D-K18-2, as
   OVERRULED).** The refused alternative is `lower_not1!`, which the draft recommended and
   which the file's own docstring (`fcmp.jl:98`) names. The two agree in all sixty-four
   lanes, so this was a cost fork and never a correctness one: it costs `C_sub(64) = 447`
   slots and 192 bits at each of the two sites (`:102` and `:154`). Recorded so it is not
   re-proposed.
8. **`SIGN_MASK` is dead and stays dead.** `fcmp.jl:9` assigns it inside `soft_fcmp_olt`
   and nothing in `:8-47` reads it. No span, no wire, no use.
9. **`EXP_MASK` and `QUIET_BIT` are never referenced by `fcmp.jl`.** The exponent is
   extracted by shift-and-mask and the quiet bit is **not** consulted — which is why an
   sNaN is a NaN to every one of the fourteen predicates, and why §5.2's sNaN anchor is the
   only instrument that would catch a port that "helpfully" tested it.
10. **The i1 result.** Upstream calls at width `w` and truncates
    (`instructions.jl:7739-7742`); our `dst` is one bit, so the source's `UInt64(result)`
    zext and the extractor's `trunc` collapse into wiring. K9's shape, K9's test adapter.
11. **The NaN test is COMPOSED from M31 rather than transcribed again (D-K18-8).**
    `(ea == 0x7FF) & (fa != 0)` at `fcmp.jl:22`, `:23`, `:68`, `:69`, `:122` and `:123` is
    byte-identical to `fadd.jl:29`, which `src/kernels/fpclass.c` already ports; K18 reaches
    it through `cq_fp_class_step`, which is Rule 1 applied to the call graph. It is **not**
    CSE: each of the six occurrences gets its own block at its own offset.

### 5.2 L1's anchors for `fcmp` — THE SHIPPED LIST

The provider is `fcmp_anchors` in `tests/test_kernel_fcmp_anchors.inc`. It **composes**

representatives inside the shared 32-case budget and replays them at three mask rows; adding
another semantic row does not increase circuit construction time.

|---|---|---|---|

| 3-4 | `(1.0, 2.0)`, `(2.0, 1.0)` | `same_sign` TRUE, `sa == 0` TRUE | `pos_lt` both ways — the inner mux's `t` arm |

Three more instruments carry §7.12's *"one unordered pair per predicate"*:
`the_unordered_row_is_the_literal_o_and_u_family_split` runs **six** unordered pairs
through all fourteen predicates in **three modes** — the host, the classical short-circuit
and the circuit at the all-quantum mask — against a literal `{0×7, 1×7}` table; and
`the_classical_row_agrees_with_the_host_on_every_anchor` checks every one of the 37 rows
without constructing a circuit. `the_full_anchor_table_stays_classical_and_the_circuit_set_is_constant`
pins the eight-row circuit provider so the exhaustive table cannot silently widen L1.

**THE ORACLE IS THE HOST C OPERATOR, AND FOR `fcmp` IT IS GENUINELY HOST-INDEPENDENT.**
PRD-v2 §7.4's hazard — the IEEE-*unspecified* NaN cells, which are x86's choice and differ
on ARM — **does not reach K18**: IEEE 754 specifies the *result* of every comparison
including every NaN case. That is a real difference from `fadd` and it is recorded in the
module header so nobody imports `fadd`'s pinned-by-table machinery here. Two riders. (i)
The oracle must **not** share the port's decomposition (Step 18's trap): the port computes
`ult` as `uno | olt`, so `host_fcmp` spells it `isunordered(x,y) || x < y` — LLVM's own
definition. (ii) A13's subnormal rows need §7.4's host probe (round-to-nearest, FTZ/DAZ
off), which the build already runs and which printed `fp host probe OK` for this work.

### 5.3 The classical short-circuit — AS SHIPPED

`sc_either_nan`, `sc_oeq`, `sc_olt` and `sc_core` in `src/kernels/fcmp_pred.c`: a C
transcription of the same four Julia bodies over `uint64_t`, with the dispatch's swap
applied by `cq_fcmp_eval` itself. **Never the host `<` / `==` / `isunordered`** (PRD-v2
§7.4). A `Bool` intermediate is an `int` and a `UInt64` one is a `uint64_t`, which is
D-K18-1's split applied to the classical row.

For `fcmp` the motivating hazard is weaker than for `fadd`, since §5.2 has just established
that comparisons have no IEEE-unspecified cells. **The rule still holds and was not relaxed**,
for two reasons that survive: the short-circuit and the circuit must agree bit-for-bit *by
construction* rather than by a shared belief about IEEE, and a `double` comparison in `src/`
is exactly the kind of thing that acquires `-ffast-math` or x87 excess precision on a host
nobody tested. `the_classical_row_agrees_with_the_host_on_every_anchor` checks it over all
37 anchors × 14 predicates and over a seeded 4,000-pattern sweep with the exponent forced
into the special range on half the draws — it runs no circuit, so it is cheap enough to be
broad, and it is the only case that would notice a transcription right on the specials and
wrong in the middle.

Under a **quantum** control L5's "zero gates, zero qubits" becomes false and that is the
correct answer: the short-circuit still writes `dst[0]` through `cq_emit_x`, whose constant
row cannot fire inside a promoted region, so the one `dst` lane becomes a wire driven by a
real `CX`. K18 has exactly **one** `dst` lane, and the driver's `CQ_KD_CTRL_Q0` row asserts
`live` grew by exactly that.

**M8 IS THE SECOND THING WORTH REMEMBERING, AND IT IS THE RECORDED SHAPE ONE COLUMN OVER.**
The guard it deletes was *added* while answering "which single case goes red if this line is

"none", because a 1-bit operator handed one of the eight negative codes indexes the row

carried by its regex, exactly as `bd remember

**M7 IS THE ONE WORTH REMEMBERING.** The kernel always passes `off = 0`, so a program that
ignored its own offset is behaviourally inert from every other case in the suite — the
value, the palindrome, the pool, the slot scan, the span scan and all fourteen goldens stay
green. Only a SECOND program at a SECOND offset in one region sees it. M31 carries the same
case for the same reason, and the death cases do **not** substitute: they drive
`check_region`, which is a different line.
