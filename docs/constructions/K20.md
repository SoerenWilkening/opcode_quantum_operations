### 1.1 `soft_fma` — `fma.jl:1-211`, verbatim

```julia
"""
    soft_fma(a::UInt64, b::UInt64, c::UInt64) -> UInt64

IEEE 754 double-precision fused multiply-add on raw bit patterns.
Single-rounded `round(a·b + c)`. Uses only integer operations.
Bit-exact with `Base.fma(::Float64, ::Float64, ::Float64)`.

Fully branchless: every path is computed unconditionally and results are
selected via `ifelse`. This ensures LLVM emits `select` instructions
(not `br`+`phi`), which is required for correct reversible circuit
compilation.

Algorithm: Berkeley SoftFloat 3 `s_mulAddF64.c` SOFTFLOAT_FAST_INT64 path,
ported branchless. 128-bit intermediate (two UInt64 limbs). The
`<<10` / `<<9` significand scaling is Hauser's — it places the normalized
product's leading 1 at bit 125 (of the 128-bit register), one bit below
the add-overflow detection boundary at bit 127.

Single rounding is the defining property of FMA: `round(a·b + c)` vs the
naïve `round(round(a·b) + c)`, which double-rounds and breaks bit-
exactness at round-half cases (Kahan single-rounding witness).

See `docs/design/soft_fma_consensus.md` for the full design, ground-truth
source citations (Berkeley SoftFloat 3 `s_mulAddF64.c`, musl `fma.c`,
IEEE 754-2019 §5.4.1), gate-count analysis, and novelty claim (first
IEEE 754 binary64 reversible FMA in the quantum/reversible literature).
"""
@inline function soft_fma(a::UInt64, b::UInt64, c::UInt64)::UInt64
    BIAS = Int64(1023)

    # ── Unpack ──────────────────────────────────────────────────────────
    sa = a >> 63
    ea = (a >> 52) & UInt64(0x7FF)
    fa = a & FRAC_MASK
    sb = b >> 63
    eb = (b >> 52) & UInt64(0x7FF)
    fb = b & FRAC_MASK
    sc = c >> 63
    ec = (c >> 52) & UInt64(0x7FF)
    fc = c & FRAC_MASK

    # ── Special-case predicates ─────────────────────────────────────────
    a_nan  = (ea == UInt64(0x7FF)) & (fa != UInt64(0))
    b_nan  = (eb == UInt64(0x7FF)) & (fb != UInt64(0))
    c_nan  = (ec == UInt64(0x7FF)) & (fc != UInt64(0))
    a_inf  = (ea == UInt64(0x7FF)) & (fa == UInt64(0))
    b_inf  = (eb == UInt64(0x7FF)) & (fb == UInt64(0))
    c_inf  = (ec == UInt64(0x7FF)) & (fc == UInt64(0))
    a_zero = (ea == UInt64(0)) & (fa == UInt64(0))
    b_zero = (eb == UInt64(0)) & (fb == UInt64(0))
    c_zero = (ec == UInt64(0)) & (fc == UInt64(0))

    sign_prod      = sa ⊻ sb
    any_nan        = a_nan | b_nan | c_nan
    prod_is_inf    = (a_inf | b_inf) & !(a_zero | b_zero)
    inf_times_zero = (a_inf & b_zero) | (b_inf & a_zero)
    inf_clash      = prod_is_inf & c_inf & (sign_prod != sc)
    prod_is_zero   = a_zero | b_zero

    # ── Mantissas with implicit 1, pre-normalize subnormals ─────────────
    ma     = ifelse(ea != UInt64(0), fa | IMPLICIT, fa)
    mb     = ifelse(eb != UInt64(0), fb | IMPLICIT, fb)
    mc     = ifelse(ec != UInt64(0), fc | IMPLICIT, fc)
    ea_eff = ifelse(ea != UInt64(0), Int64(ea), Int64(1))
    eb_eff = ifelse(eb != UInt64(0), Int64(eb), Int64(1))
    ec_eff = ifelse(ec != UInt64(0), Int64(ec), Int64(1))
    (ma, ea_eff) = _sf_normalize_to_bit52(ma, ea_eff)
    (mb, eb_eff) = _sf_normalize_to_bit52(mb, eb_eff)
    (mc, ec_eff) = _sf_normalize_to_bit52(mc, ec_eff)

    # ── Berkeley scaling: ma,mb << 10 (leading 1 at bit 62); mc << 9 ────
    ma_s = ma << 10
    mb_s = mb << 10
    mc_s = mc << 9

    # ── 128-bit product ─────────────────────────────────────────────────
    (p_hi, p_lo) = _sf_widemul_u64_to_128(ma_s, mb_s)
    # Leading 1 at bit 124 or 125 of the 128-bit product.
    expZ = ea_eff + eb_eff - Int64(0x3FE)

    # Berkeley line 122: if top of p_hi has bit 61 clear (= product < 2^125),
    # double so that leading 1 lands at bit 125 unconditionally.
    prod_lead_low = p_hi < UInt64(0x2000000000000000)   # 2^61
    (p_hi_d, p_lo_d) = _shl128_by1(p_hi, p_lo)
    p_hi = ifelse(prod_lead_low, p_hi_d, p_hi)
    p_lo = ifelse(prod_lead_low, p_lo_d, p_lo)
    expZ = ifelse(prod_lead_low, expZ - Int64(1), expZ)
    # Now product's leading 1 is at bit 61 of p_hi (= bit 125 of full reg).

    same_sign = sign_prod == sc
    expDiff   = expZ - ec_eff
    expDiff_neg = expDiff < Int64(0)

    # ── Alignment ───────────────────────────────────────────────────────
    # Product side: if expDiff < 0, shift product right-jam by -expDiff
    # (Berkeley special: if expDiff == -1 AND opposite-sign, use >>1 with
    # sticky to preserve 1 extra bit for cancellation renormalization —
    # line 144 precision-preservation trick).
    (p_rj_hi, p_rj_lo)     = _shiftRightJam128(p_hi, p_lo, -expDiff)
    (p_shr1_hi, p_shr1_lo) = _shr128jam_by1(p_hi, p_lo)
    use_short_shift = (expDiff == Int64(-1)) & !same_sign
    p_right_hi = ifelse(use_short_shift, p_shr1_hi, p_rj_hi)
    p_right_lo = ifelse(use_short_shift, p_shr1_lo, p_rj_lo)

    p_side_hi = ifelse(expDiff_neg, p_right_hi, p_hi)
    p_side_lo = ifelse(expDiff_neg, p_right_lo, p_lo)

    # C side: if expDiff > 0, shift (mc_s, 0) right-jam by expDiff.
    # For expDiff <= 0, c is unshifted at (mc_s, 0).
    (c_right_hi, c_right_lo) = _shiftRightJam128(mc_s, UInt64(0), expDiff)
    c_side_hi = ifelse(expDiff_neg, mc_s, c_right_hi)
    c_side_lo = ifelse(expDiff_neg, UInt64(0), c_right_lo)

    # Result exponent frame (c dominates if expDiff < 0, else product).
    expR = ifelse(expDiff_neg, ec_eff, expZ)

    # ── Add or subtract ─────────────────────────────────────────────────
    (sum_hi, sum_lo)  = _add128(p_side_hi, p_side_lo, c_side_hi, c_side_lo)
    (diff_hi, diff_lo) = _sub128(p_side_hi, p_side_lo, c_side_hi, c_side_lo)
    wr_hi = ifelse(same_sign, sum_hi, diff_hi)
    wr_lo = ifelse(same_sign, sum_lo, diff_lo)

    # Opposite-sign underflow (subtracted larger from smaller): negate
    # and flip the result sign.
    underflow = !same_sign & ((wr_hi >> 63) != UInt64(0))
    (neg_hi, neg_lo) = _neg128(wr_hi, wr_lo)
    wr_hi = ifelse(underflow, neg_hi, wr_hi)
    wr_lo = ifelse(underflow, neg_lo, wr_lo)

    # Result sign: if opposite-sign subtraction underflowed (we subtracted
    # larger from smaller, then negated), the result takes c's sign;
    # otherwise it takes the product's sign. For same-sign add, underflow
    # is always false, so result_sign = sign_prod = sc.
    result_sign = ifelse(underflow, sc, sign_prod)

    # ── Complete cancellation (opposite-sign, result exactly zero) ──────
    complete_cancel = !same_sign & (wr_hi == UInt64(0)) & (wr_lo == UInt64(0))

    # ── Renormalize ─────────────────────────────────────────────────────
    # Target: leading 1 at bit 61 of wr_hi_folded. This matches Berkeley's
    # post-normalize convention (product leading 1 at bit 125 of 128-bit
    # register = bit 61 of hi limb) so `expR` stays correctly biased.

    # Stage A: if wr_hi == 0, fold wr_lo up. Only possible after opposite-
    # sign subtraction with massive cancellation.
    hi_zero       = wr_hi == UInt64(0)
    wr_hi_folded  = ifelse(hi_zero, wr_lo, wr_hi)
    wr_lo_folded  = ifelse(hi_zero, UInt64(0), wr_lo)
    expR          = ifelse(hi_zero, expR - Int64(64), expR)

    # Stage B: if bit 63 of wr_hi_folded is set (possible post-fold when
    # wr_lo had its MSB set), shift right 1 with sticky, expR += 1.
    hi_bit63 = (wr_hi_folded >> 63) != UInt64(0)
    (wr_hi_s63, wr_lo_s63) = _shr128jam_by1(wr_hi_folded, wr_lo_folded)
    wr_hi_folded = ifelse(hi_bit63, wr_hi_s63, wr_hi_folded)
    wr_lo_folded = ifelse(hi_bit63, wr_lo_s63, wr_lo_folded)
    expR         = ifelse(hi_bit63, expR + Int64(1), expR)

    # Stage C: if bit 62 of wr_hi_folded is set (same-sign add carry from
    # bit 61 → bit 62, or post-B bit 63 → bit 62), shift right 1, expR += 1.
    hi_bit62 = (wr_hi_folded >> 62) != UInt64(0)
    (wr_hi_s62, wr_lo_s62) = _shr128jam_by1(wr_hi_folded, wr_lo_folded)
    wr_hi_folded = ifelse(hi_bit62, wr_hi_s62, wr_hi_folded)
    wr_lo_folded = ifelse(hi_bit62, wr_lo_s62, wr_lo_folded)
    expR         = ifelse(hi_bit62, expR + Int64(1), expR)

    # Stage D: 128-bit CLZ to bring leading 1 back to bit 61 of hi.
    # Bits from wr_lo_folded migrate up into wr_hi_folded at each shift
    # stage so no precision is lost. Substitute (1, 0) for the all-zero
    # case to keep the helper in its precondition domain; complete_cancel
    # in the select chain overrides any resulting garbage.
    both_zero = (wr_hi_folded == UInt64(0)) & (wr_lo_folded == UInt64(0))
    wr_hi_for_clz = ifelse(both_zero, UInt64(1), wr_hi_folded)
    wr_lo_for_clz = ifelse(both_zero, UInt64(0), wr_lo_folded)
    (wr_hi_norm, wr_lo_norm, expR) = _sf_clz128_to_hi_bit61(wr_hi_for_clz, wr_lo_for_clz, expR)

    # ── Collapse to 56-bit working format ───────────────────────────────
    # Leading 1 at bit 61 of wr_hi_norm → need leading 1 at bit 55.
    # Shift right 6; fold bits 0–5 of wr_hi_norm + all of wr_lo_norm
    # into sticky (bit 0 of the 56-bit payload).
    low6_nonzero = (wr_hi_norm & UInt64(0x3F)) != UInt64(0)
    lo_nonzero   = wr_lo_norm != UInt64(0)
    sticky = ifelse(low6_nonzero | lo_nonzero, UInt64(1), UInt64(0))
    wr_56  = ((wr_hi_norm >> 6) & ((UInt64(1) << 56) - UInt64(1))) | sticky

    # ── Subnormal handling + round + pack (existing helpers) ────────────
    (wr_56, expR, flushed, subnormal, flush_to_zero) =
        _sf_handle_subnormal(wr_56, expR, result_sign)
    (normal_result, overflow_result, exp_overflow, exp_overflow_after_round) =
        _sf_round_and_pack(wr_56, expR, result_sign)

    # ── Zero-product result: return c, with signed-zero combine when c==0.
    # Under round-to-nearest-even, fma(-0, +0, +0) = +0; fma(-0, +0, -0) = -0;
    # fma(+0, +0, +0) = +0; opposite-sign zero combine = +0.
    prod_zero_c_zero_result = ifelse(sign_prod == sc, c, UInt64(0))
    prod_zero_result        = ifelse(c_zero, prod_zero_c_zero_result, c)

    # ── Final priority select chain (last-write-wins; NaN strictly last) ─
    result = normal_result
    result = ifelse(exp_overflow | exp_overflow_after_round, overflow_result, result)
    result = ifelse(subnormal & flush_to_zero, flushed, result)
    result = ifelse(complete_cancel, UInt64(0), result)
    result = ifelse(prod_is_zero, prod_zero_result, result)
    result = ifelse(c_inf & !prod_is_inf, c, result)
    result = ifelse(prod_is_inf, (sign_prod << 63) | INF_BITS, result)
    result = ifelse(inf_clash, INDEF, result)                                        # Bennett-r84x
    result = ifelse(inf_times_zero, INDEF, result)                                   # Bennett-r84x
    result = ifelse(any_nan, _sf_propagate_nan3(a, b, c, a_nan, b_nan, c_nan),       # Bennett-r84x
                    result)
    return result
end
```

### 1.1a The three-operand NaN precedence, and every other named special case

**`_sf_propagate_nan3` — `softfloat_common.jl:26-35`, verbatim.** It is the only
three-operand helper in the file and the only reason `fma` cannot borrow `fadd`'s
NaN path:

```julia
"""
    _sf_propagate_nan3(a, b, c, a_nan, b_nan, c_nan) -> UInt64

Three-operand variant for FMA: a > b > c precedence, matching Intel VFMADD*'s
NaN-handling order. Caller must guard entry with `a_nan | b_nan | c_nan`.
"""
@inline _sf_propagate_nan3(a::UInt64, b::UInt64, c::UInt64, a_nan, b_nan, c_nan) =
    ifelse(a_nan, a | QUIET_BIT,
    ifelse(b_nan, b | QUIET_BIT,
                  c | QUIET_BIT))
```

**The rule is `a > b > c`, it is Intel's VFMADD order, and the docstring says so in
those words** (`softfloat_common.jl:29`). Three consequences, all structural:

1. **It is a two-level nested `ifelse` and therefore TWO `cq_mux_block`s, not one**
   (§2.2 rows O18–O22). A port that spells it `ifelse(a_nan, a|Q, ifelse(c_nan,
   c|Q, b|Q))` — the same three arms in a different nesting — is right whenever at
   most one operand is NaN and wrong on `b_nan & c_nan`. §5.x anchor group 1 has all
   seven non-empty subsets of `{a, b, c}` for exactly this.
2. **The quiet bit is OR-ed into all three arms, unconditionally**
   (`softfloat_common.jl:33-35`). That is IEEE 754-2019 §6.2.3's force-quieting of a
   signalling NaN, and it is why an sNaN anchor in each position is separate from a
   qNaN anchor in each position.
3. **It preserves the SIGN**, because `| QUIET_BIT` touches fraction bit 51 and
   nothing else. `fma` has no `soft_fneg` anywhere, so it cannot acquire
   `Bennett-m63k`'s sign-flip bug the way `fsub` could — but §5.x anchor 6 pins the
   sign anyway, because "it cannot happen" is not an instrument.

```julia
"""
    _sf_widemul_u64_to_128(a, b) -> (hi, lo)

Full 64×64 → 128-bit unsigned multiply. Returns `(hi, lo)` such that
`(hi << 64) | lo == a * b` mathematically. Uses four 32×32 partial
products; each fits in UInt64 without overflow.

General-purpose (vs. the 27×26 decomposition inlined in `soft_fmul`,
which assumes ≤53-bit inputs). Used by `soft_fma` with Berkeley-scaled
63-bit inputs (`ma << 10`, `mb << 10`).
"""
@inline function _sf_widemul_u64_to_128(a::UInt64, b::UInt64)
    a_lo = a & UInt64(0xFFFFFFFF)
    a_hi = a >> 32
    b_lo = b & UInt64(0xFFFFFFFF)
    b_hi = b >> 32

    pp_ll = a_lo * b_lo       # ≤ (2^32-1)^2 < 2^64
    pp_lh = a_lo * b_hi
    pp_hl = a_hi * b_lo
    pp_hh = a_hi * b_hi

    mid = pp_lh + pp_hl
    mid_carry = ifelse(mid < pp_lh, UInt64(1), UInt64(0))   # overflow bit

    mid_lo = mid << 32
    mid_hi = (mid >> 32) | (mid_carry << 32)

    lo = pp_ll + mid_lo
    lo_carry = ifelse(lo < pp_ll, UInt64(1), UInt64(0))

    hi = pp_hh + mid_hi + lo_carry
    return (hi, lo)
end
```

```julia
"""
    _shiftRightJam128(a_hi, a_lo, dist) -> (hi, lo)

Branchless 128-bit right shift with sticky jam, semantics per Berkeley
SoftFloat 3 `s_shiftRightJam128.c`. All bits shifted out of the bottom
are OR-reduced into bit 0 of the returned low limb.

  dist ≤ 0    → no shift
  0 < d < 64  → hi' = hi >> d
                lo' = (hi << (64-d)) | (lo >> d) | sticky_of(lo_low_d_bits)
  64 ≤ d<128  → hi' = 0
                lo' = (hi >> (d-64)) | sticky_of(low_bits_including_lo)
  d ≥ 128     → hi' = 0; lo' = (hi | lo) != 0 ? 1 : 0

All paths computed unconditionally; selected with `ifelse`. Handles
Julia's `x << 64 == x` shift-count-truncation quirk by using an explicit
mask rather than `x << (64 - d)` when d == 0.
"""
@inline function _shiftRightJam128(a_hi::UInt64, a_lo::UInt64, dist::Int64)
    nonpos = dist <= Int64(0)

    # Case A: 0 < d < 64. Use a clamped d' ∈ [1, 63] for mask/shift safety.
    dA = clamp(dist, Int64(1), Int64(63))
    dA_u = UInt64(dA)
    lostA_mask = (UInt64(1) << dA_u) - UInt64(1)
    stickyA = ifelse((a_lo & lostA_mask) != UInt64(0), UInt64(1), UInt64(0))
    hiA = a_hi >> dA_u
    loA = (a_hi << (UInt64(64) - dA_u)) | (a_lo >> dA_u) | stickyA

    # Case B: 64 ≤ d < 128. Use clamped d' ∈ [64, 127] and shift by d-64.
    dB = clamp(dist, Int64(64), Int64(127))
    dB_u = UInt64(dB - Int64(64))   # 0..63
    hi_lost_mask_B = (UInt64(1) << dB_u) - UInt64(1)
    stickyB = ifelse((a_lo != UInt64(0)) | ((a_hi & hi_lost_mask_B) != UInt64(0)),
                     UInt64(1), UInt64(0))
    hiB = UInt64(0)
    loB = (a_hi >> dB_u) | stickyB

    # Case C: d ≥ 128. Everything sticky.
    hiC = UInt64(0)
    loC = ifelse((a_hi | a_lo) != UInt64(0), UInt64(1), UInt64(0))

    # Select: nonpos → (a_hi, a_lo); d < 64 → A; d < 128 → B; else C.
    big = dist >= Int64(128)
    mid = dist >= Int64(64)
    hi_sel = ifelse(big, hiC, ifelse(mid, hiB, hiA))
    lo_sel = ifelse(big, loC, ifelse(mid, loB, loA))
    hi = ifelse(nonpos, a_hi, hi_sel)
    lo = ifelse(nonpos, a_lo, lo_sel)
    return (hi, lo)
end
```

```julia
"""
    _sf_clz128_to_hi_bit61(hi, lo, e) -> (hi, lo, e)

Normalize the 128-bit value `(hi << 64) | lo` so its leading 1 is at
bit 125 (= bit 61 of `hi`). Decrements exponent `e` by the shift count
and propagates bits from `lo` into `hi` at each stage. Six-stage
branchless binary-search CLZ over the 128-bit value.

Used by `soft_fma` because Berkeley's `<<10`/`<<9` scaling convention
places the normalized 128-bit product's leading 1 at bit 125. After
opposite-sign subtraction with cancellation, leading 1 drops below 125;
this helper shifts it back, bringing up low-limb bits into the high
limb so no precision is lost. Callers must pre-normalize any bits above
bit 125 (via `>>1 with sticky`) before calling.

Precondition: `(hi, lo) != (0, 0)` and leading 1 at position ≤ 125.
Callers that might pass the zero pair substitute `hi = UInt64(1)`
(value recovered via the select chain).
"""
@inline function _sf_clz128_to_hi_bit61(hi::UInt64, lo::UInt64, e::Int64)
    need32 = (hi & (UInt64(0xFFFFFFFF) << 30)) == UInt64(0)
    hi = ifelse(need32, (hi << 32) | (lo >> 32), hi)
    lo = ifelse(need32, lo << 32, lo)
    e  = ifelse(need32, e - Int64(32), e)
    # … five further stages, k ∈ {16, 8, 4, 2, 1}, masks
    #   (0xFFFF << 46), (0xFF << 54), (0xF << 58), (0x3 << 60), (1 << 61),
    #   and the same four-line body with `lo >> (64 - k)` in the merge …
    return (hi, lo, e)
end
```

## 2. Gate sequence as an indexed block table

### 2.0 Grain, spans, and the three representation rules

**Grain is LITERAL, per PRD-v2 §7.2** — *"One block per operator occurrence as the
source spells it; every intermediate a 64-bit span (the Julia type's width); no
common-subexpression sharing; no narrowing towards the field width."* K15.md §2.0
states the three readings this makes necessary and **K20 adopts them verbatim**;
they are summarised here only so §2.2 is readable, and K15 is the source of record:

- **"the Julia type's width" is the DECLARED type**, so a `Bool` is ONE bit and a
  `UInt64`/`Int64` is SIXTY-FOUR. `a_nan`, `same_sign`, `underflow`, `need32`,
  `nonpos`, `big`, `mid` … are `Bool` and get one-bit spans; `sa`, `ea`, `expZ`,
  `expDiff`, `expR`, `p_hi`, `p_lo`, `wr_56` are 64-bit spans. Every
  `ifelse(Bool, UInt64, UInt64)` therefore lands on `cq_mux_block` unchanged —
  `cond` one bit, arms `W` bits, which is M17's declared shape (`mux.h`, *"one bit;
  only `cond[0]` is read"*).
- **`Int64` and `UInt64` are the same 64 `cq_bit`s.** `Int64(ea)` (`fma.jl:64`),
  `UInt64(dA)` (`softfloat_common.jl:381`) and `UInt64(dB - 64)` (`:389`) are
  reinterprets: **wiring**, zero gates, zero qubits. What changes is which
  comparator the *next* row uses. **K20 has 15 signed compares and 5 unsigned ones
  and they are not interchangeable** — §2.2 names the family in every compare row
  and §6's risk 2 is that one of them gets the wrong one.
- **No CSE means no CSE.** §5.1 lists K20's fourteen repeated subexpressions.

**Three representation rules**, K15.md §2.0's, unchanged:

1. **A block** — anything that computes a new value. Every
   `+ - * & | ⊻ ~ == != < <= > >=` and every `ifelse`, and the variable-amount
   shifts. It targets a fresh scratch span; its gates are the owning module's step
   function.
2. **A view — zero gates, zero qubits** — a **constant-amount** shift and a
   reinterpret. K12.md §2.1's precedent: *"The left shift is therefore a relabelling
   of `cq_bit` array entries and costs zero gates and zero qubits (Rule 3 — a
   `cq_bit` is a value, not a wire)."* It **must be rebuilt from the step index on
   every call** and never carried in mutable state, it is sound because a scratch
   span's `cq_bit` entries never change kind mid-half (I6(b)), and the vacated lanes
   are literal `CQ_BIT_ZERO`. **K20 has 61 view rows**, more than K15's 20, because
   the whole Berkeley scaling (`<<10`, `<<10`, `<<9`), the widemul's 32-bit
   halving, both by-one shifters and all eighteen of the CLZ's shifts are constant
   amounts.
3. **A constant is a SOURCE, never scratch** — PRD-v2 §7.3, verbatim: *"We pass them
   as `const cq_bit` arrays of `CQ_BIT_ZERO`/`CQ_BIT_ONE` and the §3 fold table
   elides every gate they control."* `FRAC_MASK`, `IMPLICIT`, `INF_BITS`,
   `QUIET_BIT`, `INDEF`, `0x7FF`, `0x3FE`, `0xFFFFFFFF`, `0x2000000000000000`,
   `0x3F`, `(1<<56)-1`, `0`, `1`, `−1`, `64`, `63`, `127`, `128`, the all-ones mask
   `_neg128` needs for `~`, and the six CLZ masks are file-static `cq_bit[64]`
   tables. They cost **zero qubits**.

> **THE `a & FRAC_MASK` DISAGREEMENT IS K15's AND IS INHERITED UNRESOLVED.** A mask
> by a *constant* is bit-for-bit a relabel and could be a rule-2 view; PRD-v2 §7.3's
> own worked example costs it as a block — *"`a & ~SIGN_MASK` costs zero gates and
> zero qubits on classical lanes and **one CX per quantum lane**"* — and §2.2
> follows the PRD. **For K20 the delta is 23 `and` rows at 64 bits: 1,472 slots and
> 1,472 scratch qubits.** It is a **PRD amendment**, not a kernel choice, and
> `9ve.24` must not settle it in code. K15.md §2.0's box is the statement of record.

**Constants make the fold table fire deterministically, and in K20 that is worth
more than anywhere else in the catalogue.** Under I6(b) every scratch bit is
`CQ_BIT_Q`, so a slot whose controls are all scratch emits; a slot whose only
control is a constant `CQ_BIT_ZERO` emits **nothing** and one whose control is
`CQ_BIT_ONE` emits a **demoted** gate. This is not mask-dependence — a constant is
constant at every operand mask — but **slots ≠ gates, permanently**, and §2.6 and
§3 both turn on it. The four `cq_mul_block`s are where it bites hardest: their
operands' top 32 lanes are `CQ_BIT_ZERO` by construction (§2.2 phase F), so a large
fraction of their Toffolis fold and **none of their CNOTs do** (K11 §7.5's measured
shape).

### 2.1 Scratch layout — flat, one tape, offsets in spans

**FLAT, as K12's and K15's are** (PRD §15 D9). One `cq_scratch` region, laid out in

### 2.2 The block table — 376 rows in SOURCE ORDER

**Reading instructions.** One row per **operator occurrence** in §1's Julia. `V` =
view (rule 2: zero slots, zero gates, zero qubits). `C_x(w)` is the cost of block `x`
at width `w`, **asked of its module and never written down** — §3.0. `Kn` denotes a
`const cq_bit[64]` constant source (rule 3). Every `ifelse` row names its `cond`
first. Where a compare's *raw* flag has the wrong sense the row carries `+1`, one `X`
on the block's own flag bit, which is scratch and therefore I6(a)-legal and
self-inverse. A row citing `c:NNN` is a line of `softfloat_common.jl`; a bare `:NNN`
is a line of `fma.jl`.

**`==` is `C_eq(W) + 1` and `!=` is `C_eq(W)`.** The eq/ne block's raw flag holds
`a != b` (`cmp.h`, *"`orr[W-2]` IS `a != b`"*), so `!=` reads it directly and `==`
flips it in place. The comparators run the other way: the `ult`-family raw flag holds
`a >=u b` (`cmp.h`, *"`carry[W]` IS `a >=u b`"*) and the `slt`-family raw flag holds
`a >=s b` (K09 §2.3), so `>=` and `<=` are free and `<` and `>` cost the `+1`.

**Helper instantiations are written out ONCE and counted ONCE PER OCCURRENCE.**
`_shiftRightJam128` is expanded below as sub-table `H-*`; `fma.jl:99` and
`fma.jl:110` are **two separate instantiations** with two separate scratch extents
and two separate runs of every row — no CSE, §7.2 — so every `H-*` row is counted
**twice** in §3.1. The same holds for `_shr128jam_by1` (three instantiations, at
`:100`, `:154`, `:162`), for `_sf_normalize_to_bit52` (three, at `:67`-`:69`) and
for `_sf_clz128_to_hi_bit61`'s six written-out stages.

> ### UPSTREAM'S 128-BIT ADD NEEDS NO CARRY-IN, AND THAT IS THE ANSWER TO THE
> QUESTION `9ve.30` WOULD OTHERWISE RAISE
>
> The reflex when chaining two 64-bit adders into a 128-bit one is to ask M14 for a
> **carry-in** and a **carry-out**, and to discover that K6 exposes neither usefully:
> `add.h`'s shipped `cq_sub_block` has `c` (the carry chain) but `cq_sub_step` *"emits
> no carry-OUT, because `lower_sub!`'s `i < W` guard drops the top stage's two
> Toffolis"*, and K06 §2's own step table ends the top bit at `j == 0,1,2` with the
> comment *"top bit: no carry-out is produced"*. K6's `c[0]` **is** described as *"the
> carry-in, never a target"*, so a carry-IN is bindable in principle — but the block's
> declared vector would be a non-`const` `cq_bit *`, and there is **no carry-out to
> bind it to**.
>
> **None of that matters, because upstream does not chain the carry.** `_add128`
> (`softfloat_common.jl:299-304`) materialises the carry as a **value**:
> `carry = ifelse(lo < a_lo, 1, 0)` — an unsigned compare plus a mux — and then adds
> it as an ordinary 64-bit operand, `hi = a_hi + b_hi + carry`, which under §7.2's
> grain is **two** `add` blocks. `_sub128` does the same with a borrow, `_neg128` the
> same with `lo == 0`. So rows I1–I10 and I17–I22 need from M14 exactly **one thing
> and nothing else: a plain out-of-place `cq_add_block` / `cq_add_step` at `W = 64`,

**64 CX**, and `dst` is written nowhere else. That is Rule 7's `^=`, and it is the

### 2.4 I6(a) and I6(b)

**I6(a) — every compute-half gate target a kernel names is scratch. YES, by
construction and not by inspection.** Every row of §2.2 is either a view (emits
nothing) or a block whose targets are the block's own vectors, laid inside K20's one
scratch region. The three rails `a`, `b`, `c` appear in rows A1–A12, N2, N3, O10,
O16–O18 and **only ever as `const cq_bit *` controls**, which `cq_emit_*`'s signature
makes structural (Rule 8's first enforcement mechanism). The constant tables are
`const` for the same reason. The five hand-off rows — D19–D21, M1, M2 — inherit the
obligation and must be checked in their own beads, not here.

**Two block families need their own sentence because they take a region rather than
vectors.** `cq_mul_block` and `cq_barrel_block` carry `cq_scratch *scr` + `uint32_t
off` rather than named `cq_bit *` spans (`mul.h`, `shift_var.h`), which is M19's shape
and is chosen for M08's reason — *"`emit.c`'s I6(a) check is a pointer RANGE test over
ONE extent, so a consumer allocates one region and hands out offsets rather than
allocating a second"* (K11 §7.1). K20 allocates **one** region and hands each of its
four `mul` blocks and twelve barrel blocks a distinct `off`. **K11 §7.5's measured
finding applies directly**: a block cannot see its own base address, so a dropped
`k->off +` is invisible until a **second** block lands on the first —
`the_two_blocks_in_one_region_do_not_collide` was *"the one case of nineteen that went
red"*. K20 has sixteen region-taking blocks and is that fixture sixteen times over.

**I6(b) — every scratch bit is `CQ_BIT_Q` for the whole compute half. YES, and it is
the driver's doing.** `cq_sandwich` pre-materialises the whole region before step 0
(plan §0.2), at zero gates, because scratch is born `CQ_BIT_ZERO`. Two consequences
specific to K20:

- **No fold ever fires on a scratch bit**, so every gate whose controls are all
  scratch emits. That is what makes §3's slot arithmetic a function of `W` alone.
- **The folds that DO fire are exactly the constant-source ones** (§2.0 rule 3) **and,
  uniquely in this kernel, the `mul` blocks' zero operand lanes** — which are the
  *outputs of blocks F1–F4*, and therefore `CQ_BIT_Q` under I6(b), and therefore **do
  not fold at all.** That is worth stating because it is counter-intuitive and it is
  the difference between K11 §7.5's measured figures and K20's: §7.5 measured a block
  whose operands were *caller-supplied spans with classical ZERO lanes*; K20's are
  scratch that a preceding `and` block wrote. **At the all-quantum operand mask, K20's
  four `mul` blocks fold nothing and cost the full `4 × cq_mul_steps(64)`.** §6.3.

**The I6(a) extent must cover the views' *underlying* spans, and a view is not a
separate allocation.** `ma_s` is `[K0]×10 ++ ma[0..53]`: reading it as a control reads
`ma`, which is inside the extent. Nothing targets a view. The reflex "assert the
operand arrays are disjoint objects" is the trap K12.md §2.1a records and would reject
all 61 view rows — **guards compare ranges, never base pointers**.

### 2.5 The step dispatch — a static prefix sum, NOT a division

K12's decode is `t = s / K(W)`, `j = s % K(W)`, because its compute half is `W`
identical iterations. **K20's compute half is straight-line: `soft_fma` contains no
loop at all** — the CLZ is six written-out stages, not a loop — so there is no modulus.
The dispatch is K15's:

```
/* built once, at kernel entry, from the 376-row table of §2.2 */
static int off[377];        /* off[0] = 0; off[n+1] = off[n] + slots(row n) */

step(s):
    n = upper_bound(off, s) - 1      /* which row owns slot s */
    u = s - off[n]                   /* the row's own index    */
    dispatch on row n's block type:
        and/or/xor  -> emit directly, bit u / (gates per bit)
        eq | ne     -> cq_eq_step    (block_n, u)      [ + trailing X for `==` ]
        ult family  -> cq_ult_step   (block_n, u)      [ + trailing X for `<`/`>` ]
        slt family  -> cq_slt_step   (block_n, u)      [ 9ve.31 ]
        add         -> cq_add_step   (block_n, u)      [ 9ve.30 ]
        sub         -> cq_sub_step   (block_n, u)
        mux         -> cq_mux_step   (block_n, u)

```

**`off[]` must be a pure function of `W` and of nothing else** — the driver replays
indices in reverse and a table rebuilt from mutable state would desynchronise the
halves. Building it once at entry from `cq_ult_steps(64)`, `cq_mul_steps(64)`,
`cq_barrel_steps(64, dir)`, … — the **measurements**, never the literals — is what
makes §3.0's composition identity hold by construction rather than by coincidence.

**`cq_barrel_steps` TAKES THE DIRECTION AND K20 HAS SIX OF EACH**, so the two must not
be conflated in `off[]`. K04 §7.4 states why the parameter is forced: *"`shl`/`lshr`
emit `W - 2^k` shuffle CNOTs per stage because the out-of-range source index does not
exist, while `ashr`'s else-branch clamps to the sign bit and writes all `W`."* K20 uses
**no `ashr`** — `_shiftRightJam128` is a logical shift throughout — so all twelve
barrel blocks are `shl` or `lshr` and `cq_barrel_steps(64, ·)` is **1921** for both
(K04 §7.4, measured). A reader who assumes a direction-free count will be right here
by luck and wrong the first time a signed shift appears.

**`upper_bound` is a binary search over 377 entries per step, run ~2 × 10⁵ times per
compute half and twice per call.** That is a few million comparisons per `fma`, noise
beside the gate stream, and worth knowing before someone "optimises" it into a cached
cursor — a cursor is mutable state across steps and is the exact hazard the previous
paragraph forbids.

### 2.6 The slot-scan derivation — **and the op kind is FOUR-VALUED**

**What a K12-shaped kernel gets wrong is the slot arithmetic, not the gates**
(CLAUDE.md's callout), and K20 is K12's shape with **376 boundaries** where K12 has
four and K15 has 172. The instrument is K12's
`the_phase_boundaries_match_an_independent_slot_scan`: re-derive the **op KIND** of
every compute-half slot from the blocks' own structure and compare that against the
recorded stream at the all-quantum operand mask. It records only which of `X` / `CX` /
`CCX` each slot emits — exactly what a boundary error moves and what a gate-list error
does not — so it is not a second transcription of anything.

**THE KIND IS FOUR-VALUED, `{NONE, X, CX, CCX}`, AND THAT IS NOT OPTIONAL.** K12's scan
asserts `cq_mock_count(&m) == 2n + W` and then walks `slot s ↔ stream index s`. That
identity is **false for K20**, because §2.0 rule 3's constant sources make some slots
emit nothing and demote others: `fa = a & FRAC_MASK` is 64 slots and 52 `CX`;
`sticky`'s mux (L5) reads two constant arms and mostly vanishes; `!same_sign` (H8) is
2 slots and 2 gates. The scan must predict `{NONE, X, CX, CCX}` per slot and walk the
stream with a **separate cursor that advances only on non-`NONE`**. A scan that keeps
K12's 1:1 assumption goes red on row A3 and stays red, and the reflex fix — deleting
the constant rows from the prediction — is what turns the instrument off. K15.md §2.6
states the same thing and K20 inherits it verbatim.

**The per-block op-kind sub-schedules are K15.md §2.6's**, each read out of its
module's own K-doc and **none re-derived here**: `sched_and`, `sched_or`, `sched_xor`
(K01/K02/K03 §2, with the constant-operand rows), `sched_eq` (K09 §2.1, `5W−3` slots),
`sched_ult` (K09 §2.2, `6W+1`), `sched_slt` (K09 §2.3, `8W+3`), `sched_add` (K06 §2,
`5W−2`), `sched_sub` (K07 / `add.h`, `7W−1`), `sched_mux` (K10 §2.1, 4 per bit),
`sched_barrel` (K10 §2.2). **K20 needs one more that K15 did not**, and it is not
restated here either:

```
/* K11 §2b — mul. TWO PHASES, and the schedule is M18's. Asked, not written down. */
sched_mul (W, v) : per outer j in [0, W):
                     phase P:  (W - j) slots, each CCX(a[k], b[j] -> pp[j][k+j])
                               /* multiplier.jl:26's truncation means the dropped
                                  positions are NOT slots — one gate per slot holds */
                     phase A:  6W-5 slots, each cq_addacc_step's — K08's schedule,
                               which K20 does not transcribe and must not
```

**The top-level decode the scan re-derives** is the prefix sum over §2.2's table **as
this document writes it**, with each row's length obtained by calling
`cq_ult_steps(64)`, `cq_mul_steps(64)`, `cq_barrel_steps(64, dir)`, `cq_mux_steps(64)`,
… and **never** by reading M39's own `off[]`. That is the independence: the doc's table
against the code's table. A scan that reads `off[]` proves the array is self-consistent
and nothing else.

**Five boundaries are worth a named case**, because an off-by-one there produces a
plausible gate rather than a crash:

1. **The F4 ↔ F5 seam** — the last view of the widemul's operand split against the
   first `CCX` of `pp_ll`. Both sides are structural; only the *operands* differ.
2. **The four `mul` blocks against each other** (F5–F8). Four identical schedules in a
   row, `4 × 26,336` slots, and a boundary error is absorbed by the next block —
   exactly the "repeating structure" hazard, and the largest instance of it anywhere in
   the catalogue.
3. **The two `_shiftRightJam128` instantiations** (H-* at `:99` and at `:110`), for the
   same reason at 45 rows each.
4. **The six CLZ stages** (K-Z*k*), the third repeating structure.
5. **The H16 ↔ I1 seam**, which is the Rule 12 split point: the last mux of
   PRODUCT-AND-ALIGN against the first `CX` of the adder. Both are `CX`, so only L1
   sees a mis-wire.

`sh_k`/`d_k`/`r_k`, and the `mul` blocks' `pp[j]` arrays and Cuccaro ancillae.
Constants contribute **zero**: they are `const cq_bit` tables (§2.0 rule 3). Views
contribute **zero**: they are relabellings.

**Against upstream's 135,743 we are LOWER by roughly 70k bits — about a factor of two —
and PRD-v2 §7.3 predicted the direction before this was counted**: *"Our peak is
therefore BELOW upstream's ancilla figure for the same construction, and the difference
is not a bug to chase in either direction."* Four sources of the gap:

1. **Constants.** Nineteen distinct 64-bit constants appear in §2.2, several used ten
   or more times; upstream allocates a fresh wire per constant **per use**
   (`arith.jl:202`), we allocate none.
2. **`uge`/`sge` read the raw flag.** Every `>=`/`<=` row reads `carry[W]` (or the
   signed equivalent) directly instead of materialising `not1(ult(…))` — PRD §15 D9(b),
   already the shipped shape (K09 §5 delta 2). **K20 has seven such rows**
   (`nonpos`, `big`, `mid`, ×2 instantiations, plus G1's `==` which is the eq block's
   own inversion) against K15's four.
3. **Views.** Sixty-one rows that upstream lowers as real shifts, including all
   eighteen of the CLZ's and all three of the Berkeley scalings.
4. **K11's Cuccaro delta.** `cq_mul_region(64) = 4,224` is the Cuccaro accumulator's
   footprint, a deliberate v1 departure from upstream's ripple that CLAUDE.md records
   as *"saving ~3× scratch"*. Four blocks at 4,224 rather than at ~12.7k is most of a
   34k-bit difference on its own.

Pulling the other way: **literal grain costs us** wherever LLVM would have CSE'd —
§5.1's fourteen repeated subexpressions, of which ten are `eq`/`ne` blocks at 127 bits
each, so about **1.5k bits** upstream's optimiser removes. That is PRD-v2 §7.2's price
and it is paid on purpose. It is small against the 70k gap, which is the useful thing
to know: **the grain is not what drives K20's peak; the `mul` and barrel regions are.**

> **R11 IS LIVE AND IT IS NOT A DEFECT, AND K20 IS ITS WORST CASE IN v2.** 65.5k qubits
> against K12 i8's 543 is ~120×, against K15's 21.3k is ~3×, and D2/D20's pool ceiling
> is a **hard** one. PRD-v2 §4's R11 already records the disposition: the abort comes
> **from the pool during pre-materialisation**, unswallowed at the opcode surface, and
> **D25's prohibition is the live one — the shim must never grow its own "that will not
> fit" check.** Do not add one to M39 either. The number that matters operationally is
> not the peak but the peak **plus** whatever a caller already holds, since a CQ program
> calling `fma` in a loop holds its rails across the call.

> **A `qec_n_logical`-BOUNDED POOL WILL REFUSE THIS KERNEL ON MOST CONFIGURATIONS, AND
> THAT IS THE CORRECT BEHAVIOUR.** D2 sets the ceiling to `qec_n_logical` when the QEC
> sink is active. 65.5k logical qubits is not a modest device. The refusal is loud, it
> comes from M03, and it names the pool — which is exactly what a caller needs in order
> to decide whether to run `fma` at all. Reading it as a libcqops bug is R11.

### 5.5 PRD-v2 §5's *"Reuses M33's align and M34's product"* is a BLOCK-VOCABULARY claim, not a body-sharing one

**Measured against the snapshot, `fma` shares no body with either.**

**The product.** `soft_fmul` splits each 53-bit significand into a high **27** and a
low **26** and forms its four products inline (`fmul.jl:73-81`), with its own carry
assembly at `:92-100`. `soft_fma` calls `_sf_widemul_u64_to_128`, which splits at
**32/32** (`softfloat_common.jl:266-269`). The helper's docstring states the reason and
it is load-bearing rather than stylistic:

> *"General-purpose (vs. the 27×26 decomposition inlined in `soft_fmul`, which assumes
> ≤53-bit inputs). Used by `soft_fma` with Berkeley-scaled 63-bit inputs (`ma << 10`,
> `mb << 10`)."* — `softfloat_common.jl:261-263`

`ma_s = ma << 10` is up to **63** bits, so `fmul`'s 27/26 split would overflow a
`UInt64` partial product. **An implementer who "reuses M34's product" gets a silently
wrong high limb on any operand whose scaled significand exceeds 53 bits — which is
every normalised operand.** What `fma` genuinely reuses is **M18's `cq_mul_block`**,
which is what M34 reuses too: the same integer block, at a different split, four times
in each case.

**The align.** `soft_fadd`'s alignment is a **64-bit** `wb >> d | sticky` with a
`d ≥ 56` / `d > 0` / else select (`fadd.jl:73-83`), 17 rows in K15.md's phase G.
`soft_fma`'s is `_shiftRightJam128` over a **128-bit** `(hi, lo)` pair with four cases
(`nonpos`, `0 < d < 64`, `64 ≤ d < 128`, `d ≥ 128`), 45 rows, **instantiated twice**,
plus a `_shr128jam_by1` special case for Berkeley's `expDiff == −1` precision trick that
`fadd` has no analogue of. **Different helper, different width, different case
structure, and different D8 verdict (§5.3's box).** M33 exporting its ALIGN half — which
its own Rule 12 seam contemplates — gives M39 nothing it can call.

**So the accurate statement of PRD-v2 §5's M39 row is:**

> `fma` reuses the **block vocabulary** M33 and M34 reuse — M18's `cq_mul_block`, M12's
> barrel, M16's `eq`/`ult`/`slt`, M17's mux, M14's `add`/`sub` — and M32's shared tail.
> It reuses **neither M33's align body nor M34's product body**, because upstream
> deliberately gives it different ones.

**This is a §5 amendment, and this document does not make it.** It is recorded because
an implementer reading the current row will look for an `M33_align_step` to call, will
not find one, and may reach for `fadd`'s 64-bit shape — which is the wrong construction
and is invisible to every structural check. §6.5 risk 1.

  substitutable and CLAUDE.md says why: in-place, destructive in `acc`, *"transiently

  *"it may never be substituted for K6/K7: the forward value would be right and only the

  every one of its twelve adds to leave both operands intact — rows I4/I5 and I9/I10

  **`cq_add_block` / `cq_add_step` / `cq_add_steps` must be added**, as `k6_compute`'s
  exported form: `5W − 2` slots, scratch `t` (the sum, and the output) and `c` (the

  compares them fifteen times. Routing those through the **unsigned** block is a wrong
  answer for every negative value, which is roughly half the input space, and it is
  invisible to the slot scan, to L4 and to the palindrome — because `slt`'s compute half
  *is* `ult`'s with a two-gate sign-flip prologue (K09 §2.3). **Only L1 sees it.**
  `cq_slt_block` / `cq_slt_step` / `cq_slt_steps` must be added: `8W + 3` slots,
  `5W + 1` scratch.

**Two of these are prerequisites for `9ve.24` and neither is new** — `9ve.30` and
`9ve.31` were filed by K15.md's block table on 2026-09-18 and are already in PRD-v2 §5's

### 5.x L1's anchors for `fma` — PRD-v2 §7.12, refined against this source's predicates

**PRD-v2 §7.12 requires it**: *"Per kernel the list is refined against the source's own
special-case predicates (`a_nan`, `a_inf`, `a_zero`, `swap`, `d ≥ 56`, …): each named
predicate gets an anchor that makes it true, because each is a branch of the `ifelse`
tree that a random draw of 32 reaches with no guarantee."* The budget stays
`cq_kd_samples() = 32`; these are **forced into every draw**, not pooled.

**THE PROVIDER MUST NAME THE THIRD OPERAND, AND THIS IS THE `cq_kd_case2` TRAP IN ITS
CURRENT FORM.** `tests/support/kerneldrv.h` fixes the contract: *"IT OVERWRITES, IT DOES
NOT FILL. The sampler draws a random value per operand at its own width FIRST and then
lets the provider overwrite the operands it names, so a three-source kernel whose
provider names two of them still gets a drawn third."* `cq_fp_anchors_binary`
(`tests/support/fpanchors.h`) *"Writes v[0] and v[1] and NOTHING ELSE"* — so composing
it alone gives `fma` a **randomly drawn `c`**, which is fine for a sampler and **useless
for every anchor below whose whole point is the relation between `a·b` and `c`**.
`fma`'s own provider must therefore compose `cq_fp_anchors_binary` for the operand-pair
rows *and write `v[2]` explicitly on every row it owns*. Filling `v[2]` with zero
instead is the recorded `cq_kd_case2` trap — *"every mux case run with one arm pinned at
0, green, and half a kernel"* — one edit away, in a kernel whose third operand is the
addend.

**Anchor 26 is the Kahan single-rounding witness and it is derived here rather than
guessed.** `(1 + 2⁻⁵²)² = 1 + 2⁻⁵¹ + 2⁻¹⁰⁴` exactly. Near 1 the ulp is `2⁻⁵²`, so
`1 + 2⁻⁵¹` is representable (fraction field `2`, i.e. `3ff0000000000002`) and the
residual `2⁻¹⁰⁴` is far below the half-ulp `2⁻⁵³` — so `fl(a·b) = 3ff0000000000002`,
**not a tie**. With `c = −fl(a·b)`, a **fused** `fma` returns
`(1 + 2⁻⁵¹ + 2⁻¹⁰⁴) − (1 + 2⁻⁵¹) = 2⁻¹⁰⁴`, biased exponent `1023 − 104 = 919 = 0x397`,
fraction zero. A **double-rounded** `fmul`-then-`fadd` returns `fl(a·b) − fl(a·b) = +0`.
**The two answers are `3970000000000000` and `0000000000000000`** — maximally
distinguishable, and the single case that would go red if anyone ever spelled M39 as
`fmul` then `fadd`. It also drives `hi_zero`, the deep CLZ and `complete_cancel = false`
in one input. **This derivation is UNVERIFIED-BY-EXECUTION (§6.3); check it against the
host `fma()` in the oracle, not against the transcription.**

**Anchors 27 and 28 are the `complete_cancel` sign rule** (§1.1a's box): `fma.jl:202`
returns `UInt64(0)`, positive zero, at **every** operand sign combination. A port that
writes `result_sign << 63` there passes anchor 27 and fails anchor 28.

### 5.y The classical short-circuit — a C transcription over `uint64_t` pairs, never the host

Risk R9's short-circuit applies: all-classical operands never enter the sandwich and
`dst` is written as constants. **PRD-v2 §7.4 forbids computing those constants with the
host `double` operator**, on a measurement, and `fma` reaches **four** of its five
IEEE-unspecified cells:

| cell | reached from | this box (x86_64) | the circuit |
|---|---|---|---|
| `0 · Inf` | `fma.jl:207`'s `inf_times_zero` | `fff8000000000000` | `INDEF` |
| `Inf − Inf` | `fma.jl:206`'s `inf_clash` | `fff8000000000000` | `INDEF` |
| `qNaN₁ ⊕ qNaN₂` | `fma.jl:208` / `_sf_propagate_nan3` | the FIRST operand's payload | first operand, by `a > b > c` |
| `qNaN + sNaN`, both orders | same | **the first operand, quietened** (PRD-v2 §7.4's 2026-09-18 correction) | quietened operand, upstream's priority |

They agree **on this box** and would not on arm64, so a host-operator short-circuit
gives a program whose classical mode and quantum mode return different bits on the same
input, on some hosts only.

**So `cq_fma_classical(uint64_t a, uint64_t b, uint64_t c)` is a C transcription of
§1.1's Julia over `uint64_t`** — the same source, evaluated on constants. Five riders,
and the first is specific to `fma`:

- **IT NEEDS `(hi, lo)` PAIRS, AND THE TYPE IS A SMALL STRUCT — NEVER
  `unsigned __int128`, AND NEVER THE HOST `fma()`.** Nine of the eleven helpers return
  or consume a 128-bit value: `_sf_widemul_u64_to_128`, `_add128`, `_sub128`,
  `_neg128`, `_shl128_by1`, `_shr128jam_by1`, `_shiftRightJam128` (pairs in and out),
  `_sf_clz128_to_hi_bit61` (a pair plus an `int64_t`). In C11 that is
  `typedef struct { uint64_t hi, lo; } cq_u128;` and a handful of out-params, or nine
  small functions returning it by value. **`unsigned __int128` is refused for two
  independent reasons**: upstream declined native `UInt128` deliberately —
  *"the helpers' explicit hi/lo decomposition is the direct ancestor of the gate
  sequence soft_fma emits"* (`softfloat_common.jl:244-246`) — so a `__int128` C arm
  would stop being line-for-line checkable against the circuit, which is the entire
  point of §7.4; and it is not C11, it is a compiler extension, against PRD §14's
  *"nothing beyond libc"*. **The host `fma()` is refused twice over**: it is `double`
  arithmetic (§7.4), and on some platforms it is not even correctly rounded — a libm
  `fma` that falls back to a double-rounded emulation returns the *wrong* answer for
  anchor 26, which is the one value this kernel exists to get right.
- **`-ffp-contract=off`'s reason does not reach here**: the transcription is integer
  only and touches no `double`. The library's only contact with a C `double` in the fp
  surface is the `memcpy` at `cqrt_alloc_f64` / `cqrt_measure_f64` (PRD-v2 §3.1).
- **L1's oracle stays INDEPENDENT**: it is the host `fma()` with the four cells above
  **pinned by table as literals** (`tests/support/fphost.h`'s constants), so the
  reference does not reuse the transcription. An oracle sharing code with the
  implementation is blind to what that code gets wrong.
- **`tests/support/`'s host probe** (PRD-v2 §7.4, `cmake/CqopsFpHost.cmake`,
  `tests/support/fphost.c`) — round-to-nearest, FTZ/DAZ off — must be in place before
  anchors 52–54, or a host with FTZ set fails them in the *oracle* rather than in the
  port. **It should additionally probe that the host `fma()` is fused**, since an
  unfused one fails anchor 26 in the oracle; that is a new probe arm and is not in
  `9ve.4`'s landed set.
- **Cost: ~150 lines**, roughly 2.5× K15's ~60, one C function per Julia helper. That
  is a real fraction of M39's 260-LOC budget and argues for the classical arm living in
  its own TU beside the kernel — a Rule 12 question for `9ve.24`, not a decision here.

### 6.5 Ranked risks

1. **PRD-v2 §5's M39 ROW POINTS AT TWO BODIES THAT DO NOT EXIST FOR `fma`** (§5.5).
   *"Reuses M33's align and M34's product"* is true of the block vocabulary and false of
   the bodies: `fma`'s product is `_sf_widemul_u64_to_128`'s **32/32** split, chosen
   because `fmul`'s **27/26** one *"assumes ≤53-bit inputs"* and `fma`'s Berkeley-scaled
   operands are 63 bits; `fma`'s align is a 128-bit four-case `_shiftRightJam128`
   instantiated twice where `fadd`'s is a 64-bit one-case shift. **An implementer who
   follows the row gets a silently wrong high limb on every normalised operand.** It
   ranks first because the PRD is the document an implementer reads and this K-doc is
   the one they might not. Fix it in PRD-v2 §5.
2. **FIFTEEN SIGNED COMPARES, AND THE UNSIGNED BLOCK IS THE ONE THAT EXISTS** (§5.3's
   box, §5.7). `expDiff`, `dist` and `shift_sub` are `Int64` and genuinely negative on
   roughly half the input space. `cq_slt_block` does not exist (`9ve.31`), `cq_ult_block`
   does, and substituting it is **invisible to the slot scan, to L4 and to the
   palindrome** because `slt`'s compute half is `ult`'s plus a two-gate prologue. Only L1
   sees it. This is K9's `uge`-meaning-`ule` for the fourth time in this repo and the
   first time at fifteen sites.
3. **THE G/R/S HAND-OFF TO M32, AND THE SINGLE-ROUNDING BOUNDARY ABOVE IT** (§2.2 phase
   L, §1.3). `wr_56`'s format — implicit 1 at bit 55, fraction 54–3, G/R/S at 2/1/0 — is
   a contract between M39 and M32 that **no C type expresses**, and K20 reaches it
   through a 128-bit CLZ plus a `>> 6` rather than `fadd`'s direct route. A one-bit
   disagreement is right on every input that does not round and wrong on the ties, so
   L1's 32 random samples reach it essentially never and only anchors 47–50 and 53 see
   it. It also crosses a bead boundary (`9ve.19` ↔ `9ve.24`), which is where contracts go
   to be assumed.
4. **THE SLOT ARITHMETIC — 376 BOUNDARIES, THREE REPEATING STRUCTURES** (§2.6). The
   instrument is the four-valued slot scan and it is the single most important thing
   `9ve.24` writes, before the kernel. Three hazards inside it: the op kind must be
   **four-valued** (a constant-folded slot emits nothing, so slot index is not stream
   index — the assumption K12's scan is built on); the four consecutive `mul` blocks and
   the six CLZ stages and the two `_shiftRightJam128` instantiations are three places
   where an off-by-one is **absorbed by the next group** and produces a plausible gate;
   and sixteen region-taking blocks share one `cq_scratch`, where K11 §7.5 measured that
   a dropped `k->off +` is invisible until a second block collides.
5. **THE `mul`-NARROWING MUTANT IS 40% OF THE KERNEL AND LOOKS EXACTLY LIKE AN
   OPTIMISATION** (§2.2 phase F's first box, §3.3 case 3). `cq_mul_steps(64) = 26,336`
   against `cq_mul_steps(32) = 6,512`, four times over, on operands whose top 32 lanes
   are provably zero. L1/L2/L3/L5 stay green; `CQOPS_UPDATE_GOLDENS=1` blesses it. This
   is K11's recorded finding at the largest scale it has ever been offered, and the only
   durable detector is the composition check — **written before the kernel**.
6. **TWO OWED v1 EXPORTS, AND ONE WITH A SILENTLY-WRONG SUBSTITUTE** (§5.7). `9ve.30`
   (`cq_add_block`) and `9ve.31` (`cq_slt_block`) are prerequisites. K8's
   `cq_addacc_step` is the tempting stand-in for the first and is *"a silent miscompile
   rather than a test failure"* — right forward, wrong `_unc`. **What is NOT owed, and
   an implementer will think it is: a carry-in/carry-out extension to the add block.**
   §2.2's phase-I box derives from `_add128`'s own spelling that upstream materialises
   the carry as a value; building a carry-chained 128-bit adder instead is a
   re-derivation.
7. **`_sf_normalize_to_bit52` IS UNASSIGNED AND `fma` INSTANTIATES IT THREE TIMES**
   (§5.4). Unassigned, five modules transcribe it and K20's phase D grows from 21 rows
   to ~141. Deciding it changes M39's row count and its LOC budget, so it has to be
   decided **before** `9ve.24` starts, in PRD-v2 §5 — the same shape as K15.md's risk 5,
   one helper further along.
8. **R11's POOL CEILING, AND K20 IS ITS WORST CASE** (§4's boxes). 65.5k qubits is ~120×
   K12 at i8 and ~3× K15, and D2/D20's ceiling is hard. The behaviour is already decided
   (PRD-v2 §4's R11, D25) and the live prohibition is that **neither the shim nor M39 may
   grow its own "that will not fit" check**. Listed here rather than higher because it is
   a known disposition, not an open question.
9. **`clamp` IS NOT A PORT, FOUR TIMES** (§1.4, §5.6). Small, unambiguous, signed, and
   the one construction in K20 that Rule 1 does not cover. It needs the decision K15.md
   already asked for, not an implementer's judgement — and K20 is where the count is
   largest and a `clamp_block` helper is most tempting.
10. **THE §7.3 vs K12 DISAGREEMENT ABOUT CONSTANT MASKS** (§2.0's box). Worth 1,472
    slots and 1,472 qubits here, resolvable only in PRD-v2 §7.3, and easy to settle
    silently in code in either direction.

### 6.6 What this document is for

It is the specification `9ve.24` implements against — **together with PRD-v2 §6.1's
vendoring, in the same commit** — and the thing the composition check and the
four-valued slot scan are written from **before** M39 exists. It is not a status claim:
nothing here is on disk, `cq_fma_steps` does not exist, `fma` is not on the link surface
today, and three of the twelve `C_*` symbols §3.0 depends on are exports that have not
been written and one has not been assigned to a module. Read `bd ready` and the
filesystem for what is true today.
